# frontend/suppliers-management Specification

## Purpose

Раздел административной панели для просмотра списка поставщиков, создания поставщика с валидацией, удаления с подтверждением и изменения адреса существующего поставщика с обработкой ошибок и локализацией EN/RU.

## Requirements

### Requirement: Страница загружает список поставщиков

Система MUST отправлять GET-запрос на `/api/v1/suppliers` с Bearer-авторизацией при загрузке страницы `/suppliers`.

#### Scenario: Запрос с Bearer токеном

- **WHEN** пользователь открывает страницу `/suppliers`
- **THEN** система отправляет GET-запрос на `/api/v1/suppliers` с заголовком `Authorization: Bearer <token>`, где `<token>` — значение из localStorage под ключом `auth_token`

### Requirement: Состояние загрузки отображает skeleton loader

Система MUST отображать skeleton loader во время загрузки списка поставщиков.

#### Scenario: Загрузка данных

- **WHEN** пользователь открывает страницу `/suppliers` и запрос к API находится в процессе выполнения
- **THEN** система отображает skeleton loader вместо таблицы
- **THEN** skeleton содержит 5 строк с заглушками колонок

### Requirement: Успешный ответ с данными отображает таблицу

Система MUST отображать таблицу поставщиков при успешном ответе 200 с непустым массивом.

#### Scenario: Успешный ответ с поставщиками

- **WHEN** GET-запрос на `/api/v1/suppliers` возвращает 200 с массивом поставщиков
- **THEN** система отображает таблицу с колонками: Name, Phone, Country, City, Street
- **THEN** каждая строка соответствует одному поставщику из массива `internal_supplier.Response[]`
- **THEN** колонка "Name" содержит значение поля `name`
- **THEN** колонка "Phone" содержит значение поля `phone_number`
- **THEN** колонки "Country", "City", "Street" содержат значения `address.country`, `address.city`, `address.street`
- **THEN** каждая строка содержит меню действий с пунктами изменения адреса и удаления

### Requirement: Пустой список отображает empty state

Система MUST отображать empty state при успешном ответе 200 с пустым массивом поставщиков.

#### Scenario: Пустой список поставщиков

- **WHEN** GET-запрос на `/api/v1/suppliers` возвращает 200 с пустым массивом `[]`
- **THEN** система отображает сообщение "No suppliers found"
- **THEN** система отображает иллюстрацию или иконку пустого состояния
- **THEN** таблица не отображается

### Requirement: Ошибки списка отображаются на странице

Система MUST отображать сообщение об ошибке при неуспешных ответах на запрос списка и при сетевой ошибке.

#### Scenario: Internal Server Error (500)

- **WHEN** GET-запрос на `/api/v1/suppliers` возвращает 500
- **THEN** система отображает Alert с сообщением из поля `message` ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Server error. Please try again later."
- **THEN** таблица не отображается

#### Scenario: Service Unavailable (503)

- **WHEN** GET-запрос на `/api/v1/suppliers` возвращает 503 (auth service недоступен)
- **THEN** система отображает Alert с сообщением из поля `message` ErrorResponse, если оно присутствует
- **THEN** если поле `message` отсутствует, система отображает "Server error. Please try again later."
- **THEN** таблица не отображается

#### Scenario: Сетевая ошибка без ответа

- **WHEN** GET-запрос на `/api/v1/suppliers` не возвращает ответ (timeout, network error)
- **THEN** система отображает Alert с сообщением "Network error. Please try again."
- **THEN** таблица не отображается

### Requirement: Ошибка 401 завершает сессию

Система MUST обрабатывать ответ 401 как истекший или невалидный токен и завершить сессию.

#### Scenario: Unauthorized response

- **WHEN** GET-запрос на `/api/v1/suppliers` возвращает 401
- **THEN** система удаляет токен из localStorage
- **THEN** система очищает кеш TanStack Query
- **THEN** система перенаправляет пользователя на `/auth/login`

### Requirement: Форма создания поставщика

Система MUST предоставлять форму создания поставщика с полями Name, Phone, Country, City, Street и MUST отправлять данные на `POST /api/v1/suppliers` с Bearer-авторизацией.

#### Scenario: Открытие формы создания

- **WHEN** пользователь находится на странице `/suppliers` и активирует действие создания поставщика
- **THEN** система отображает форму с полями Name, Phone, Country, City, Street

#### Scenario: Успешное создание поставщика

- **WHEN** пользователь отправляет форму с валидными значениями
- **THEN** система отправляет POST-запрос на `/api/v1/suppliers` с телом `{"name": "<name>", "phone_number": "<phone>", "address": {"country": "<country>", "city": "<city>", "street": "<street>"}}`
- **THEN** при ответе 201 система закрывает форму
- **THEN** система инвалидирует кеш списка поставщиков
- **THEN** созданный поставщик отображается в обновлённом списке

#### Scenario: Блокировка повторной отправки

- **WHEN** запрос создания выполняется
- **THEN** кнопка отправки становится disabled и отображает текст выполнения
- **THEN** повторная отправка формы невозможна до завершения запроса

### Requirement: Клиентская валидация формы создания поставщика

Система MUST проверять форму до отправки: обязательность полей, ограничение длины 255 символов для имени и полей адреса, а также соответствие телефона правилу backend.

#### Scenario: Пустые обязательные поля

- **WHEN** пользователь отправляет форму с пустым обязательным полем
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/suppliers` не отправляется

#### Scenario: Превышение длины поля

- **WHEN** значение имени, страны, города или улицы превышает 255 символов
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/suppliers` не отправляется

#### Scenario: Телефон соответствует правилу после нормализации

- **WHEN** телефон после удаления всех символов кроме цифр и ведущего `+` соответствует шаблону `^\+[1-9]\d{7,14}$` (например, `+7 (999) 123-45-67` нормализуется в `+79991234567`)
- **THEN** система считает значение валидным и не блокирует отправку

#### Scenario: Телефон не соответствует правилу после нормализации

- **WHEN** телефон после удаления всех символов кроме цифр и ведущего `+` не соответствует шаблону `^\+[1-9]\d{7,14}$` (например, `8 999 123 45 67` нормализуется в `89991234567` без ведущего `+`)
- **THEN** система отображает сообщение валидации о некорректном телефоне
- **THEN** запрос на `/api/v1/suppliers` не отправляется

#### Scenario: Телефон отправляется без преобразования

- **WHEN** пользователь отправляет форму с телефоном `+7 (999) 123-45-67`
- **THEN** тело POST-запроса содержит поле `phone_number` со значением `+7 (999) 123-45-67` без изменений
- **THEN** нормализация телефона выполняется backend

### Requirement: Ошибки мутаций отображаются и сохраняют ввод

Система MUST отображать понятное сообщение при неуспешном ответе мутации (400, 404, 500, 503 или сетевая ошибка) и MUST сохранять введённые данные в открытой форме.

#### Scenario: Ошибка 400 или 404 с сообщением

- **WHEN** мутация завершается ответом 400 или 404 с полем `message` в ErrorResponse
- **THEN** система отображает сообщение из поля `message`

#### Scenario: Ошибка 400 без сообщения

- **WHEN** мутация завершается ответом 400 без поля `message`
- **THEN** система отображает "Invalid request"

#### Scenario: Ошибка 404 без сообщения

- **WHEN** мутация завершается ответом 404 без поля `message`
- **THEN** система отображает локализованное сообщение о том, что поставщик не найден

#### Scenario: Ошибки сервера и сеть

- **WHEN** мутация завершается ответом 500 или 503 без поля `message`
- **THEN** система отображает "Server error. Please try again later."
- **WHEN** запрос не возвращает ответ (timeout, network error)
- **THEN** система отображает "Network error. Please try again."

#### Scenario: Ввод сохраняется при ошибке отправки формы

- **WHEN** отправка формы завершается ошибкой
- **THEN** форма остаётся открытой
- **THEN** введённые пользователем значения сохранены

#### Scenario: 401 завершает сессию

- **WHEN** мутация завершается ответом 401
- **THEN** система удаляет токен, очищает кеш и перенаправляет на `/auth/login` в соответствии с существующим глобальным поведением

### Requirement: Удаление поставщика с подтверждением

Система MUST предоставлять удаление поставщика из строки списка только после явного подтверждения и MUST отправлять `DELETE /api/v1/suppliers/{id}` с Bearer-авторизацией лишь при подтверждении.

#### Scenario: Подтверждение показывает поставщика

- **WHEN** пользователь активирует удаление в строке поставщика
- **THEN** система отображает диалог подтверждения с именем этого поставщика

#### Scenario: Отмена удаления

- **WHEN** пользователь отменяет подтверждение
- **THEN** запрос на удаление не отправляется
- **THEN** список поставщиков не изменяется

#### Scenario: Успешное удаление

- **WHEN** пользователь подтверждает удаление
- **THEN** система отправляет DELETE-запрос на `/api/v1/suppliers/{id}`
- **THEN** при ответе 204 система закрывает диалог подтверждения
- **THEN** система инвалидирует кеш списка поставщиков
- **THEN** удалённый поставщик отсутствует в обновлённом списке

#### Scenario: Поставщик используется товарами

- **WHEN** запрос удаления завершается ответом 400 с полем `message` `supplier is used by products`
- **THEN** система отображает это сообщение в диалоге подтверждения
- **THEN** список поставщиков не меняется и не инвалидируется

#### Scenario: Блокировка повторного удаления

- **WHEN** запрос удаления выполняется
- **THEN** элементы управления подтверждения становятся disabled
- **THEN** повторная отправка невозможна до завершения запроса

### Requirement: Изменение адреса поставщика из строки списка

Система MUST позволять изменять адрес существующего поставщика из строки списка, MUST предзаполнять форму текущими значениями адреса из загруженного `SupplierResponse` и MUST отправлять на `PATCH /api/v1/suppliers/{id}/address` только адрес.

#### Scenario: Предзаполнение формы адреса

- **WHEN** пользователь активирует изменение адреса в строке поставщика
- **THEN** система отображает форму с текущими значениями `address.country`, `address.city`, `address.street` этого поставщика из загруженного списка
- **THEN** система не выполняет дополнительный запрос за данными поставщика

#### Scenario: Тело запроса содержит только адрес

- **WHEN** пользователь отправляет форму адреса
- **THEN** система отправляет PATCH-запрос на `/api/v1/suppliers/{id}/address` с телом `{"address": {"country": "<country>", "city": "<city>", "street": "<street>"}}`
- **THEN** поля `name` и `phone_number` в запрос не включаются

#### Scenario: Успешное изменение адреса

- **WHEN** сервер отвечает 204 на PATCH-запрос
- **THEN** система закрывает форму
- **THEN** система инвалидирует кеш списка поставщиков
- **THEN** повторное открытие формы адреса для этого поставщика показывает обновлённые значения после обновления списка

#### Scenario: Ошибка изменения адреса

- **WHEN** PATCH-запрос завершается ошибкой 400 или 404 с полем `message`
- **THEN** система отображает сообщение из поля `message`
- **THEN** форма остаётся открытой с сохранёнными значениями

#### Scenario: Отмена изменения адреса

- **WHEN** пользователь отменяет форму адреса
- **THEN** PATCH-запрос не отправляется
- **THEN** данные списка не изменяются

### Requirement: Инвалидация кеша списка поставщиков

Система MUST инвалидировать кеш списка `["suppliers"]` только после успешного завершения мутации (201 для создания, 204 для удаления и изменения адреса) и MUST NOT инвалидировать его при неуспешных запросах.

#### Scenario: Успешная мутация обновляет кеш

- **WHEN** мутация создания, удаления или изменения адреса завершилась успешно
- **THEN** система помечает кеш списка поставщиков устаревшим
- **THEN** список отображает актуальные данные с сервера

#### Scenario: Неуспешная мутация не обновляет кеш

- **WHEN** мутация завершилась ошибкой 400, 404, 500, 503 или сетевой ошибкой
- **THEN** система не инвалидирует кеш списка поставщиков
- **THEN** отображаемые данные списка не изменяются

#### Scenario: 401 очищает кеш глобально

- **WHEN** мутация завершилась ответом 401
- **THEN** кеш очищается существующим глобальным обработчиком 401, а сессия завершается

### Requirement: Локализация раздела поставщиков

Система MUST отображать все тексты раздела поставщиков (заголовки колонок, подписи полей, кнопки, диалоги подтверждения, сообщения валидации и ошибок) на выбранном языке: английском или русском.

#### Scenario: Английский язык

- **WHEN** выбранный язык — английский
- **THEN** заголовки колонок: "Name", "Phone", "Country", "City", "Street"
- **THEN** подписи формы создания, формы адреса, диалога удаления и сообщения валидации отображаются на английском

#### Scenario: Русский язык

- **WHEN** выбранный язык — русский
- **THEN** заголовки колонок: "Имя", "Телефон", "Страна", "Город", "Улица"
- **THEN** подписи формы создания, формы адреса, диалога удаления и сообщения валидации отображаются на русском
