# frontend/user-authentication Specification

## Purpose

Позволяет пользователям административного интерфейса войти в систему с использованием email и пароля через интеграцию с backend API.

## Requirements

### Requirement: Форма входа принимает email и пароль

Система MUST отображать форму входа с полями email и password и кнопкой отправки.

#### Scenario: Форма отображает обязательные поля
- **WHEN** пользователь открывает страницу входа `/auth/login`
- **THEN** система отображает поле email (type="email")
- **THEN** система отображает поле password (type="password")
- **THEN** система отображает кнопку "Sign In"

#### Scenario: Валидация пустых полей на клиенте
- **WHEN** пользователь пытается отправить форму с пустым email
- **THEN** система отображает ошибку валидации "Email is required"
- **THEN** форма не отправляется на сервер

#### Scenario: Валидация пустого пароля на клиенте
- **WHEN** пользователь пытается отправить форму с пустым password
- **THEN** система отображает ошибку валидации "Password is required"
- **THEN** форма не отправляется на сервер

#### Scenario: Валидация формата email на клиенте
- **WHEN** пользователь вводит невалидный email (например, "notanemail")
- **THEN** система отображает ошибку валидации "Invalid email format"
- **THEN** форма не отправляется на сервер

### Requirement: Успешный вход сохраняет токен

Система MUST отправлять credentials на `POST /api/v1/auth`, сохранять полученный JWT-токен в localStorage и перенаправлять пользователя на защищённую страницу при успешном ответе.

#### Scenario: Успешный ответ с токеном
- **WHEN** пользователь отправляет форму с валидными email и password
- **THEN** система отправляет POST-запрос на `/api/v1/auth` с телом `{"email": "<email>", "password": "<password>"}`
- **THEN** при ответе 200 с непустым полем `token` система сохраняет токен в `localStorage` под ключом `auth_token`
- **THEN** система перенаправляет пользователя на `/clients`

#### Scenario: Успешный ответ без токена
- **WHEN** пользователь отправляет форму с валидными email и password
- **THEN** система отправляет POST-запрос на `/api/v1/auth`
- **THEN** при ответе 200 с пустым или отсутствующим полем `token` система отображает ошибку "Authentication failed: no token received"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице входа

### Requirement: Состояние загрузки блокирует повторную отправку

Система MUST отображать индикатор загрузки во время отправки запроса и блокировать повторную отправку формы.

#### Scenario: Загрузка во время запроса
- **WHEN** пользователь отправляет форму
- **THEN** кнопка "Sign In" становится disabled
- **THEN** кнопка отображает текст "Signing in..." вместо "Sign In"
- **THEN** пользователь не может отправить форму повторно до завершения запроса

### Requirement: Ошибки API отображаются пользователю

Система MUST отображать понятное сообщение об ошибке при неуспешном ответе от API.

#### Scenario: Некорректные credentials (400)
- **WHEN** пользователь отправляет форму с некорректными credentials
- **THEN** при ответе 400 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Invalid credentials"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице входа

#### Scenario: Недоступность auth service (502)
- **WHEN** пользователь отправляет форму
- **THEN** при ответе 502 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Authentication service unavailable"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице входа

#### Scenario: Сетевая ошибка без ответа
- **WHEN** запрос на `/api/v1/auth` не возвращает ответ (timeout, network error)
- **THEN** система отображает сообщение "Network error. Please try again."
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице входа

#### Scenario: Занятый email при регистрации (409)
- **WHEN** пользователь отправляет форму регистрации с email, который уже зарегистрирован
- **THEN** при ответе 409 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "User already exists"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице регистрации

#### Scenario: Некорректные данные регистрации (400)
- **WHEN** пользователь отправляет форму регистрации с данными, отклонёнными сервисом авторизации
- **THEN** при ответе 400 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Invalid request"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице регистрации

#### Scenario: Недоступность auth service при сбросе пароля (502)
- **WHEN** пользователь отправляет форму сброса пароля
- **THEN** при ответе 502 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Authentication service unavailable"

#### Scenario: Сетевая ошибка при сбросе пароля
- **WHEN** запрос на `/api/v1/reset` не возвращает ответ (timeout, network error)
- **THEN** система отображает сообщение "Network error. Please try again."

#### Scenario: Недоступность auth service при смене пароля (502)
- **WHEN** пользователь отправляет диалог смены пароля
- **THEN** при ответе 502 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Authentication service unavailable"
- **THEN** диалог остаётся открытым

### Requirement: Автоматический переход для авторизованных пользователей

Система MUST перенаправлять пользователя на главную страницу, если он уже авторизован.

#### Scenario: Авторизованный пользователь открывает страницу входа
- **WHEN** пользователь открывает `/auth/login` и в localStorage присутствует токен под ключом `auth_token`
- **THEN** система перенаправляет пользователя на `/clients` без отображения формы входа

### Requirement: Поддержка локализации

Система MUST отображать все тексты форм аутентификации на выбранном языке (английский или русский).

#### Scenario: Английский язык по умолчанию
- **WHEN** пользователь открывает страницу входа без предварительного выбора языка
- **THEN** форма отображается на английском языке (label "Email", "Password", кнопка "Sign In")

#### Scenario: Русский язык
- **WHEN** пользователь открывает страницу входа и выбранный язык — русский
- **THEN** форма отображается на русском языке (label "Email", "Пароль", кнопка "Войти")
- **THEN** сообщения об ошибках отображаются на русском языке

#### Scenario: Формы регистрации и сброса пароля на русском языке
- **WHEN** пользователь открывает `/auth/register` или `/auth/reset` и выбранный язык — русский
- **THEN** подписи полей, кнопки отправки и сообщения об ошибках отображаются на русском языке
- **THEN** при выборе английского языка те же элементы отображаются на английском языке

#### Scenario: Диалог смены пароля на русском языке
- **WHEN** пользователь открывает диалог смены пароля и выбранный язык — русский
- **THEN** подписи полей, кнопки отправки и сообщения об ошибках отображаются на русском языке
- **THEN** при выборе английского языка те же элементы отображаются на английском языке

### Requirement: Регистрация создаёт учётную запись и выполняет вход

Система MUST валидировать регистрационные данные по правилам сервиса авторизации: все поля обязательны, email — только в доменах `.ru` и `.com` и короче 50 символов, имя и фамилия — только из букв и короче 30 символов, телефон — в формате `+7` или `8`, пароль — длиннее 5 символов и не длиннее 72 байт; и MUST отправлять валидные данные на `POST /api/v1/register`, при успешном ответе сохраняя выданный токен и перенаправляя пользователя на защищённый раздел.

#### Scenario: Форма регистрации содержит обязательные поля
- **WHEN** пользователь открывает страницу `/auth/register`
- **THEN** система отображает поля name, surname, email, phone и password
- **THEN** система отображает кнопку отправки регистрации

#### Scenario: Валидация данных регистрации на клиенте
- **WHEN** пользователь отправляет форму с email не в доменах `.ru` и `.com`
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с именем или фамилией, содержащими цифры
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с телефоном вне формата `+7` или `8`
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с паролем длиной не более 5 символов
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с пустым обязательным полем
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с именем или фамилией не короче 30 символов
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с email не короче 50 символов
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер
- **WHEN** пользователь отправляет форму с паролем длиннее 72 байт
- **THEN** система отображает ошибку валидации и не отправляет форму на сервер

#### Scenario: Успешная регистрация
- **WHEN** пользователь отправляет форму с валидными данными
- **THEN** система отправляет POST-запрос на `/api/v1/register` с телом `{"name": "...", "surname": "...", "email": "...", "phone": "...", "password": "..."}`
- **THEN** при ответе 201 с непустым полем `token` система сохраняет токен в `localStorage` под ключом `auth_token`
- **THEN** система перенаправляет пользователя на `/clients`

#### Scenario: Успешная регистрация без токена
- **WHEN** пользователь отправляет форму с валидными данными
- **THEN** при ответе 201 с пустым или отсутствующим полем `token` система отображает ошибку "Authentication failed: no token received"
- **THEN** токен не сохраняется
- **THEN** пользователь остаётся на странице регистрации

### Requirement: Сброс пароля сообщает, где искать новый пароль

Система MUST отправлять email на `POST /api/v1/reset` и при успешном ответе сообщать, что новый пароль записан в лог сервиса авторизации, и предупреждать, что текущий пароль перестал действовать.

#### Scenario: Успешный сброс пароля
- **WHEN** пользователь отправляет форму с email
- **THEN** система отправляет POST-запрос на `/api/v1/reset` с телом `{"email": "..."}`
- **THEN** при ответе 204 система сообщает, что новый пароль записан в лог сервиса авторизации
- **THEN** система сообщает, что текущий пароль больше не действует

#### Scenario: Сброс пароля для неизвестного email
- **WHEN** пользователь отправляет форму с email, которого нет в системе
- **THEN** система отображает тот же ответ, что и при успешном сбросе, не раскрывая, существует ли учётная запись

### Requirement: Смена пароля требует текущий пароль

Система MUST отправлять текущий и новый пароль на `POST /api/v1/change` вместе с токеном авторизации и при ответе 204 подтверждать успех.

#### Scenario: Успешная смена пароля
- **WHEN** пользователь отправляет диалог с текущим и новым паролем
- **THEN** система отправляет POST-запрос на `/api/v1/change` с телом `{"current_password": "...", "new_password": "..."}` и заголовком `Authorization: Bearer <токен>`
- **THEN** при ответе 204 система подтверждает успех и закрывает диалог

#### Scenario: Неверный текущий пароль (400)
- **WHEN** пользователь отправляет диалог с неверным текущим паролем
- **THEN** при ответе 400 система отображает сообщение из поля `message` ответа ErrorResponse
- **THEN** если поле `message` отсутствует, система отображает "Invalid current password"
- **THEN** диалог остаётся открытым

#### Scenario: Новый пароль короче 5 символов
- **WHEN** пользователь отправляет диалог с новым паролем длиной не более 5 символов
- **THEN** система отображает ошибку валидации и не отправляет запрос на сервер

### Requirement: Переходы между экранами аутентификации

Система MUST позволять переходить между экранами входа, регистрации и сброса пароля.

#### Scenario: Переход к регистрации и сбросу со страницы входа
- **WHEN** пользователь находится на странице `/auth/login`
- **THEN** система отображает ссылку на регистрацию
- **THEN** система отображает ссылку на сброс пароля
- **WHEN** пользователь переходит по ссылке на регистрацию
- **THEN** система открывает страницу `/auth/register`
- **WHEN** пользователь переходит по ссылке на сброс пароля
- **THEN** система открывает страницу `/auth/reset`

#### Scenario: Возврат к входу
- **WHEN** пользователь находится на странице `/auth/register` или `/auth/reset`
- **THEN** система отображает ссылку обратно на `/auth/login`

#### Scenario: Авторизованный пользователь открывает публичный экран аутентификации
- **WHEN** пользователь открывает `/auth/register` или `/auth/reset` и в localStorage присутствует токен под ключом `auth_token`
- **THEN** система перенаправляет пользователя на `/clients` без отображения формы
