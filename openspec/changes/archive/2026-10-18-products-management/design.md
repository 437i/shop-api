# Design

## Context

См. `proposal.md` — Why. Техническая база:

- В `frontend/src/pages/suppliers/` и `frontend/src/pages/clients/` существуют рабочие паттерны: страница со списком и состояниями, диалоги создания/удаления/подтверждения, zod-схемы, хуки мутаций с резолвером ошибок, unit- и E2E-тесты.
- `frontend/src/pages/products/ProductsListPage.tsx` — read-only список: `useQuery({ queryKey: ["products"] })`, скелетон, empty state, Alert ошибок; меню действий и кнопки операций нет.
- `frontend/src/shared/api/client.ts` предоставляет `get`, `post`, `patch`, `delete`; 204 обрабатывается, Bearer добавляется автоматически, 401 завершает сессию глобально. Для товаров этого достаточно.
- Типы `internal_product.CreateRequest`, `internal_product.DecreaseStockRequest`, `internal_product.ListResponse`, `internal_supplier.Response` уже есть в `frontend/src/shared/api/generated/schema.d.ts`.
- Компоненты shadcn/ui `dialog`, `alert-dialog`, `dropdown-menu`, `select`, `table`, `input`, `label` уже установлены.
- Реальный контракт (проверен по `api/internal/server/router.go`, `product/handler.go`, `product/dto.go`, `product/errors.go`, `product/service.go`, `product/pg_repository.go`, `category/dto.go`, `category/pg_repository.go`, `image`-триггерам миграций):
  - `GET /api/v1/products` → 200 массив `internal_product.ListResponse`; возвращает только товары с `available_stock > 0` (`pg_repository.go`: `Where(sq.Gt{availableStockCol: 0})`); 500; middleware добавляет 401/503.
  - `POST /api/v1/products` → 201 `internal_product.CreateResponse`; 400 (`invalid request body`, `empty name`, `empty price`, `invalid price`, `empty category`); 404 `supplier not found`; 500. Обязательные поля: `name` (max 255, trim), `category.name` (max 255, trim), `price` — строка по шаблону `^[1-9]\d{0,9}(\.\d{1,2})?$`, `available_stock` — целое `gt=0`, `supplier_id` — UUID.
  - `DELETE /api/v1/products/{id}` → 204; 400 `invalid product id`; 404 `product not found`; 500. FK-ссылок на `products` нет; триггеры удаляют осиротевшие `image` и `category`.
  - `PATCH /api/v1/products/{id}/stock` → 204; 400; 404; 409 `insufficient stock` (при `amount > available_stock`); 500. Тело — `{"amount": <целое gt=0>}`.
  - Категории: `GET /categories` отсутствует; `POST /products` выполняет `GetOrCreate` по точному имени (trim пробелов, совпадение с учётом регистра).
  - Операции увеличения остатка и обновления полей товара в API отсутствуют.
  - `GET /api/v1/suppliers` → 200 массив `internal_supplier.Response`; используется для выбора поставщика.

## Goals / Non-Goals

**Goals:**

- Полный пользовательский сценарий управления товаром: создание с выбором поставщика, удаление с подтверждением, уменьшение остатка с предупреждением о нулевом остатке.
- Следование реальному API-контракту без изобретения полей, статусов и преобразований.
- Переиспользование проверенных паттернов `clients-management`/`suppliers-management`; меню действий строки в списке товаров.
- Покрытие unit- и E2E-тестами, включая ошибку 409 `insufficient stock` и исчезновение товара из списка при остатке 0.
- Согласованное изменение спецификации `frontend/products-list` (меню действий строки).

**Non-Goals:**

- Изображения товаров (загрузка, замена, удаление, отображение) и детальная страница `/products/:id`.
- Фильтры, поиск, сортировка и пагинация товаров.
- Редактирование полей существующего товара (нет операции в API).
- Любые изменения Go API, БД, миграций и `schema.d.ts`.
- Извлечение общего CRUD-слоя из разделов клиентов/поставщиков (см. решение 1).
- Новые зависимости и новые тестовые инструменты.

## Decisions

### 1. Структура кода: третий раздел повторяет организацию `pages/<section>/`, общий слой не извлекается

**Решение:** новые модули в `frontend/src/pages/products/`:
`ProductsListPage.tsx` (расширяется), `CreateProductDialog.tsx`, `DeleteProductDialog.tsx`, `DecreaseStockDialog.tsx`, `productFormSchema.ts`, `useProductMutations.ts`.

**Альтернативы:**
- Извлечь общий CRUD-слой (`shared/`) теперь, когда появился третий однотипный раздел — отклонено: потребовало бы переписать резолверы и тесты двух рабочих разделов, резко расширив scope изменения, что противоречит AGENTS.md («избегать несвязанных правок и широкого рефакторинга»). Дублирование ограничено небольшими стабильными фрагментами (фабрика строковых полей, форма резолвера).
- Использовать пустой каркас `features/product-create`, `features/product-stock` — отклонено: фактические реализации всех существующих разделов лежат в `pages/`, каркас не используется; смена конвенции в одном разделе создала бы несогласованность.

**Обоснование:** соответствует конвенции проекта, минимизирует риск для существующего кода. Отложенное решение об извлечении общего слоя сохраняется; триггер для пересмотра — планируемая правка клиентов/поставщиков или четвёртый однотипный раздел.

### 2. Категория: свободный текст без подсказок

**Решение:** обязательное текстовое поле Category (max 255), значение уходит в `category.name` без преобразования. Подсказки/выпадающий справочник не добавляются.

**Альтернативы:**
- Подсказки из категорий загруженного списка товаров — отклонено: `GET /products` возвращает только товары в наличии, это неполный источник и он вводил бы в заблуждение.
- Отдельный запрос категорий — отклонено: `GET /categories` в API отсутствует; изобретать его нельзя.

**Обоснование:** `GetOrCreate` — единственный поддержанный контрактом путь. Побочный эффект (два похожих имени с разным регистром создают разные категории) — поведение backend; UI не маскирует его и показывает серверные сообщения об ошибках.

### 3. Числовые поля: строки в форме, явная конвертация на границе мутации

**Решение:**
- Price — текстовое поле (`inputMode="decimal"`), схема повторяет backend-шаблон `^[1-9]\d{0,9}(\.\d{1,2})?$`; значение отправляется строкой без изменений.
- Available Stock и amount уменьшения — текстовые поля (`inputMode="numeric"`), схема требует `^[1-9]\d*$` (положительное целое без ведущих нулей), конвертация `Number(value)` выполняется в хуке мутации при формировании JSON-числа.

**Альтернативы:**
- `z.coerce.number()` — отклонено: скрывает место преобразования и расходится с конвенцией схем (строки + superRefine + i18n-ключи).
- Разрешить ведущие нули (`^\d+$`) и молча нормализовать — отклонено: это незаметное преобразование пользовательского ввода; ввод `007` отклоняется сообщением валидации.

**Обоснование:** контракт ожидает строку для `price` и целое для `available_stock`/`amount`; конвертация локализована в одном месте и фиксируется тестами (точное тело запроса).

### 4. Выбор поставщика: общий кеш с разделом поставщиков

**Решение:** форма создания товара выполняет `useQuery` с ключом `SUPPLIERS_QUERY_KEY`, импортируемым из `frontend/src/pages/suppliers/useSupplierMutations.ts` (существующий экспорт). Опции shadcn `Select`: label — `name`, value — `id`. Состояния: загрузка — select и отправка disabled; ошибка — локализованное сообщение, отправка disabled; пустой список — локализованное сообщение «сначала создайте поставщика», отправка disabled.

**Альтернативы:**
- Локальная константа `["suppliers"]` — отклонено: дублирование строкового ключа кеша без источника истины.
- Отдельный запрос под своим ключом — отклонено: дублирующий сетевой запрос и второй кеш тех же данных.

**Обоснование:** импортируется только контракт кеша (query key), а не логика раздела; TanStack Query переиспользует свежие данные (staleTime 5 минут) и не делает лишний запрос.

### 5. Политика ошибок мутаций: локальный резолвер с параметром fallback для 404

**Решение:** `resolveProductMutationError(error, translate, notFoundKey?)`: NetworkError → `errors.network`; 400 → `message` или `errors.invalidRequest`; 404 → `message` или ключ `notFoundKey` (по умолчанию `errors.productNotFound`; форма создания передаёт `errors.supplierNotFound`); 409 → `message` или `errors.insufficientStock`; остальное → `message` или `errors.server`; 401 → null (глобальный обработчик).

**Альтернативы:**
- Один жёстко заданный fallback 404 — отклонено: для создания 404 означает «поставщик не найден», для удаления и остатка — «товар не найден».
- Отдельный резолвер на каждую мутацию — отклонено: лишнее дублирование при общем правиле.

**Обоснование:** одно поведение с точным fallback для каждого сценария; серверные сообщения (включая англоязычные `supplier not found`, `product not found`, `insufficient stock`) отображаются как есть — та же политика, что в предыдущих разделах.

### 6. Диалоги

**Решение:**
- Создание: контролируемый `Dialog` из состояния страницы, react-hook-form + zod; при 201 — закрытие и сброс формы и мутации; во время запроса кнопки disabled.
- Удаление: `AlertDialog` с именем товара; кнопки disabled во время запроса; ошибка отображается внутри диалога; доступное имя действия содержит имя товара.
- Уменьшение остатка: `Dialog` с именем товара и текущим `available_stock` из выбранной строки списка (без дополнительного запроса); поле amount; при 204 — закрытие и сброс.

**Обоснование:** проверенные паттерны `clients-management`/`suppliers-management`; контракт `GET /products/{id}` для предзаполнения не требуется.

### 7. Нулевой остаток: предупреждение вместо блокировки

**Решение:** когда введённая сумма равна текущему `available_stock`, диалог уменьшения остатка показывает локализованное предупреждение: товар исчезнет из списка после обнуления остатка, так как `GET /products` возвращает только товары в наличии, а операции пополнения в API нет. Отправка не блокируется. Клиентская валидация: `^[1-9]\d*$` и сумма не больше текущего остатка; серверный 409 остаётся страховкой от устаревших данных (гонка), его сообщение отображается как есть.

**Альтернативы:**
- Заблокировать уменьшение до нуля — отклонено: API допускает операцию, блокировка была бы изобретённым ограничением.
- Показывать предупреждение после успеха — отклонено: тостов успеха в проекте нет (отложены), а диалог закрывается; предупреждение до отправки детерминировано и тестируемо.

**Обоснование:** администратор принимает решение осознанно, поведение остаётся в рамках контракта.

### 8. Данные и кеш

**Решение:** `PRODUCTS_QUERY_KEY = ["products"]` экспортируется из `useProductMutations.ts`; `ProductsListPage` переключается на константу. Мутации инвалидируют `["products"]` только в `onSuccess` (201/204). Конфигурация QueryClient не меняется.

**Альтернативы:** оптимистичные обновления — отклонено: конвенция проекта (только инвалидация), вне scope.

### 9. Меню действий строки

**Решение:** `dropdown-menu` в последней колонке (паттерн клиентов/поставщиков) с пунктами «Decrease stock» и «Delete». Пункт «Edit» не добавляется: обновления полей товара в API нет. Спецификация `frontend/products-list` изменяется: требование таблицы дополняется меню действий.

### 10. Локализация

**Решение:** новые ключи в оба локаля: `products.actions.*` (addProduct, menuLabel, decreaseStock, delete, deleteNamed), `products.create.*` (title, nameLabel, categoryLabel, priceLabel, stockLabel, supplierLabel, supplierPlaceholder, suppliersLoading, suppliersEmpty, suppliersError, submit, submitting, cancel), `products.decreaseStock.*` (title, description, amountLabel, zeroWarning, submit, submitting, cancel), `products.delete.*` (title, description, confirm, deleting, cancel), `products.validation.*` (обязательность, длины, форматы price/stock/amount, supplierRequired, amountTooLarge), `errors.productNotFound`, `errors.insufficientStock`. RU-тексты по образцу разделов клиентов/поставщиков. Серверные сообщения отображаются как есть.

### 11. Тестирование

**Решение:**
- Unit: `products-management-schema.test.ts` (price: границы шаблона — `0.5`, `007`, `10.123`, 10/11 цифр целой части, 2/3 знака после точки; stock и amount: ноль, отрицательное, дробное, ведущие нули, граница «равно остатку»/«больше остатка»; supplierRequired); `products-management.test.tsx` (создание: точное тело POST с string price и integer available_stock, состояния поставщиков — загрузка/ошибка/пусто, успех, 400/404/500/503/сеть, сохранение ввода, disabled; удаление: отмена, успех, 404, disabled; уменьшение остатка: предзаполнение, точное тело PATCH, предупреждение при сумме, равной остатку, успех, 409, отмена); обновление `products-list-page.test.tsx` (наличие меню действий в строках).
- E2E: расширение `e2e/helpers.ts` перехватами `GET/POST /api/v1/products`, `PATCH /api/v1/products/{id}/stock`, `DELETE /api/v1/products/{id}` и `GET /api/v1/suppliers` (фикстура для select); новый `e2e/products-management.spec.ts`: создание товара появляется в списке; удаление только после подтверждения; уменьшение остатка обновляет строку; уменьшение до нуля — предупреждение видно, строка исчезает; ошибка 409 отображается.
- Ручная проверка на реальном стеке (Go API с dev-mock auth + PostgreSQL + Vite, без перехвата): поставщик → создание товара → уменьшение остатка → предупреждение при обнулении → проверка через `GET /products/{id}` (список товар скрывает) → удаление; повторное создание с той же категорией подтверждает `GetOrCreate`; очистка данных.


> **Уточнение (2026-10-21).** Описанное выше — состояние на момент архивации: стенд использовал dev-mock auth, реальная аутентификация была недоступна. С тех пор `docker-compose` поднимает Java auth service (`auth`, `auth-postgres`), `cmd/api` запускает `app.Module` с реальным gRPC-клиентом, а dev-mock приведён в соответствие и остаётся опциональной альтернативой; поэтому приведённые выше утверждения о недоступности реального auth service, об актуальности `frontend/README.md` и о работе раздела только при dev-mock auth не описывают текущий стенд — см. `frontend/README.md`, раздел «Local authentication».

## Risks / Trade-offs

- **[Риск] Товар с остатком 0 исчезает из списка и не может быть возвращён (нет операции пополнения)** → митигация: предупреждение до отправки; сценарий зафиксирован спецификацией и ручной проверкой; ограничение контракта задокументировано в proposal.
- **[Риск] Форма создания зависит от загрузки поставщиков** → митигация: явные состояния (загрузка/ошибка/пусто) с блокировкой отправки и понятными сообщениями.
- **[Trade-off] Категории с разным регистром создают разные записи** → поведение backend (`GetOrCreate`, точное совпадение); UI не скрывает его — серверные сообщения и результат видны пользователю.
- **[Trade-off] Третье осознанное дублирование CRUD-паттернов** → отложенное решение об извлечении общего слоя сохраняется; пересмотр при правке клиентов/поставщиков или четвёртом разделе.
- **[Риск] Существующие тесты списка товаров не ожидают меню действий и новую кнопку** → митигация: обновление `products-list-page.test.tsx` в рамках изменения; поведение списка (запрос, skeleton, empty, ошибки, кеш) не меняется.
- **[Trade-off] Очень большие значения в числовых полях** → `Number()` и серверный binding `int`; экзотические переполнения отклоняются сервером с 400 `invalid request body`, клиентская валидация покрывает практический диапазон.
- **[Информация] `price` отображается и принимается строкой без валюты** → существующая политика списка, вне scope.

## Migration Plan

Не применимо: изменений API, БД и контракта нет. Развёртывание — обычный `npm run build`; rollback — откат коммита изменения. Данные не мигрируются.

## Open Questions

Нет блокирующих. Отложено (вне scope): извлечение общего CRUD-слоя — пересмотр при планируемой правке разделов клиентов/поставщиков или появлении четвёртого однотипного раздела; изображения товаров и детальная страница — отдельные будущие изменения.
