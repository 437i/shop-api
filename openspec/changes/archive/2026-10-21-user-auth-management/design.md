# Design

## Context

См. `proposal.md` — Why.

Факты, определяющие подход:

- `api/internal/auth/handler.go:12` — интерфейс `Service`: `Register`, `Login`, `ResetPassword`, `ChangePassword(ctx, ChangeRequest, token string) error`. `ResetPassword` не принимает токен, `ChangePassword` — принимает.
- `api/internal/auth/dto.go` — тела запросов: `RegisterRequest{name, surname, email, phone, password}`, `ResetRequest{email}`, `ChangeRequest{current_password, new_password}`. Ответ `Response{token}`; `Register` — 201, `Reset` и `Change` — 204 без тела.
- `api/internal/auth/errors.go` — `MapErrToHTTP`: `ErrAlreadyExists` → 409 «user already exists», `ErrInvalidData` → 400 «invalid data», `ErrWrongPassword` → 400 «invalid current password», `ErrUnauthenticated` → 401, `ErrUnavailable` → 503, `ErrServiceError` → 502.
- `api/internal/auth/grpc_client.go:124` — `ResetPassword` глушит `ErrNotFound` и возвращает `nil`, поэтому и для неизвестного email ответ 204: отличить существующую учётную запись от несуществующей через API нельзя.
- `service_auth/.../GrpcServiceAuthImpl.java:27-29,58-75` — правила валидации на сервере: все поля обязательны, `EMAIL_REGEX = ^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.(ru|com)$` и длина < 50, `NAME_REGEX = ^[А-Яа-яЁёA-Za-z]+$` и длина < 30 для имени и фамилии, `PHONE_REGEX = ^(\+7|8)-?\d{3}-?\d{3}-?\d{2}-?\d{2}$`, длина пароля > 5 и ≤ 72 байта.
- `service_auth/.../PasswordResetService.java:37,40` — сброс пароля пишет новый пароль в лог, письмо не отправляется.
- `api/docs/swagger.yaml:370` и `:72` — контракт содержит путь `/change` и схему `internal_auth.ChangeRequest`, но в `frontend/openapi/openapi.yaml` и `frontend/src/shared/api/generated/schema.d.ts` их нет: swagger обновлялся, типы — нет. Остальные 14 путей в трёх файлах совпадают.
- `frontend/src/pages/auth/LoginPage.tsx` — образец: `useMutation` внутри компонента, `zodResolver(loginSchema)`, `resolveLoginError` для 400/502/сети, `MissingTokenError` при пустом токене, токен в `localStorage` под `auth_token`, переход на `/clients`.
- `frontend/src/pages/auth/loginSchema.ts` — `loginSchema` проверяет `z.email()`, то есть любой домен; для регистрации его использовать нельзя.
- `frontend/src/app/AdminLayout.tsx:89-107` — в футере боковой панели живут переключатель языка и выход; это единственное место, доступное авторизованному пользователю без навигации по разделам.
- `api/internal/auth/mock_grpc_client.go` — dev-мок обслуживает все четыре auth-эндпоинта и принимает любые credentials.

## Goals / Non-Goals

**Goals:**
- Три недостающих auth-сценария доступны из интерфейса и описаны требованиями, а не только кодом.
- Ошибки API на новых формах различаются по статусу и показывают текст сервера, а не общий «что-то пошло не так».
- Клиентская валидация совпадает с серверной, чтобы пользователь не отправлял заведомо отклоняемую форму.

**Non-Goals:**
- Продление сессии, refresh-токен, выход по смене пароля — контракт не предусматривает.
- Отображение «кто я»: `GET /api/v1/me` в API нет, а имя пользователя доступно только из декодированного без проверки подписи JWT — интерфейс не строит на нём никаких решений.
- Политика учётных записей: ограничение числа администраторов, приглашения, роли — контракт их не выражает.
- Изменения Go API, Java-сервиса и схемы БД.

## Decisions

### 1. Регистрация — отдельная страница `/auth/register` с собственной схемой валидации

**Решение.** Новая публичная страница рядом с существующей `/auth/login`, со своим `registerSchema`, повторяющим правила Java: все поля обязательны, домен email только `.ru` или `.com` и короче 50 символов, имя и фамилия — только буквы и короче 30 символов, телефон в формате `+7`/`8`, пароль длиннее 5 символов и не длиннее 72 байт.

**Обоснование.** `loginSchema` проверяет `z.email()` и потому принимает `user@gmail.com`, тогда как сервер такой адрес отвергнет (домен не `.ru`/`.com`) — пользователь получил бы ошибку с сервера вместо подсказки в форме. Схема регистрации намеренно не переиспользует `loginSchema`, а зеркалит `GrpcServiceAuthImpl`, чтобы расхождение было в одном месте, а не размазанным по двум схемам.

**Альтернативы.**
- *Расширить `loginSchema` параметром* — сделало бы его неоднозначным: одни и те же поля email означали бы разные правила в зависимости от формы. Отклонено.
- *Не валидировать на клиенте, полагаться на 400 от сервера* — проще в коде, но пользователь отправляет форму и получает серверное сообщение вместо подсветки конкретного поля; расходится с подходом существующей формы входа, которая валидирует на клиенте. Отклонено.

### 2. Сброс пароля — отдельная страница `/auth/reset` с фиксированным ответом

**Решение.** Страница отправляет только email. При любом ответе 204 система показывает одно и то же сообщение: новый пароль записан в лог сервиса авторизации, текущий пароль больше не действует.

**Обоснование.** `grpc_client.go:124` глушит `ErrNotFound`, поэтому API отвечает 204 и для несуществующего email. Любая формулировка, различающая «сброшено» и «нет такого email», раскрыла бы наличие учётной записи. Сообщение о логе — не оговорка, а отражение контракта: `PasswordResetService.java:40` пишет пароль в stdout, письма сервис не отправляет.

**Альтернативы.**
- *«Письмо отправлено на …»* — прямо противоречит поведению сервиса и вводило бы пользователя в заблуждение. Отклонено.
- *Спросить email ещё раз, чтобы «подтвердить»* — лишний шаг, не добавляющий гарантий: сервис меняет пароль по первому же запросу. Отклонено.

### 3. Смена пароля — диалог из футера боковой панели

**Решение.** Пункт «Change password» рядом с переключателем языка и выходом открывает модальный диалог с полями текущего и нового пароля. Отдельного маршрута нет.

**Обоснование.** Действие доступно только авторизованному пользователю, и менять маршрут ради него — лишнее состояние навигации: после смены пароля пользователь остаётся в текущем разделе. Футер боковой панели — единственное место, где уже собраны пользовательские действия, не связанные с содержимым раздела.

**Альтернативы.**
- *Отдельная страница `/auth/change-password`* — потребовала бы пункта навигации для неавторизованного пользователя и обработки перехода назад. Отклонено.
- *Пункт в меню профиля* — профиля в интерфейсе нет и вводить его ради одной кнопки избыточно. Отклонено.

### 4. После успешной смены пароля сессия сохраняется

**Решение.** При ответе 204 диалог подтверждает успех и закрывается; принудительного выхода нет.

**Обоснование.** Смена пароля не отзывает выданный токен — ни Java-сервис, ни Go API этого не делают, поэтому «выйти и войти снова» не изменило бы состояние сессии, а лишь добавило бы шаг. Интерфейс не обещает, что смена пароля продлила сессию: токен остаётся действителен до истечения (24 часа).

### 5. Типы API перегенерируются из контракта, а не дописываются

**Решение.** Выполняется существующий скрипт `npm run api:types`: `swagger2openapi` пересобирает `frontend/openapi/openapi.yaml` из `api/docs/swagger.yaml`, затем `openapi-typescript` пересобирает `frontend/src/shared/api/generated/schema.d.ts`. Тип тела запроса смены пароля берётся из `components["schemas"]["internal_auth.ChangeRequest"]`.

**Обоснование.** `internal_auth.ChangeRequest` есть в контракте, но отсутствует в сгенерированных типах — без перегенерации тело запроса не типизировано. Правила проекта прямо запрещают правку сгенерированных файлов и требуют перегенерации из контракта.

**Альтернативы.**
- *Описать тело запроса вручную в коде* — дублирование контракта, расходящееся при каждом изменении swagger. Отклонено.

**Ожидаемый диф регенерации:** путь `/change` и определение `internal_auth.ChangeRequest` в обоих файлах. Остальные 14 путей в трёх файлах уже совпадают. Если диф окажется шире, значит контракт и типы расходились и до этого изменения — это отдельная находка, которую нужно разобрать до продолжения.

### 6. Мутации живут в общем `useAuthMutations`, разбор ошибок — в одном месте

**Решение.** В `frontend/src/pages/auth/useAuthMutations.ts` собираются три хука: `useRegister`, `useResetPassword`, `useChangePassword`. Разбор ошибок по статусу (400 / 409 / 502 / сеть) вынесен в общий резолвер рядом с ними, а не дублируется в трёх компонентах.

**Обоснование.** В разделах клиентов, товаров и поставщиков принят единый конвенционный слой `use*Mutations` рядом со страницей. Копирование одного и того же разбора ошибок в три новых компонента дало бы те самые дубли, которые уже пришлось выносить при рефакторинге. `LoginPage` держит мутацию внутри компонента, потому что она одна; здесь их три, и общий слой окупается.

### 7. После регистрации пользователь сразу авторизуется

**Решение.** Ответ 201 содержит токен — он сохраняется в `localStorage` под `auth_token`, пользователь перенаправляется на `/clients`. Пустой или отсутствующий токен трактуется как ошибка, токен не сохраняется, пользователь остаётся на странице регистрации.

**Обоснование.** Тот же путь, что и при входе (`LoginPage.tsx:77-80`): успешная регистрация без отдельного шага входа. Отдельный сценарий «зарегистрировался — теперь войди» создал бы вторую точку, где токен можно потерять.

## Risks / Trade-offs

- **[Risk] Мок принимает любые credentials, поэтому e2e против мока не может проверить ни валидацию логина, ни занятость email** → регистрация с занятым email проверяется перехватом маршрута с ответом 409, а не моком; проверка реальной аутентификации выполняется против живого стенда.
- **[Risk] Правила валидации продублированы на клиенте и могут разойтись с Java-сервисом** → источник правды остаётся сервер: при расхождении пользователь получит 400 с текстом сервера, и клиентская подсказка будет уточнением, а не заменой. Правила в дизайне ссылаются на конкретные константы `GrpcServiceAuthImpl`, чтобы правка сервира была видна при следующем изменении.
- **[Risk] Регистрация создаёт полноценного пользователя Java-сервиса** → в среде с несколькими администраторами форма регистрации становится открытым входом. Ограничивать её нечем: в контракте нет ни приглашений, ни ролей. Для учебного стенда приемлемо; решение о закрытии регистрации принимается уровнем развёртывания, а не интерфейса.
- **[Risk] `npm run api:types` перегенерирует оба файла целиком** → ожидаемый диф ограничен путём `/change` и схемой `internal_auth.ChangeRequest`; более широкий диф означает прежнее расхождение контракта и типов, которое нужно разобрать отдельно.
- **[Trade-off] Смена пароля не меняет состояние сессии** → пользователь может продолжить работу со старым токеном до его истечения; это свойство сервиса, а не выбор интерфейса, и оно зафиксировано в требованиях.

## Migration Plan

Не применимо — миграции данных, новых маршрутов и зависимостей нет. Развёртывание обычное (`npm run build`). **Откат:** revert изменений `frontend/src/pages/auth/`, `frontend/src/app/router.tsx`, `frontend/src/app/AdminLayout.tsx`, `frontend/openapi/`, `frontend/src/shared/api/generated/`.
