# Proposal

## Why

Административная панель умеет только вход. У администратора нет способа завести учётную запись, сменить пароль или восстановить его после смены в другом месте: смена пароля вне панели навсегда закрывает доступ, а восстановление возможно только вручную — через лог Java-сервиса авторизации. Три из четырёх auth-эндпоинтов Go API (`POST /api/v1/register`, `POST /api/v1/reset`, `POST /api/v1/change`) не задействованы вообще.

## What Changes

- **Регистрация.** Новая публичная страница `/auth/register` отправляет `POST /api/v1/register` с полями `name`, `surname`, `email`, `phone`, `password`. При ответе 201 с токеном пользователь сразу авторизуется: токен сохраняется в `localStorage` под ключом `auth_token`, пользователь попадает на `/clients`. Ответ 409 (`user already exists`) показывается как «email уже занят», ответ 400 — текстом сервера.
- **Сброс пароля.** Новая публичная страница `/auth/reset` отправляет `POST /api/v1/reset` с полем `email`. При ответе 204 система сообщает, что новый пароль записан в лог сервиса авторизации, и предупреждает, что текущий пароль перестал действовать сразу. Причина в контракте: Java-сервис не отправляет письмо, а пишет новый пароль в лог (`PasswordResetService.java:37,40`).
- **Смена пароля.** Новое действие в футере боковой панели открывает диалог `POST /api/v1/change` с полями `current_password` и `new_password`. При ответе 204 система подтверждает успех; ответ 400 (`invalid current password`) показывается в диалоге.
- **Навигация между экранами аутентификации.** Страница входа получает ссылки на регистрацию и сброс пароля; страницы регистрации и сброса — ссылку обратно на вход.
- **Регенерация типов API.** `internal_auth.ChangeRequest` присутствует в `api/docs/swagger.yaml`, но отсутствует в сгенерированных типах фронтенда, поэтому для смены пароля тип тела запроса недоступен. Типы перегенерируются скриптом `npm run api:types` из исходного контракта.
- **Клиентская валидация** новых форм зеркалит правила Java-сервиса: все поля обязательны, email только с доменом `.ru` или `.com` и короче 50 символов, имя и фамилия — только буквы и короче 30 символов, телефон в формате `+7`/`8`, пароль длиннее 5 символов и не длиннее 72 байт.

Изменение **не является BREAKING**: HTTP-контракт, Go API и Java-сервис не затрагиваются; новая capability не создаётся — расширяется существующая `frontend/user-authentication`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `frontend/user-authentication`: добавляются требования регистрации, сброса пароля, смены пароля и переходов между экранами аутентификации; расширяются требования об отображении ошибок API и о поддержке локализации — на новые формы.

## Impact

**Код фронтенда:**
- `frontend/src/pages/auth/` — новые страницы `RegisterPage.tsx`, `ResetPasswordPage.tsx` и схемы валидации `registerSchema.ts`, `resetPasswordSchema.ts`, `changePasswordSchema.ts`.
- `frontend/src/pages/auth/ChangePasswordDialog.tsx` — диалог смены пароля.
- `frontend/src/app/router.tsx` — маршруты `/auth/register` и `/auth/reset`.
- `frontend/src/app/AdminLayout.tsx` — пункт «Change password» в футере боковой панели.
- `frontend/src/shared/api/generated/schema.d.ts`, `frontend/openapi/openapi.yaml` — регенерация из контракта.

**Используемые API-эндпоинты** (контракт не меняется):
- `POST /api/v1/register` — регистрация, 201 с телом `{"token": "..."}`.
- `POST /api/v1/reset` — сброс пароля, 204 без тела.
- `POST /api/v1/change` — смена пароля, 204 без тела, требует Bearer-токен.

**Зависимости:** новых нет. `swagger2openapi` и `openapi-typescript` уже установлены — используется существующий скрипт `npm run api:types`.

**Не затрагивается:** Go API, Java-сервис авторизации, схема БД, основные спецификации других capability, код бэкенда.

**Незавершённые вопросы контракта и аутентификации:**
- Refresh-токена в контракте нет, поэтому смена пароля не продлевает сессию: текущий токен остаётся действительным до истечения (24 часа), а новый пароль на уже выданный токен не влияет. Интерфейс не выдаёт обещаний о продлении сессии.
- `GET /api/v1/me` в контракте отсутствует, поэтому «кто я» нельзя получить из API. Идентификатор пользователя доступен только из декодирования JWT, которое браузер не проверяет подписью, — интерфейс его не использует: отображение «кто я» в объём изменения не входит, и никаких решений об авторизации на декодированном токене не принимается.
- Сброс пароля на живом стенде меняет пароль в базе Java-сервиса немедленно, без письма пользователю. Формулировка «новый пароль записан в лог auth-сервиса» — сознательное отражение контракта, а не недоработка интерфейса.
- Регистрация на живом стенде создаёт полноценного пользователя Java-сервиса. Для учебного стенда это ожидаемо, но в среде с несколькими администраторами самостоятельная регистрация означает возможность появления лишних учётных записей.
