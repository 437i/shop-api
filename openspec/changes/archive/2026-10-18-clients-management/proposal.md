# Proposal

## Why

Административная панель сейчас работает только на чтение: единственный рабочий сценарий — просмотр списка клиентов. Администратор не может создать клиента, удалить его или изменить его адрес, хотя backend-операции для этого существуют в Go API. Реализация этих операций даёт первый сценарий записи в панели и задаёт паттерны мутаций (форма, подтверждение, инвалидация кеша, обработка ошибок) для последующих разделов.

## What Changes

- Кнопка «Add client» и диалог создания клиента с формой: имя, фамилия, дата рождения, пол, адрес (страна, город, улица).
- Клиентская валидация формы, соответствующая backend: обязательные поля и лимиты длины, корректная календарная дата, дата не в будущем, возраст от 16 до 100 лет включительно по календарной дате UTC, значения пола из контракта (`m`, `f`, `n/a`).
- Интеграция с `POST /api/v1/clients`: при 201 диалог закрывается, кеш списка `["clients"]` инвалидируется, новый клиент появляется в списке.
- Удаление клиента из строки списка с подтверждением: интеграция с `DELETE /api/v1/clients/{id}`, состояние выполнения запроса, обновление списка только после успеха.
- Изменение адреса клиента из строки списка: диалог предзаполняется данными `address` из уже загруженного `ClientResponse` (без GET by ID), интеграция с `PATCH /api/v1/clients/{id}/address` с телом только `{address: {country, city, street}}`.
- Единая политика ошибок мутаций: 400/404/500/503 и сетевые ошибки отображаются понятным сообщением (`message` из ErrorResponse или локализованный fallback), ввод пользователя не теряется; 401 обрабатывается существующим глобальным сбросом сессии.
- Ключи локализации EN/RU для всех новых текстов интерфейса.
- Unit-тесты (Vitest + Testing Library) для схемы валидации, диалогов, мутаций и инвалидации кеша; E2E-тесты (Playwright, `page.route()`) для создания, ошибки 400, удаления с подтверждением и изменения адреса.

## Capabilities

### New Capabilities

- `frontend/clients-management`: управление клиентами из административной панели — создание клиента с валидацией, удаление с подтверждением, изменение адреса из строки списка, обработка ошибок мутаций и инвалидация кеша списка клиентов.

## Impact

**Затронутый код:**
- `frontend/src/shared/api/client.ts` — добавление методов `patch` и `delete` в существующий клиент (204 No Content уже обрабатывается).
- `frontend/src/pages/clients/` — новые диалоги создания/удаления/изменения адреса, zod-схема формы, хуки мутаций; изменения в `ClientsListPage.tsx` (кнопка создания, действия в строках).
- `frontend/src/shared/i18n/locales/en/common.json`, `frontend/src/shared/i18n/locales/ru/common.json` — новые ключи.
- `frontend/src/test/` — новые unit-тесты; `frontend/e2e/` — расширение `helpers.ts` и новый spec.

**API endpoints:**
- `POST /api/v1/clients` (`internal_client.CreateRequest` → 201 `internal_client.Response`, статусы 400/500, требует Bearer-авторизацию)
- `DELETE /api/v1/clients/{id}` (uuid path → 204, статусы 400/404/500, требует Bearer-авторизацию)
- `PATCH /api/v1/clients/{id}/address` (`internal_client.UpdateAddressRequest` → 204, статусы 400/404/500, требует Bearer-авторизацию)
- `GET /api/v1/clients` — существующий запрос списка, инвалидируется после успешных мутаций
- Ответы middleware: 401 (сброс сессии) и 503 (сообщение об ошибке) — существующая обработка без изменений

**Ограничения контракта:**
- `GET /api/v1/clients/{id}` отсутствует — изменение адреса использует данные строки списка, отдельный запрос за клиентом не планируется.
- Возрастные ограничения возвращает backend как HTTP 400 с англоязычным `message` (`validate bday: client can't be younger than 16 years`, `validate bday: client can't be older than 100 years`, `validate bday: time travellers not welcome`); frontend зеркалит правила на клиенте и отображает серверное сообщение как есть.
- Backend-проверка возраста содержала дефект (отклоняла клиентов с возрастом ровно 100); дефект исправлен в изменении `client-age-validation` — изменение заархивировано, основная спецификация `backend/clients-management` создана; frontend-валидация и спецификация согласуются с этой же UTC-политикой в задачах группы 8.
- Успешные `DELETE` и `PATCH` возвращают 204 без тела.

**Зависимости:**
- Только существующие пакеты: react-hook-form, zod, TanStack Query, shadcn/ui (`dialog`, `alert-dialog`, `select`, `dropdown-menu`), i18next, Vitest, Playwright.
- Регенерация API-типов не требуется — контракт не меняется.
- Координация: backend-исправление `client-age-validation` (16–100 включительно по календарной дате UTC) реализовано и проверено; см. tasks → Workflow follow-up.

**Системы:**
- Go HTTP API — источник истины; backend, БД, маршруты и контракты не изменяются.
- Локальная проверка — против существующего стека с dev-mock auth-модулем Go API (реальная аутентификация недоступна до подключения Java auth service; ограничение уже задокументировано в `frontend/README.md`).


> **Уточнение (2026-10-21).** Описанное выше — состояние на момент архивации: стенд использовал dev-mock auth, реальная аутентификация была недоступна. С тех пор `docker-compose` поднимает Java auth service (`auth`, `auth-postgres`), `cmd/api` запускает `app.Module` с реальным gRPC-клиентом, а dev-mock приведён в соответствие и остаётся опциональной альтернативой; поэтому приведённые выше утверждения о недоступности реального auth service, об актуальности `frontend/README.md` и о работе раздела только при dev-mock auth не описывают текущий стенд — см. `frontend/README.md`, раздел «Local authentication».

**Незавершённые вопросы:**
- Нет блокирующих. Принятые решения: опорная календарная дата для возрастной валидации — календарная дата UTC (единая политика frontend и backend; backend приведён к ней в `client-age-validation`); диалоги размещаются на странице списка клиентов (отдельные маршруты не вводятся из-за отсутствия `GET /clients/{id}`); в API отправляются сырые значения пола (`m`/`f`/`n/a`), локализуются только подписи; отдельные toast-уведомления об успехе не добавляются — обратная связь это закрытие диалога и обновлённый список.
