# Design

## Context

См. `proposal.md` — Why. Техническая база:

- В `frontend/src/pages/clients/` уже существуют рабочие паттерны: страница со списком и состояниями, диалоги создания/удаления/адреса, zod-схема, хуки мутаций с резолвером ошибок, unit- и E2E-тесты.
- `frontend/src/shared/api/client.ts` предоставляет `get`, `post`, `patch`, `delete`; 204 обрабатывается, Bearer добавляется автоматически, 401 завершает сессию глобально. Для поставщиков этого достаточно.
- Типы `internal_supplier.CreateRequest`, `internal_supplier.Response`, `internal_supplier.UpdateAddressRequest` уже есть в `frontend/src/shared/api/generated/schema.d.ts`.
- `AdminLayout.tsx` содержит пункт «Suppliers» как disabled, а активность «Clients» задана жёстко (`isActive` без привязки к маршруту).
- Реальный контракт (проверен по `api/internal/server/router.go`, `supplier/handler.go`, `supplier/dto.go`, `supplier/service.go`, `supplier/pg_repository.go`, `supplier/errors.go`, `address/dto.go`):
  - `GET /api/v1/suppliers` → 200 массив `internal_supplier.Response`; 500; middleware добавляет 401/503.
  - `POST /api/v1/suppliers` → 201 `internal_supplier.Response`; 400; 500.
  - `DELETE /api/v1/suppliers/{id}` → 204; FK-нарушение `products.supplier_id` → 400 `supplier is used by products`; 404 `supplier not found`; 500.
  - `PATCH /api/v1/suppliers/{id}/address` → 204; 400; 404; 500.
  - Телефон: backend сначала нормализует значение (`normalizePhone`: удаляются все символы, кроме цифр и ведущего `+`), затем проверяет шаблоном `^\+[1-9]\d{7,14}$`.
  - Адрес: `country`, `city`, `street` — обязательные, максимум 255; backend выполняет trim перед проверкой; адреса дедуплицируются `GetOrCreate` по уникальной комбинации country/city/street.

## Goals / Non-Goals

**Goals:**

- Полный пользовательский сценарий раздела «Поставщики»: список, создание, удаление с подтверждением, изменение адреса.
- Следование реальному API-контракту без изобретения полей, статусов и преобразований.
- Переиспользование проверенных паттернов `clients-management` без механического копирования и без преждевременных абстракций.
- Активация навигации с согласованным изменением спецификации `frontend/protected-navigation`.
- Покрытие unit- и E2E-тестами, включая ошибку «поставщик используется товарами».

**Non-Goals:**

- Редактирование имени и телефона существующего поставщика (нет операции в API).
- Пагинация, фильтры и детальная страница поставщика.
- Управление товарами и изображениями.
- Любые изменения Go API, БД, миграций и `schema.d.ts`.
- Новые зависимости, новые тестовые инструменты, рефакторинг раздела клиентов.

## Decisions

### 1. Структура кода: копируем организацию `pages/clients/`, не выносим общий CRUD-слой

**Решение:** новые файлы в `frontend/src/pages/suppliers/`:
`SuppliersListPage.tsx`, `CreateSupplierDialog.tsx`, `DeleteSupplierDialog.tsx`, `EditSupplierAddressDialog.tsx`, `supplierFormSchema.ts`, `useSupplierMutations.ts`.

**Альтернативы:**
- Универсальный `CrudPage`/`useCrudMutations` в `shared/` — отклонено: два потребителя (clients, suppliers) ещё не оправдывают обобщение, формы заметно различаются (поля, валидация, API-методы), риск регрессии в рабочем разделе клиентов.
- Копирование `DeleteClientDialog` через проп-параметризацию — отклонено по той же причине.

**Обоснование:** соответствует конвенции проекта (`pages/<section>/`), минимизирует риск для существующего кода. Триггер для извлечения общего слоя — третий однотипный раздел или плановая правка клиентов.

### 2. Политика ошибок: локальный резолвер поставщиков

**Решение:** `resolveSupplierMutationError(error, translate)` в `useSupplierMutations.ts` повторяет политику `resolveClientMutationError` (NetworkError → `errors.network`; 400 → `message` или `errors.invalidRequest`; 404 → `message` или `errors.supplierNotFound`; остальное → `message` или `errors.server`; 401 → null, глобальный обработчик).

**Альтернативы:**
- Вынести общий резолвер в `shared/` и перевести на него клиентов — отклонено: изменение рабочего кода вне scope, различие только в ключе fallback для 404.
- Импортировать `resolveClientMutationError` в раздел поставщиков — отклонено: кросс-разделённая зависимость и вводящее в заблуждение имя.

**Обоснование:** conscious duplication маленького стабильного фрагмента предпочтительнее связности разделов; логика зафиксирована тестами.

### 3. Телефон: валидация зеркалит backend, значение не преобразуется

**Решение:** в `supplierFormSchema.ts` экспортируются `normalizePhone` (точное повторение `supplier/dto.go`: сохраняется ведущий `+` на позиции 0, все остальные символы кроме цифр удаляются) и `resolvePhoneError(value)` (после нормализации обязателен шаблон `^\+[1-9]\d{7,14}$`). Схема использует эти функции, но значение формы и тело запроса остаются введёнными пользователем без изменений; нормализация и хранение — на backend.

**Альтернативы:**
- Отправить заранее нормализованное значение — отклонено: это собственное преобразование данных (пользователь явно просил не изобретать правило); неверная реализация исказила бы данные.
- Не валидировать телефон на клиенте, полагаться на 400 от backend — отклонено: требование спецификации — проверять по реальным backend-правилам до отправки.

**Обоснование:** правило не изобретено, а скопировано из проверенного кода backend; зеркало фиксируется unit-тестами на границы (8–15 цифр после `+`, отсутствие ведущего `+`, нецифровые символы).

### 4. Валидация обязательности и длины: конвенция `clientFormSchema`

**Решение:** name и поля адреса — `min(1)`/`max(255)` с i18n-ключами сообщений, как `createLimitedStringField` в `clientFormSchema.ts`. Trim не добавляем: серверный trim и серверные сообщения остаются источником истины для whitespace-only ввода.

**Альтернатива:** собственная trim-политика на клиенте — отклонено для консистентности с существующим разделом.

### 5. Данные и кеш: существующий API-клиент и TanStack Query

**Решение:** `useQuery({ queryKey: ["suppliers"], queryFn: () => apiClient.get<SupplierResponse[]>("/suppliers") })`; мутации инвалидируют `["suppliers"]` только при 201/204. Конфигурация QueryClient не меняется (staleTime 5 минут, refetchOnWindowFocus).

**Альтернативы:** отдельный query-клиент или локальное состояние — отклонено: дублирование server state запрещено конвенциями фронтенда.

### 6. Диалоги

**Решение:**
- Создание: контролируемый `Dialog` из состояния страницы, форма react-hook-form + zod; при успехе — закрытие и сброс формы; во время запроса кнопки disabled, повторная отправка заблокирована.
- Удаление: `AlertDialog`, показывает имя поставщика; кнопки disabled во время запроса; ошибка (включая 400 `supplier is used by products`) отображается внутри диалога; доступное имя действия содержит имя поставщика.
- Адрес: `Dialog`, предзаполнение через `useEffect` + `reset` из `supplier.address` выбранной строки (паттерн `EditClientAddressDialog`); PATCH-тело — ровно `{address: {country, city, street}}`.

**Обоснование:** проверенные паттерны, нулевые дополнительные запросы (контракт `GET /suppliers/{id}` не требуется).

### 7. Навигация: активность по маршруту

**Решение:** в `AdminLayout.tsx` активный пункт определяется текущим путём (`useLocation`): `/clients` → Clients, `/suppliers` → Suppliers. Пункт Suppliers становится `SidebarMenuButton` с `render={<Link to="/suppliers" />}`; Products остаётся disabled. В `router.tsx` маршрут `/suppliers` добавляется в тот же защищённый layout.

**Обоснование:** согласовано с delta-спецификацией `frontend/protected-navigation`; существующие тесты, фиксирующие Suppliers как disabled, обновляются в рамках изменения.

### 8. Локализация

**Решение:** новые ключи в оба локаля по образцу клиентских: `suppliers.columns.*`, `suppliers.empty`, `suppliers.loading`, `suppliers.actions.*`, `suppliers.create.*`, `suppliers.editAddress.*`, `suppliers.delete.*`, `suppliers.validation.*`, `errors.supplierNotFound`. RU: заголовки «Имя, Телефон, Страна, Город, Улица», empty state «Поставщики не найдены». Серверные сообщения (включая `supplier is used by products`) отображаются как есть — политика `clients-management`.

### 9. Тестирование

**Решение:**
- Unit: `suppliers-management-schema.test.ts` (обязательность, длины, телефон: нормализация, границы 8/15 цифр после `+`, без ведущего `+`, мусорные символы; ввод не изменяется), `suppliers-list-page.test.tsx` (запрос, skeleton, empty, ошибки, 401), `suppliers-management.test.tsx` (создание: точное тело POST, успех, 400 без/с сообщением, 500/503/сеть, сохранение ввода, disabled; удаление: отмена, успех, 400 `supplier is used by products`, 404, 500/503/сеть, без инвалидации при ошибке; адрес: предзаполнение, точное тело PATCH, успех, ошибки, отмена; локализация RU).
- Обновление существующих тестов, фиксирующих Suppliers как disabled: `src/test/admin-layout.test.tsx`, `src/test/routing.test.tsx`, `e2e/auth.spec.ts`.
- E2E: расширение `e2e/helpers.ts` перехватами `/api/v1/suppliers` (GET/POST), `/api/v1/suppliers/{id}` (DELETE), `/api/v1/suppliers/{id}/address` (PATCH) с флагами ошибок; новый `e2e/suppliers-management.spec.ts` (создание, ошибка 400 при in-use удалении с точным сообщением, удаление с подтверждением, изменение адреса, переход по пункту меню).
- Ручная проверка на реальном стеке (Go API с dev-mock auth + PostgreSQL + Vite, без перехвата): создание, изменение адреса, удаление; для 400 in-use — создать товар через API (`POST /api/v1/products` с `supplier_id`), попытаться удалить поставщика через UI, получить сообщение, затем удалить товар и поставщика, подтвердить очистку через `GET`.


> **Уточнение (2026-10-21).** Описанное выше — состояние на момент архивации: стенд использовал dev-mock auth, реальная аутентификация была недоступна. С тех пор `docker-compose` поднимает Java auth service (`auth`, `auth-postgres`), `cmd/api` запускает `app.Module` с реальным gRPC-клиентом, а dev-mock приведён в соответствие и остаётся опциональной альтернативой; поэтому приведённые выше утверждения о недоступности реального auth service, об актуальности `frontend/README.md` и о работе раздела только при dev-mock auth не описывают текущий стенд — см. `frontend/README.md`, раздел «Local authentication».

## Risks / Trade-offs

- **[Риск] Дрейф зеркала телефонной валидации при изменении backend** → митигация: unit-тесты фиксируют правило, серверное сообщение при 400 отображается пользователю как fallback; контракт проверен на момент проектирования.
- **[Риск] Дублирование резолвера ошибок и частей схемы с разделом клиентов** → принято осознанно; триггер для извлечения общего слоя зафиксирован (третий раздел или плановая правка клиентов).
- **[Риск] Существующие тесты, ожидающие Suppliers disabled, начнут падать** → митигация: обновление `admin-layout.test.tsx`, `routing.test.tsx`, `e2e/auth.spec.ts` включено в задачи.
- **[Trade-off] Список поставщиков загружается целиком** → API не поддерживает пагинацию; для административного масштаба приемлемо, вне scope.
- **[Trade-off] Сообщение `supplier is used by products` англоязычное** → консистентно с существующей политикой отображения серверных сообщений; локализованный fallback только при отсутствии `message`.
- **[Информация] Адреса дедуплицируются backend** (`GetOrCreate` по country/city/street): смена адреса на уже существующий переиспользует запись; UI-поведение не отличается.

## Migration Plan

Не применимо: изменений API, БД и контракта нет. Развёртывание — обычный `npm run build`; rollback — откат коммита изменения. Данные не мигрируются.

## Open Questions

Нет блокирующих. Отложенное решение: вынесение общего CRUD-слоя (резолвер ошибок, поля с лимитом длины) в `shared/` — рассматривается при появлении третьего однотипного раздела.
