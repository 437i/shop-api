# Design

## Context

Панель уже умеет показывать список товаров и управлять из строки остатком, фотографией и удалением (`frontend/products-list`, `frontend/products-management`, `frontend/product-images`). Данные карточки приходят из отдельного эндпоинта `GET /api/v1/products/{id}` → `internal_product.FullResponse`, фронтендом он не используется. Фотография товара уже имеет полный слой `frontend/src/features/product-images/` (запрос `useProductImage`, мутации, диалог `ProductImageDialog`), привязанный к списку товаров через кеш `["products"]`. Глобальные правила панели не меняются: `providers.tsx` содержит обработчик 401, маршруты `/products` защищены `ProtectedRoute`, кеш TanStack Query настроен на staleTime 5 минут.

## Goals / Non-Goals

**Goals:**
- Дать оператору страницу карточки товара со всеми полями `FullResponse` и фотографией.
- Переиспользовать существующий слой фотографии и диалог без дублирования операций `product-images`.
- Сохранить целостность кеша: мутации товара из списка и фотографии меняют то, что карточка показывает.
- Остаться в границах фронтенда: Go API, Java-сервис и БД не меняются.

**Non-Goals:**
- Операции записи на карточке (редактирование полей, пополнение остатка) — их нет в контракте.
- Живые e2e-сценарии (`frontend/e2e-live/`) — процедура остаётся без изменений.
- Общая страница поставщика `/suppliers/:id`, справочники категорий, пагинация.
- Извлечение общего резолвера ошибок в `shared/` (отложенное решение из `2026-10-18-suppliers-management/design.md`).

## Decisions

### 1. Вход в карточку — действие в меню строки, а не ссылка в названии

**Решение.** В `ProductsListPage.tsx` в меню действий строки добавляется первый пункт «Details» («Карточка»), открывающий `navigate(`/products/${id}`)`. Название товара в таблице остаётся текстом, клик по строке ничего не делает.

**Обоснование.** Все операции строки уже живут в меню строки (decrease stock, image, delete у товаров; edit address, delete у клиентов и поставщиков) — конвенция проекта. Ссылка в названии изменила бы семантику ячейки Name, заданную спецификацией `frontend/products-list` («колонка Name содержит значение поля name»), и потревожила бы тесты списка ради того же результата.

**Альтернативы.**
- *Ссылка на названии товара* — отклонено: меняет наблюдаемое поведение колонки таблицы и добавляет смешение «текст/ссылка» на одном типе ячеек.
- *Клик по строке целиком* — отклонено: строки целиком управляются меню, клик по пустой зоне строки конфликтует со всплывающим меню.

### 2. Маршрут `/products/:id` — защищённый дочерний маршрут существующего layout

**Решение.** В `router.tsx` внутри общего защищённого блока добавляется `{ path: "/products/:id", element: <ProductDetailsPage /> }`. Навигация в sidebar не меняется: карточка не раздел, а просмотровый экран раздела.

**Обоснование.** Повторяет схему трёх существующих защищённых маршрутов без их изменений. Неизвестный путь остаётся `*` → `NotFoundPage`.

**Альтернативы.** Вложенный маршрут `/products/:id` под `/products` (Outlet) — отклонено: у `ProductsListPage` нет Outlet, а переход «список → карточка» соответствует плоской структуре маршрутов, уже реализованной в панели (клиенты и поставщики — по одной странице уровня).

### 3. Данные карточки — отдельный кеш `["product", id]`, 404 как состояние данных

**Решение.** Хук `useProductDetails.ts`: `useQuery({ queryKey: ["product", id], queryFn: getProduct })`, где `getProduct` выполняет `GET /api/v1/products/{id}` и при 404 возвращает `null` (шаблон запроса фотографии в `useProductImage`). Страница рендерит три состояния: skeleton при загрузке, карточку по данным, состояние отсутствия товара при `null`. Ошибки 400/500/503/сеть — состояние ошибки с «Повторить».

**Обоснование.** 404 — легитимное состояние прямого URL (удалённый товар, нулевой остаток недостижим из списка, но достигается по id), сообщение об ошибке здесь вводит в заблуждение. Отдельный ключ изолирует карточку от инвалидации списка: мутации фотографии инвалидируют `["products"]` и `["product-image", id]`, которые с данными карточки, кроме области фотографии, не связаны.

**Альтернативы.**
- *404 как ошибка* — отклонено: состояние «товар не существует» пользовательски отличается от «запрос сломался» и должно предлагать возврат, а не повторение.
- *Кеш внутри `["products"]`* — отклонено: заставляет страницу карточки ждать полный список и смешивает обновления несовместимых форм (`ListResponse` vs `FullResponse`).

### 4. Мутации списка актуализируют карточку: `["product"]` инвалидируется вместе с `["products"]`

**Решение.** В `useDecreaseStock` и `useDeleteProduct` после успеха добавляется `invalidateQueries({ queryKey: ["product"] })` рядом с существующей инвалидацией `["products"]`. Префикс `["product"]` совпадает с кешами карточек любого товара и не совпадает ни с `["products"]`, ни с `["product-image", id]`, так что другие кеши это не задевает. Область фотографии на карточке продолжает пользоваться инвалидацией `["product-image", productId]` из хуков фичи — её добавлять не надо.

**Обоснование.** Без актуализации кеш карточки (staleTime 5 минут) показывал бы устаревший `available_stock` до пяти минут после уменьшения остатка из списка — видимый дефект, задокументированный в спецификации карточки.

**Альтернативы.** Выключить кеширование карточки — отклонено: ломает общий контракт панели (список и карточка должны вести себя одинаково) и лишает карточку защиты от лишних запросов.

### 5. Фотография: разделяемый компонент `ProductImage` + существующий запрос фото

**Решение.** В `frontend/src/features/product-images/` выделяется компонент `ProductImage` (элемент `img` + управление object URL: создание, отмена при размонтировании и замене, локализованное доступное имя, заглушка отсутствия), который используется и карточкой, и существующим `ProductImageDialog` (поведение диалога — механическая замена, тесты диалога остаются). Данные фото карточка получает существующим хуком `useProductImage(productId, true)` (диалог всегда «открыт»), мутации — через существующий диалог.

**Обоснование.** Два потребителя одной фотографии = один запросный узел кеша `["product-image", productId]`: после загрузки/замены/удаления область фотографии на карточке обновляется по той же инвалидации, что и диалог, ничего дописывать не нужно. Отрисовка object URL и отмена — уже отлаженный код диалога, выделять компонент дешевле, чем дублировать.

**Альтернативы.**
- *Независимый inline-код фото на карточке* — отклонено: дублирование и риск расхождения обработки object URL и заглушки.
- *Только кнопка «Фото» без области на карточке* — отклонено: фотография и полные данные поставщика — основной смысл карточки.

### 6. Отображение данных: текстовые блоки карточки, форматирование дат локальным хелпером

**Решение.** Карточка собирается из shadcn `Card` (заголовок — название товара, две группы полей: товар и поставщик). `price` показывается как есть из контракта, `available_stock` — как есть; `last_update_date` форматируется локальным хелпером страницы по образцу `formatRegistrationDate` в `ClientsListPage.tsx` (год-месяц-день час:минута), на невалидную дату показывается сырое значение.

**Обоснование.** Формат даты регистрации уже принят в панели; `price` — строка контракта, панель её не переформатирует (решение `2026-10-18-products-management`). Повторение готового шаблона дешевле преждевременного вынесения в `shared/`.

**Альтернативы.** Вынести форматтер в `src/shared` — отложено (одно дублирование, в соответствии с решениями прежних изменений о переносе общего кода в отдельный change).

### 7. Резолвер ошибок карточки — локальная функция страницы

**Решение.** В `ProductDetailsPage.tsx` — локальный резолвер по шаблону списка товаров и клиентов: `NetworkError` → `errors.network`; `ApiError` 401 → `null` (сообщение не показывается, сессию завершает глобальный обработчик); 400/500 → `responseMessage ?? fallback`; 503 → откат `errors.server` независимо от тела ответа; прочее → `errors.server`. Откат для 503 — мандат спецификации `frontend/products-list` (сценарий «Service Unavailable (503)» требует откат безусловно); текущий auth middleware (`api/internal/auth/middleware.go` через `response.Abort` в `api/internal/response/response.go`) возвращает 503 с полем `message`, и карточка его не показывает.

**Обоснование.** Списочные страницы панели, страницы аутентификации и фича фотографий держат резолверы ошибок локально; вынесение в `shared/` — зафиксированное отложенное решение, не входит в этот change.

**Альтернативы.** Использовать `resolveProductMutationError` — отклонено: резолвер мутаций содержит смыслы статусов (409), отсутствующие у GET, и fallback-ключ не совпадает с трактовками ошибок загрузки.

### 8. Состав действий карточки — только просмотр, фото и возврат

**Решение.** На карточке ровно две кнопки-действия: управление фотографией (диалог) и возврат к `/products`. Никаких delete/edit/stock-кнопок: список остаётся местом мутаций.

**Обоснование.** Спецификация карточки требует отсутствия операций, не поддерживаемых контрактом; страница карточки не должна выманивать пользователя из строки списка на место, где мутации недоступны. Удаление товара остаётся на строке.

**Альтернативы.** Дублировать «Удалить» и «Уменьшить остаток» на карточке (операции API поддерживает) — отклонено: не является целью карточки, дублирует операции списка, размывает, где живёт операция.

## Risks / Trade-offs

- **[Trade-off] Прямой URL — единственный путь к товару с нулевым остатком.** Список таких товаров не отдаёт (`available_stock > 0`), поэтому из списка карточку zero-stock товара не открыть. → Принято как контрактное ограничение (см. proposal); поиск по всем товарам — отдельная тема для backend, не затрагивающая спецификацию карточки, которая корректно обрабатывает и товар с `available_stock = 0` при прямом URL.
- **[Risk] Разделение кешей `["products"]` и `["product", id]` создаёт два источника данных одного товара.** → Смягчается решением 4: обе точки входа инвалидируются в мутациях списка, фотография инвалидируется существующими хуками; юнит-тесты фиксируют каждую инвалидацию.
- **[Risk] После удаления товара открытая карточка показывает состояние отсутствия.** → Смягчается инвалидацией `["product"]` в `useDeleteProduct`: повторный GET отвечает 404, карточка показывает not-found, а не устаревшие данные.
- **[Trade-off] Локальные дубли хелпера даты и резолвера ошибок.** → Принято по прецедентам панели; вынесение в `shared/` отложено (см. Non-Goals), тесты покрытием не зависят.
- **[Risk] Компонент `ProductImage` изменяет существующий диалог.** → Замена механическая: поведение диалога и его тесты (`src/test/product-images.test.tsx`) обязаны остаться зелёными; сценарии списка товаров и его моков не затрагиваются.
