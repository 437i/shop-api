# Design

## Context

См. `proposal.md` — Why.

Факты, определяющие подход:

- `api/internal/auth/handler.go:12` — интерфейс `Service` из четырёх методов: `Register`, `Login`, `ResetPassword`, `ChangePassword(ctx, ChangeRequest, token string) error`. `ValidateToken` вынесен в отдельный интерфейс `Validator` (`internal/auth/middleware.go:16`).
- `api/internal/auth/mock_grpc_client.go` — `Mock` реализует `ValidateToken`, `Register`, `Login`, `ResetPassword`, но **не** `ChangePassword`. Метод появился в интерфейсе вместе с коммитом «add ChangePassword endpoint to api», а мок не был дополнен.
- `api/internal/app/app.go:109` — `mockAuthModule` объявляет `fx.Annotate(auth.NewMock, fx.As(new(auth.Service)), fx.As(new(auth.Validator)))`. Проверка интерфейса выполняется рефлексией в рантайме: `fx@v1.24.0/annotated.go:1356` — `if !t.Implements(at.types[i].typ) { return ... "invalid fx.As: %v does not implement %v" }`. Ошибка возникает при построении графа, поэтому `go build` и `go vet` её не видят.
- `cmd/api/main.go:21` — основная конфигурация использует `fx.New(app.Module)`, то есть реальный gRPC-клиент; `app.MockModule` в рабочем стенде не участвует.
- `api/internal/auth/grpc_client.go:133` — реальный клиент отображает `UNAUTHENTICATED` в `ErrWrongPassword`, который `MapErrToHTTP` (`internal/auth/errors.go:13`) превращает в HTTP 400 «invalid current password».
- Тестов в пакете `internal/auth` нет; ни один тест в `api/` не собирает `MockModule` — дефект не ловится ни CI, ни локальной проверкой.
- `docker-compose.yml` поднимает `auth` (Java, gRPC 50051) и `auth-postgres`; `be3-auth` в рабочем стенде отвечает, а `POST /api/v1/register` против Go API возвращает 201 с настоящим JWT.

## Goals / Non-Goals

**Goals:**
- `app.MockModule` собирается, а dev-mock обслуживает все четыре auth-эндпоинта, включая `POST /api/v1/change`.
- Регрессия на этот дефект ловится автоматически: тест строит fx-граф и обращается к auth-эндпоинтам.
- Документация описывает фактическое состояние стенда и разводит два пути аутентификации, не переписывая историю архивных изменений.

**Non-Goals:**
- Поведение продукта, HTTP-контракт и код фронтенда не меняются; основные спецификации `openspec/specs/` не затрагиваются.
- Java auth service и `app.Module` не изменяются.
- Dev-mock не становится полноценной реализацией аутентификации: он по-прежнему принимает любые credentials и отдаёт фиксированный токен.
- Мок не переносит реальные правила валидации Java (email `.ru`/`.com`, длина пароля, формат телефона) — они не относятся к дефекту и потребуют отдельного решения, когда появится auth-контур на фронтенде.

## Decisions

### 1. `Mock` получает `ChangePassword`, возвращая `ErrWrongPassword` для чужого токена

**Решение.** Метод реализуется по образцу реального клиента: токен сверяется с `m.mockToken`, при совпадении возвращается `nil`, при несовпадении — `ErrWrongPassword`.

**Обоснование.** `ErrWrongPassword` — тот же тип ошибки, что отдаёт реальный gRPC-клиент при `UNAUTHENTICATED` (`grpc_client.go:147-149`), и он же маппится в HTTP 400 «invalid current password». Мок, возвращающий другую ошибку, разошёлся бы с боевым поведением по коду ответа — а dev-конфигурация существует именно для того, чтобы проверять интеграцию без расхождений.

**Альтернативы.**
- *Возвращать `nil` всегда* — endpoint принимал бы любой токен, и проверка через middleware стала бы единственным барьером; расхождение с реальным поведением. Отклонено.
- *Возвращать `ErrUnauthenticated`* — этот тип отображается в HTTP 401, что для ошибки «неверный текущий пароль» неверно: контракт `POST /api/v1/change` отдаёт 400. Отклонено.
- *Удалить `MockModule` целиком* — устраняет дефект, но забирает у фронтенда возможность работать без стенда, которую `frontend/README.md` обещает. Отклонено.

### 2. Регрессионная защита — тест fx-графа, а не тест метода

**Решение.** Тест в пакете `internal/app` (внутренний тест, `package app`) строит граф из `mockAuthModule` и проверяет, что он собирается; второй тест поднимает gin-роутер с `auth.NewHandler` и `auth.NewMiddleware` и проверяет, что `POST /api/v1/change` с mock-токеном отвечает 204. Ветка с чужим токеном проверяется прямым вызовом метода в `internal/auth`: через HTTP она недостижима, потому что middleware (`internal/auth/middleware.go:43`) отклоняет невалидный токен раньше обработчика и отвечает 401, а не 400.

**Обоснование.** Дефект возник не в логике метода, а в несовпадении типа с интерфейсом, и проверяется только сборкой графа. Тест одного метода его бы не поймал: `Mock` без `ChangePassword` просто не удовлетворяет интерфейсу, и компилятор на это не смотрит. Сборка графа — единственная проверка, которая воспроизводит исходный отказ, и `mockAuthModule` не требует БД, поэтому тест остаётся без инфраструктуры.

**Альтернативы.**
- *Компиляционная проверка `var _ auth.Service = (*auth.Mock)(nil)`* — ловит дефект на этапе компиляции и стоит ноль кода. Отклонена как единственная мера: она не проверяет, что граф действительно собирается (ошибка `fx.As` возникает в рантайме), и не защищает от следующей подобной рассинхронизации интерфейса.
- *Ручная проверка запуска* — не воспроизводится автоматически. Отклонена.

### 3. Документация: README переписывается, архивы дополняются датированной сноской

**Решение.** Раздел «Local authentication (dev-mock)» в `frontend/README.md` переписывается целиком: Java auth service подключён и используется по умолчанию, dev-mock — опциональная альтернатива. В архивных артефактах **не переписывается** исторический текст, а добавляется датированное «Уточнение» с фактом: на момент архивации утверждение было верно, сейчас — нет.

**Обоснование.** Архив — запись о том, что было проверено тогда; переписывание стёрло бы след проверки и создало бы впечатление, будто ручная проверка шла против реального auth service. Сноска сохраняет и историю, и актуальную правду, и не даёт следующему читателю принять устаревшее ограничение за действующее.

**Альтернативы.**
- *Переписать архивные формулировки начисто* — архив перестал бы отражать состояние на момент архивации. Отклонено.
- *Оставить архивы как есть* — ложное утверждение осталось бы в восемнадцати файлах шести архивных изменений и продолжало уводить читателя. Отклонено.
- *Вынести правку в отдельный документ вне архива* — читатель архивного артефакта не встретит указания, где искать актуальную версию. Отклонено.

### 4. `skip_specs: true` — продуктовое поведение не меняется

**Решение.** В `.openspec.yaml` установлен `skip_specs: true`; файлы дельт не создаются.

**Обоснование.** Изменение чинит dev-инструмент и корректирует документацию. Ни одно требование существующих capability не меняется: HTTP-контракт, поведение основной конфигурации Go API, Java auth service и фронтенд не затрагиваются. Требование о том, что dev-конфигурация обязана собираться, относится к внутреннему dev-инструменту, а продукт в dev-конфигурации не работает по-другому — он просто не запускается.

**Альтернативы.**
- *Новая capability `backend/dev-mock-auth`* — спецификация описывала бы не продуктовое поведение, а артефакт dev-режима; в наборе спецификаций проекта нет ни одной capability про внутренний auth service, и добавлять её для мока — структурное решение, выходящее за рамки починки. Отклонено.
- *Изменение существующей capability `backend/*`* — потребовало бы выдумать требование, которого нет. Отклонено.

## Risks / Trade-offs

- **[Risk] Мок принимает любые credentials** → dev-проверка аутентификации может выглядеть успешной, не будучи таковой. Митигация: README явно разводит два пути и прямо называет, что dev-мок не проверяет аутентификацию; в `proposal.md` этот факт зафиксирован как открытый вопрос контракта.
- **[Risk] Новый тест в `internal/app` может потребовать инфраструктуры** → тест не должен требовать БД или gRPC-сервиса. Митигация: используется только `mockAuthModule` — он даёт `auth.Service`, `auth.Validator` и `auth.Middleware` и не зависит от `repoModule`/`infraModule`; `auth.Handler` в тесте предоставляется явно (`fx.Provide(auth.NewHandler)`), потому что он зависит только от `auth.Service` (`internal/auth/handler.go:23`). `handlerModule` в тест не подключается: он тянет доменные обработчики, а через них — сервисы, репозитории и БД.
- **[Trade-off] Сноски в архивах — это правка исторических файлов** → диф выглядит как изменение прошлого. Митигация: каждая сноска явно датирована и помечена как уточнение; исходный текст не тронут.
- **[Trade-off] `skip_specs: true` оставляет dev-путь без спецификации** → следующий разработчик может снова сломать интерфейс мока, не заметив. Митигация: регрессия закрыта тестом fx-графа, который падает при любом несовпадении набора методов с интерфейсом.
