# Design

## Context

Панель уже умеет управлять поставщиком из строки списка: создание с валидацией, изменение адреса, удаление (`frontend/suppliers-management`). Данные карточки приходят из эндпоинта `GET /api/v1/suppliers/{id}` → `internal_supplier.Response`, фронтендом он не используется, хотя backend его объявляет (`api/internal/server/router.go:63`). Прямой прецедент — только что реализованная карточка товара `frontend/product-details`: хук `useProductDetails` с 404-как-данными, страница на shadcn `Card`, локальный резолвер ошибок, e2e-мок в `helpers.ts`. Глобальные правила панели не меняются: `providers.tsx` содержит обработчик 401, маршруты защищены `ProtectedRoute`, кеш TanStack Query настроен на staleTime 5 минут.

## Goals / Non-Goals

**Goals:**
- Дать оператору страницу карточки поставщика со всеми полями `internal_supplier.Response` (имя, телефон, адрес).
- Повторить установленный паттерн карточки товара: тот же состав состояний, кеширование, обратная целостность с мутациями списка.
- Сохранить целостность кеша: мутации поставщика из списка (изменение адреса, удаление) актуализируют карточку.
- Остаться в границах фронтенда: Go API, Java-сервис и БД не меняются.

**Non-Goals:**
- Операции записи на карточке: редактирование имени/телефона — их нет в контракте; изменение адреса остаётся в меню строки списка.
- Блоки фотографии и дат: в `internal_supplier.Response` их нет, создавать заглушки не за чем.
- Карточка клиента (`GET /clients/{id}` в контракте отсутствует), справочники адресов, пагинация.
- Извлечение общего резолвера ошибок в `shared/` (отложенное решение из `2026-10-18-suppliers-management/design.md`, подтверждённое `add-product-details-page/design.md`).

## Decisions

### 1. Вход в карточку — первым пунктом меню строки

**Решение.** В `SuppliersListPage.tsx` в меню действий строки добавляется первый пункт «Details» («Карточка»), открывающий `navigate(`/suppliers/${id}`)`. Название поставщика в таблице остаётся текстом, клик по строке ничего не делает.

**Обоснование.** Точная копия решения `add-product-details-page/design.md` (решение 1): все операции строки уже живут в меню строки — конвенция проекта; ссылка в названии меняла бы наблюдаемое поведение колонки Name и тесты списка. Русская локализация пункта повторяет ключ товара — «Карточка».

**Альтернативы.** Ссылка на имени поставщика и клик по строке — отклонены по тем же причинам, что и в карточке товара.

### 2. Маршрут `/suppliers/:id` — защищённый дочерний маршрут существующего layout

**Решение.** В `router.tsx` внутри общего защищённого блока добавляется `{ path: "/suppliers/:id", element: <SupplierDetailsPage /> }`. Навигация в sidebar не меняется: карточка — просмотровый экран раздела.

**Обоснование.** Повторяет схему четырёх существующих защищённых маршрутов, включая `/products/:id`. Неизвестный путь остаётся `*` → `NotFoundPage`.

**Альтернативы.** Вложенный маршрут под `/suppliers` (Outlet) — отклонено: повторяет аргумент решения 2 из `add-product-details-page/design.md`.

### 3. Данные карточки — отдельный кеш `["supplier", id]`, 404 как состояние данных

**Решение.** Хук `useSupplierDetails.ts`: `useQuery({ queryKey: ["supplier", id], queryFn: getSupplier })`, где `getSupplier` выполняет `GET /api/v1/suppliers/{id}` и при 404 возвращает `null` (шаблон `getProduct`). Страница рендерит skeleton при загрузке, карточку по данным, состояние отсутствия при `null`; ошибки 400/500/503/сеть — Alert с «Повторить».

**Обоснование.** Отдельный ключ изолирует карточку от инвалидации списка `["suppliers"]` — так же, как `["product", id]` отделён от `["products"]`. Форма ответа `internal_supplier.Response` несовместима со строкой списка лишь частично, но изоляция ключей делает независимость явной и согласованной с карточкой товара.

**Альтернативы.**
- *404 как ошибка* — отклонено: состояние «поставщик не существует» (удалён, прямой URL) пользовательски отличается от «запрос сломался».
- *Кеш внутри `["suppliers"]`* — отклонено по тем же причинам, что и для товаров.

### 4. Мутации списка актуализируют карточку: `["supplier"]` инвалидируется вместе с `["suppliers"]`

**Решение.** В `useSupplierMutations.ts` экспортируется `SUPPLIER_QUERY_KEY = ["supplier"]`; после успеха `useUpdateSupplierAddress` и `useDeleteSupplier` добавляется `invalidateQueries({ queryKey: SUPPLIER_QUERY_KEY })` рядом с существующей инвалидацией `["suppliers"]`. Префикс `["supplier"]` не пересекается ни с `["suppliers"]`, ни с `["product"]`/`["product-image", id]`, ни с `["clients"]` — другие кеши не задеваются.

**Обоснование.** Аналог решения 4 `add-product-details-page/design.md`: без инвалидации карточка (staleTime 5 минут) показывала бы старый адрес до пяти минут после его изменения из списка. Для товаров у товарных мутаций свой ключ `["product"]`; эти инвалидации не конфликтуют, потому что ключи не пересекаются.

**Альтернативы.** Выключить кеширование карточки — отклонено: ломает общий контракт панели, как и для товаров.

### 5. Отображение данных: текстовые блоки карточки без фото и дат

**Решение.** Карточка собирается из shadcn `Card` (заголовок — имя поставщика, одна группа полей: Name, Phone, и блок Address: Country, City, Street). Действия карточки — единственная кнопка возврата к `/suppliers`. Резолвер ошибок — локальная функция страницы, дословно следующая решению 7 `add-product-details-page/design.md`: `NetworkError` → `errors.network`; `ApiError` 401 → `null`; 400 → `responseMessage ?? errors.invalidRequest`; 500 → `responseMessage ?? errors.server`; 503 → откат `errors.server` независимо от тела; прочее → `errors.server`.

**Обоснование.** У поставщика нет фотографии и дат — из шаблона карточки товара удаляются ровно эти блоки и хук `useProductImage`, остальное (skeleton с теми же строками/колонками, локальные функции, `RetryableErrorAlert`) переносится без изменений. Единая обработка ошибок между карточками товара и поставщика — видимая консистентность панели.

**Альтернативы.** Форма редактирования на карточке — отклонено: контракт не поддерживает `PATCH` name/phone; вынести резолвер в `shared/` — отложено (зафиксированное отложенное решение).

## Risks / Trade-offs

- **[Trade-off] Прямой URL — единственный способ открыть карточку удалённого поставщика.** Из списка его карточку не открыть (строка удалена) — это ожидаемое поведение; состояние 404 на карточке обрабатывается.
- **[Risk] Разделение кешей `["suppliers"]` и `["supplier", id]` создаёт два источника данных одного поставщика.** → Смягчается решением 4: обе точки инвалидируются в мутациях списка; юнит-тесты фиксируют каждую инвалидацию.
- **[Risk] После удаления поставщика открытая карточка показывает старые данные.** → Смягчается инвалидацией `["supplier"]` в `useDeleteSupplier`: повторный GET отвечает 404, карточка показывает not-found.
- **[Risk] Второй однотипный change повышает дублирование между карточками.** → Принято: локальные дубли (хук, резолвер) следуют прецедентам панели; вынесение в `shared/` — отдельная тема, зафиксированная как отложенное решение в двух прежних changes.
- **[Note] Мок атрибутов поставщика в e2e уже есть** (`MOCK_SUPPLIERS` содержит адрес), мок `GET /suppliers/{id}` не конфликтует со списком.
