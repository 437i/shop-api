# Proposal

## Why

Административная панель не различает пользователей по правам: Go API не содержит ролей и проверок прав, а Java-сервис аутентификации выдаёт JWT без claim `roles`, поэтому любой пользователь, получивший валидный токен через открытую регистрацию, может выполнять все операции CRUD над клиентами, товарами, поставщиками и изображениями. Это поведение нигде не зафиксировано, из-за чего его легко принять за осознанную гарантию безопасности. Нужно описать фактическую модель доступа, закрепить её наблюдаемую frontend-часть в спецификации и явно обозначить ограничение локального учебного стенда — не превращая неограниченный CRUD в нормативную гарантию.

## What Changes

- Появляется новая capability `frontend/admin-access-model`, фиксирующая наблюдаемое поведение интерфейса: панель не применяет ролевых проверок при определении набора отображаемых разделов и действий, не определяет самостоятельно валидность сохранённого токена и не запрашивает сведения о роле, правах или профиле. Правило открытия защищённых разделов по наличию сохранённого токена остаётся в `frontend/protected-navigation` и в новой capability не дублируется.
- Capability не определяет и не гарантирует разрешения на стороне Go API или Java-сервиса аутентификации: серверная проверка токена и отсутствие серверного разграничения прав — отдельные факты, которые эта capability не изменяет. Отсутствие серверного разграничения прав описывается как зафиксированный риск текущего локального стенда, а не как постоянная целевая модель безопасности.
- Ограничение модели доступа описывается в Purpose новой capability, в design и в proposal как принятый риск: стенд с открытой саморегистрацией и без ролевой авторизации нельзя считать пригодным для публичного развёртывания; до публичной эксплуатации требуется отдельное изменение модели доступа с проверкой авторизации на backend.
- **Не создаётся** backend-спека про неограниченный CRUD для любого аутентифицированного пользователя: фактическое отсутствие ролей и проверок прав в Go API фиксируется как контекст и принятый риск, а не как желаемое нормативное поведение.
- Go API и Java-сервис не изменяются: продуктового поведения изменения нет.
- В `frontend/README.md` добавляется примечание о том, что локальный стенд не предназначен для публичного развёртывания.
- Добавляются регрессионные тесты, фиксирующие текущую frontend-модель доступа: валидность токена определяет сервер, набор отображаемых разделов и действий не зависит от сведений о пользователе, сведения о роле и профиле не запрашиваются и не передаются. Существующее покрытие маршрутной защиты и навигации (`routing.test.tsx`, `admin-layout.test.tsx`) не дублируется и не изменяется.

## Capabilities

### New Capabilities

- `frontend/admin-access-model`: фактическое поведение интерфейса административной панели — ролевые проверки не применяются, валидность сохранённого токена панель не определяет, сведения о роле, правах и профиле не запрашиваются; описано, что capability не распространяет гарантий на разрешения серверной стороны и не дублирует правило открытия защищённых разделов, принадлежащее `frontend/protected-navigation`.

### Modified Capabilities

- Нет. Требования существующих capabilities не меняются: `frontend/protected-navigation` остаётся единственным нормативным источником правила открытия защищённых разделов по наличию токена и требований об отображении всех разделов навигации, а новая capability ссылается на них без дублирования; требования о завершении сессии по 401, выходе и переключателе языка не затрагиваются.

## Impact

- **Код продукта:** не изменяется. Изменение документационное по отношению к поведению, оно фиксирует уже реализованное состояние.
- **Фронтенд:** новая capability `frontend/admin-access-model`; три регрессионных теста в `frontend/src/test/`; примечание в `frontend/README.md`.
- **API:** новых, изменяемых и удаляемых endpoints нет. Используется существующее поведение защищённых маршрутов Go API, зафиксированное в спецификациях: `GET /api/v1/clients`, `GET /api/v1/products`, `GET /api/v1/suppliers` — успех 200 для аутентифицированного пользователя и 401 от middleware при отсутствующем или недействительном токене; проверка токена выполняется на стороне сервера (`api/internal/auth/middleware.go:28-51`).
- **Сервисы:** Go API и Java-сервис аутентификации не изменяются.
- **Зависимости:** новых пакетов нет.

## Существующие API endpoints, на которые опирается изменение

| Endpoint | Использование в модели доступа |
|---|---|
| `GET /api/v1/clients` | Ответ 200 подтверждает доступ аутентифицированного пользователя; 401 — завершение сессии |
| `GET /api/v1/products` | То же |
| `GET /api/v1/suppliers` | То же |
| `POST /api/v1/auth`, `POST /api/v1/register` | Единственный источник токена; `POST /api/v1/register` открыт и не требует одобрения |

## Нерешённые вопросы контракта и аутентификации

1. **Где должны появляться роли и права** — как claim в JWT, как поле ответа API или как отдельный endpoint — в текущем контракте не определено: ни Go API, ни proto (`grpc/auth.proto`) не содержат ни одного упоминания ролей или прав. Вопрос относится к будущему изменению модели доступа, а не к текущему.
2. **Нет endpoint профиля текущего пользователя.** `GET /api/v1/me` в контракте отсутствует, поэтому панель не может узнать ни имя, ни роль пользователя — и сегодня не запрашивает их.
3. **Нет отзыва токена.** В proto отсутствуют `RefreshToken` и logout/revoke, поэтому завершение сессии возможно только по 401 от middleware; скомпрометированный токен остаётся действительным до истечения срока.
4. **Регистрация открыта.** `POST /api/v1/register` не требует подтверждения и не проверяет право на административный доступ; в сочетании с отсутствием ролей это и есть источник описанного риска.
