# Design

## Context

Мотивация изменения — в `proposal.md` (раздел Why). Здесь только фактическое состояние и ограничения, определяющие подход.

**Фактическая модель доступа по слоям:**

```
  [Java auth service]  UserEntity без поля ролей; JWT-claim'ы только
                        sub, email, firstName, lastName, iat, exp
                        (service_auth/.../security/JwtService.java:30-38)
        |  gRPC ValidateToken(valid bool)  -- 5-секундный таймаут
        |  (api/internal/auth/grpc_client.go:48-63)
        v
  [Go API]  единственный guard -- auth.Middleware.Auth на группе protected
             (api/internal/auth/middleware.go:28-51)
             проверяет только Bearer-токен: 401 при отсутствии/невалидном,
             404/400/409 -- бизнес-ошибки, 403 не возвращается ни одним маршрутом
             (api/internal/server/router.go:27-73)
        |
        v
  [Frontend]  ProtectedRoute проверяет только наличие токена в localStorage
              (frontend/src/app/ProtectedRoute.tsx:6-12);
              навигация отображает все разделы безусловно
              (frontend/src/app/AdminLayout.tsx:58-90);
              запросы несут только Authorization: Bearer <token>
              (frontend/src/shared/api/client.ts:80-98)
```

- `POST /api/v1/register` открыт, подтверждения и проверки права на административный доступ не требует (`api/internal/server/router.go:29`).
- В proto отсутствуют `RefreshToken`, logout/revoke и любые RPC про роли или права (`grpc/auth.proto:13-31`).
- Endpoint профиля текущего пользователя (`GET /api/v1/me`) в контракте отсутствует, поэтому панель не может узнать ни личность, ни роль пользователя.
- Токен на frontend — непрозрачная строка: `getAuthToken()` возвращает `localStorage.getItem("auth_token")` (`frontend/src/shared/api/client.ts:44-46`), `ProtectedRoute` проверяет только наличие этой строки (`frontend/src/app/ProtectedRoute.tsx:7`), а JWT нигде не разбирается и не проверяется. Подлинность и срок действия определяет сервер; отказ приходит ответом 401, который обрабатывает API-клиент (`frontend/src/shared/api/client.ts:122-129`).
- `frontend/protected-navigation` уже фиксирует и правило открытия защищённых маршрутов по наличию токена в localStorage, и отображение всех разделов навигации без неактивных разделов — новая capability ссылается на эти требования, но не дублирует их.

**Ограничения, заданные решением владельца:** не создавать нормативное требование, превращающее неограниченный CRUD для любого пользователя в постоянное желаемое поведение; фактическое поведение и принятый риск должны быть указаны явно; стенд с такой моделью нельзя считать безопасным для публичного развёртывания; Go API и Java-сервис не изменяются.

## Goals / Non-Goals

**Goals:**
- Зафиксировать наблюдаемую frontend-модель доступа в спецификации как отдельную capability с собственным Purpose, где ограничение остаётся видимым после переноса в main specs.
- Разделить нормативную часть (что панель делает) и описательную (почему так и почему это временно).
- Сохранить в проекте проверяемый след: регрессионные тесты фиксируют текущее поведение, чтобы случайная правка не изменила модель молча.
- Обозначить в документации проекта, что локальный стенд не предназначен для публичного развёртывания.

**Non-Goals:**
- Не вводить роли, права, профили пользователя и любые новые endpoints.
- Не менять Go API, Java-сервис, proto, миграции и контракт Swagger.
- Не менять продуктовый код панели: поведение уже соответствует тому, что фиксируется.
- Не проектировать будущую модель доступа и не выбирать, где появятся роли — это отдельное изменение.
- Не добавлять в UI предупреждение о стенде: визуальное сообщение о временном характере режима не запрашивалось и изменило бы продукт.

## Decisions

### 1. Новая capability `frontend/admin-access-model`, а не модификация `frontend/protected-navigation`

**Решение.** Создаётся отдельная capability `frontend/admin-access-model`; требования `frontend/protected-navigation` не меняются. Новая capability не пересказывает требование «Защищённые маршруты требуют токен»: правило открытия разделов по наличию сохранённого токена остаётся в `frontend/protected-navigation`, а новая capability фиксирует только то, чего в проекте нет, — отсутствие ролевых проверок, отсутствие самостоятельной проверки валидности токена и отсутствие запросов сведений о роле и профиле.

**Обоснование.** Существующая capability описывает механику защиты маршрутов и навигации и уже содержит два смежных требования: «Защищённые маршруты требуют токен» (наличие токена в localStorage) и «Административный layout содержит навигацию» (все пункты меню отображаются, неактивных разделов нет). Если продублировать их в новой capability, одно и то же наблюдаемое поведение окажется заявлено в двух местах, и при первом же изменении правила открытия разделов обновлять придётся обе capability — иначе одна из них станет ложной. Поэтому новая capability не пересказывает уже заявленные правила, а ссылается на них и фиксирует только новое. Разные утверждения в одной capability по-прежнему смешали бы маршрутизацию, сессию и модель прав.

**Альтернативы.**
- *Добавить требование в `frontend/protected-navigation`* — отклонено: capability превратилась бы в смесь маршрутизации, сессии и модели доступа, а её Purpose («Защищает административные маршруты от неавторизованного доступа и предоставляет навигацию с возможностью выхода») не вмещает описание отсутствия ролевой модели.
- *Продублировать в новой capability требование «Защищённые маршруты требуют токен»* — отклонено: два нормативных источника для одного поведения расходятся при первом же изменении правила открытия разделов; вместо дублирования применена ссылка на существующую capability.
- *Без capability, только в proposal* — отклонено: proposal архивируется вместе с изменением и через несколько изменений перестаёт быть актуальным документом; ограничение должно жить рядом с нормативными требованиями.

### 2. Нормативная часть ограничена frontend-частью; backend-факты живут в design

**Решение.** Delta spec содержит только утверждения о поведении панели. Факты об отсутствии ролей в Go API, об отсутствии `roles` в JWT, об открытой регистрации и об отсутствии 403 фиксируются в `design.md` (Context, Risks) и в `proposal.md` (принятый риск), но не становятся требованиями.

Лексика требований ограничена интерфейсом: «отображаемые разделы» и «отображаемые действия». Формулировка про «доступные операции» читалась бы как обещание backend, что пользователь с действительным JWT вправе выполнять любой CRUD-запрос, а это и есть то самое обещание, которое запрещено. Поэтому требования говорят о том, что панель показывает и открывает, а не о том, что разрешено на сервере.

Правило открытия разделов по наличию сохранённого токена в новой capability не воспроизводится, а упоминается ссылкой на `frontend/protected-navigation`: это позволяет читателю найти нормативное требование там, где оно живёт, не создавая второго.

**Обоснование.** Требование в backend-capability вида «любой аутентифицированный пользователь имеет полный доступ ко всем ресурсам» нормативно закрепило бы временное ограничение стенда как желаемую постоянную гарантию — прямое противоречие принятому решению. При этом терять сведения о фактическом поведении нельзя, поэтому они вынесены в документы, которые живут вместе с изменением, и явно помечены как риск. Граница проходит по слоям: нормативно фиксируется то, что наблюдаемо в интерфейсе, и явно оговаривается, что capability не определяет и не гарантирует разрешения на стороне Go API и Java-сервиса аутентификации.

**Альтернативы.**
- *Capability `backend/access-control` с требованием «403 не используется, роли не проверяются»* — отклонено по той же причине: это нормативное обещание неограниченного доступа.
- *Требование «frontend MUST запрещать себе ролевые проверки» (запрет на запрет)* — отклонено: такое требование описывает отсутствие функции и плохо проверяется; положительная формулировка «панель не применяет ролевых проверок» проверяется наблюдаемо — через одинаковый набор разделов и действий у пользователей с разными сохранёнными токенами.

### 3. `skip_specs: true` не используется

**Решение.** Изменение объявляет capability, а не отказывается от спецификации.

**Обоснование.** Общее правило схемы — «если поведение не меняется, спецификация не меняется» — защищает от выдумывания требований ради валидации. Здесь не выдумывается: наблюдаемое поведение уже реализовано, и решение владельца — зафиксировать его в спеке. Capability вводит контракт текущей модели, чтобы будущее изменение модели доступа обязано было её обновить, а не изменить поведение молча. Кроме того, без capability изменение свелось бы к документации в proposal, который архивируется и теряет актуальность.

**Альтернативы.**
- *`skip_specs: true` и фиксация только в proposal/design* — отклонено: ограничение перестаёт быть частью нормативного контракта панели.

### 4. Формулировка требований и место ограничения

**Решение.** Требования формулируются положительно и наблюдаемо:

- панель не применяет ролевых проверок при определении набора отображаемых разделов и действий;
- панель не определяет самостоятельно валидность сохранённого токена: она работает с непрозрачной строкой из localStorage, а подлинность и срок действия определяет сервер;
- панель не запрашивает сведения о роле, правах или профиле пользователя и не включает их в запросы;
- текст требований и Purpose явно оговаривают, что capability не определяет и не гарантирует разрешения на стороне Go API или Java-сервиса аутентификации, и что правило открытия защищённых разделов принадлежит `frontend/protected-navigation`.

Формулировка «действительный токен» в требованиях не используется: она означала бы, что панель сама проверяет подлинность и срок действия, чего в коде нет и что делало бы capability зависимой от способа хранения токена. Спецификация говорит о наличии сохранённого токена, а серверная проверка остаётся отдельным фактом вне этой capability.

Ограничение разделено по слоям. Нормативные требования фиксируют только поведение frontend — отсутствие ролевых проверок, отсутствие самостоятельной проверки валидности токена, отсутствие запросов сведений о роле и профиле — и содержат нейтральную оговорку о том, что capability не определяет и не гарантирует разрешения на стороне Go API или Java-сервиса аутентификации. Фактическое состояние стенда — отсутствие серверного разграничения прав — документируется описательно: в Purpose новой capability (путешествует вместе с main spec), в разделе Risks этого design, в разделе «Нерешённые вопросы» proposal и в примечании `frontend/README.md`; внутри нормативного требования оно не фиксируется.

**Обоснование.** Требование — это обещание системе; описание ограничения — это контекст для человека. Смешивать их в одном артефакте нельзя: нормативная форма делает временное ограничение бессрочным. Purpose существует именно для описания границ capability и переносится в main spec при архивировании, поэтому именно там ограничение остаётся видимым.

**Альтернативы.**
- *Добавить в требование оговорку «в рамках текущей конфигурации стенда»* — отклонено: оговорка внутри нормативного текста размывает его и превращает временное условие в часть обещания; при следующем изменении модели оговорку пришлось бы вычищать из требования.
- *Требование «модель доступа должна измениться до публичного развёртывания»* — отклонено: это намерение, а не наблюдаемое поведение; оно принадлежит будущему изменению.

### 5. Регрессионные тесты вместо изменения продуктового кода

**Решение.** Продуктовый код не меняется. В `frontend/src/test/` добавляются три теста на непокрытые утверждения: (1) валидность токена определяет сервер — раздел открывается по наличию сохранённого токена, а отказ приходит ответом сервера; (2) набор отображаемых разделов и действий не зависит от сведений о пользователе; (3) панель не запрашивает сведения о роле, правах или профиле пользователя и не включает их в запросы. Существующие проверки `routing.test.tsx` (открытие защищённого маршрута по наличию токена, редирект без токена, видимость всех разделов), `admin-layout.test.tsx` (пункты навигации) и `api-client.test.ts` (Bearer-заголовок, обработка 401) не дублируются и не изменяются.

**Обоснование.** Спецификация без проверки остаётся декларацией. Тест делает модель доступа наблюдаемо защищённой от случайной правки: если кто-то добавит скрытие разделов по признаку доступа или запрос ролей, тесты упадут. Существующие тесты закрывают смежные, но не те же утверждения: маршрутная защита проверяется одним и тем же токеном, тогда как в требованиях заявлена независимость набора разделов и действий от сведений о пользователе, и нигде не проверяется отсутствие запроса профиля. Новых зависимостей не требуется, существующие моки `fetch` и `apiClient` достаточны.

**Альтернативы.**
- *Только чтение существующих тестов* — отклонено: `routing.test.tsx` и `admin-layout.test.tsx` используют один и тот же токен и не проверяют, что запросы не несут сведений о правах; без новых тестов часть требования не покрыта.
- *Предупреждение в UI о стенде* — отклонено как изменение продуктового поведения, выходящее за рамки.

### 6. Формулировка «стенд не пригоден для публичного развёртывания» фиксируется в документации проекта

**Решение.** В `frontend/README.md` добавляется короткое примечание: локальный стенд использует реальную аутентификацию без ролевого разделения и открытую регистрацию, поэтому не должен использоваться в публичном развёртывании; до этого требуется отдельное изменение модели доступа с проверкой авторизации на backend.

**Обоснование.** README — единственное место, где читатель стенда видит ограничение до того, как начнёт им пользоваться. Ограничение только в архиве OpenSpec до читателя кода не дойдёт.

## Risks / Trade-offs

- **[Risk] Документация не является защитой: любой зарегистрированный пользователь по-прежнему может удалить все товары, клиентов и поставщики, потому что ролей нет ни в Go API, ни в Java-сервисе, а `POST /api/v1/register` открыт.** → Mitigation: риск явно зафиксирован в proposal, design и README; стенд помечен как непригодный для публичного развёртывания; отдельное изменение модели доступа с проверкой авторизации на backend вынесено за пределы этого изменения и обозначено как обязательное до публичной эксплуатации. Ограничение регистрации в одиночку может оказаться недостаточным, поскольку без проверки прав на backend ограничение не создаёт ролевой модели.
- **[Trade-off] Спецификация закрепляет текущее поведение как контракт, и будущее изменение модели доступа обязано её обновить.** → Это цель: контракт заставляет менять модель явно, а не молча. Затрагивается только frontend-часть; backend-спека о CRUD не создаётся.
- **[Trade-off] Требование «панель не применяет роли» станет ложным, когда роли появятся в контракте, и потребует обновления capability.** → Обновление capability — ожидаемый и предсказуемый шаг будущего изменения модели доступа; до тех пор требование соответствует коду.
- **[Risk] Фактическое состояние серверного разграничения прав, вынесенное в Purpose и Risks, а не в нормативное требование, может быть пропущено читателем спецификации, смотрящим только на требования.** → Mitigation: Purpose новой capability открывает её первую строку в main spec; текст ограничения в нём сформулирован прямо и повторяется в README, а нормативное требование содержит нейтральную оговорку о том, что capability не определяет и не гарантирует серверные разрешения.
- **[Risk] Регрессионный тест фиксирует текущую реализацию, а не контракт, и при легитимном будущем изменении начнёт падать.** → Mitigation: тест проверяет наблюдаемое поведение (доступ по токену, отсутствие сведений о правах в запросах), а не внутренние детали; при появлении ролей тест обновляется вместе с capability в том же изменении.
- **[Trade-off] Новая capability ссылается на требование `frontend/protected-navigation` вместо того, чтобы повторять его, — при изменении правила открытия разделов ссылку нужно перепроверить.** → Ссылка названа явно в Purpose, в описании требования о ролевых проверках и в сценарии про серверную проверку токена; изменение правила открытия разделов по наличию сохранённого токена обязано затронуть и новую capability.
