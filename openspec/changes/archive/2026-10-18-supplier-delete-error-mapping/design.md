# Design

## Context

См. `proposal.md` — Why. Техническая база (проверена по коду репозитория):

- `DELETE /api/v1/suppliers/{id}`: `handler.Delete` → `service.Delete` → `repository.Delete` (`api/internal/supplier/handler.go:122`, `service.go:74`, `pg_repository.go:99`). `service.Delete` возвращает ошибку репозитория без дополнительной обёртки, поэтому `errors.Is` доходит до handler без потерь.
- `repository.Delete` распознаёт только `pgerrcode.ForeignKeyViolation` (`23503`) и возвращает `ErrSupplierInUse`; остальные ошибки оборачиваются как `execute delete query: %w` (`pg_repository.go:108-115`).
- `MapErrToHTTP` уже отображает `ErrSupplierInUse` в HTTP 400 с текстом `supplier is used by products` (`errors.go:28-29`); `ErrNotFound` → 404, прочее → 500 `internal server error`.
- Ограничение — `products.supplier_id REFERENCES suppliers(id) ON DELETE RESTRICT` (`api/migrations/20260908133601_init_schema.sql:65-67`).
- Причина 500: в PostgreSQL 18 (образ `postgres:18` в `docker-compose.yml`) нарушение referential action RESTRICT возвращает SQLSTATE `23001` (`restrict_violation`) вместо `23503` (`foreign_key_violation`) — изменение PostgreSQL коммитом `086c84b23`; для PostgreSQL ≤ 17 остаётся `23503`.
- В закреплённой версии `github.com/jackc/pgerrcode` уже есть константа `RestrictViolation = "23001"` (проверено в `errcode.go`) — новых зависимостей не требуется.
- В `api/` нет тестов с реальной БД: существующие тесты (`api/internal/client/*_test.go`) — это unit-тесты с фейковыми `Service`/`Repository` и таблицами на стандартной библиотеке; тестовой инфраструктуры с PostgreSQL нет.

## Goals / Non-Goals

**Goals:**

- Восстановить контракт HTTP 400 `supplier is used by products` при удалении используемого поставщика на PostgreSQL 18 и сохранить его на PostgreSQL ≤ 17.
- Сохранить точное поведение всех остальных веток удаления (204, 404, 500, обёртка `execute delete query`).
- Покрыть маппинг SQLSTATE детерминированными unit-тестами без БД и проверить реальный сценарий на PostgreSQL 18.

**Non-Goals:**

- Изменение слоёв handler/service/errors, DTO, маршрутов, Swagger, БД и миграций.
- Маппинг FK-ошибок в других операциях (например, удаление товара в `api/internal/product/pg_repository.go`) — отдельная задача, вне scope.
- Автоматизированные интеграционные тесты с БД и новые зависимости (testcontainers, pgxmock).
- Проверка ветки `23503` на реальном PostgreSQL ≤ 17 — кодовая ветка покрывается unit-тестами с синтетической `pgconn.PgError`.

## Decisions

### 1. Маппинг остаётся в репозитории и расширяется на два SQLSTATE

**Решение:** в `repository.Delete` условие проверки становится `pgErr.Code == pgerrcode.ForeignKeyViolation || pgErr.Code == pgerrcode.RestrictViolation`; результат — существующий `ErrSupplierInUse`. Оба кода ведут к HTTP 400 с существующим сообщением.

**Альтернативы:**
- Обрабатывать только `23001` — отклонено: ломает PostgreSQL ≤ 17 и противоречит требованию сохранить `23503`.
- Проверять `pgErr.ConstraintName` (только FK `products.supplier_id`) — отклонено: текущий контракт маппит любое ссылочное нарушение при удалении в `ErrSupplierInUse`; привязка к имени ограничения хрупка при миграциях и меняет существующее поведение.
- Маппить всю группу `23xxx` — отклонено: `23505`/`23514` и прочие не являются конфликтом удаления и должны остаться 500.
- Перенести маппинг в service или `MapErrToHTTP` — отклонено: слои выше не должны знать о SQLSTATE; диагностика pgx остаётся в репозитории.

**Обоснование:** минимальное точечное изменение в единственном месте, где уже есть доступ к `*pgconn.PgError`, без изменения публичного контракта пакета.

### 2. Выделение неэкспортируемой функции маппинга ошибки удаления

**Решение:** проверку и обёртку вынести в небольшую неэкспортируемую функцию в `pg_repository.go` (рабочее имя `mapDeleteError(err error) error`): при `*pgconn.PgError` с кодом `23001` или `23503` возвращает `ErrSupplierInUse`, иначе — прежнее `fmt.Errorf("execute delete query: %w", err)`. `Delete` вызывает её вместо inline-логики. Поведение и тексты ошибок сохраняются байт-в-байт.

**Альтернативы:**
- Тестировать маппинг только через реальную БД — отклонено: в проекте нет тестовой инфраструктуры с PostgreSQL; добавление testcontainers — новая зависимость без доказанной необходимости (ограничение задачи).
- `pgxmock`/мок `DBTX` — отклонено: репозиторий держит конкретный `*pgxpool.Pool`, внедрение мока потребовало бы структурных изменений; сам маппинг — чистая функция от ошибки.
- Оставить логику inline и не тестировать — отклонено: именно эта логика содержит дефект, регрессия должна ловиться тестом.

**Обоснование:** рефакторинг без изменения поведения, ограниченный одним файлом; unit-тесты конструируют `*pgconn.PgError` напрямую (в том числе обёрнутый через `%w`) и проверяют `errors.Is(err, ErrSupplierInUse)` — детерминированно и без новых зависимостей.

### 3. Тестирование на двух уровнях

**Решение:**
- `api/internal/supplier/pg_repository_test.go`: табличные тесты `mapDeleteError` — `23001`, `23503`, обёрнутые `%w`-версии обоих, `23505`, `*pgconn.PgError` с пустым кодом (`Code == ""`), ошибка без `*pgconn.PgError`; для нессылочных ошибок — проверка префикса `execute delete query` и `errors.Is` не срабатывает.
- `api/internal/supplier/handler_test.go`: тестовый gin-роутер с фейковым `Service` (паттерн `api/internal/client/handler_test.go`): `ErrSupplierInUse` → 400 и тело `ErrorResponse` с точным сообщением `supplier is used by products`; прочая ошибка → 500 `internal server error`; `ErrNotFound` → 404 `supplier not found`; успешное удаление → 204 без тела; недействительный id → 400 без обращения к сервису.

**Обоснование:** unit-уровень фиксирует маппинг SQLSTATE (в том числе ветку `23503`, недостижимую на PG 18), handler-уровень фиксирует наблюдаемый HTTP-контракт.

### 4. Реальная проверка — ручная на локальном стеке PostgreSQL 18

**Решение:** проверка сценария на локальном стеке (`docker compose` → PostgreSQL 18 + Go API с dev-mock auth, см. `frontend/README.md`), без перехватов: создать поставщика (`POST /api/v1/suppliers`), создать товар с `supplier_id` (`POST /api/v1/products`: `name`, `category`, `price`, `available_stock`, `supplier_id`), вызвать `DELETE /api/v1/suppliers/{id}` → ожидается 400 с `supplier is used by products`; убедиться через `GET /api/v1/suppliers/{id}` и `GET /api/v1/products/{id}`, что обе записи на месте; очистка — удалить товар, затем поставщика (204). Результат зафиксировать в `tasks.md`.

**Альтернатива:** автотест с реальной БД — отклонено: нет существующей инфраструктуры, новая зависимость не оправдана; формат ручной проверки повторяет проверку 6.3 изменения `suppliers-management` (где дефект и был обнаружен).

**Обоснование:** проверяется именно продовый путь PostgreSQL 18 → pgx → handler, который unit-тесты не покрывают.


> **Уточнение (2026-10-21).** Описанное выше — состояние на момент архивации: стенд использовал dev-mock auth, реальная аутентификация была недоступна. С тех пор `docker-compose` поднимает Java auth service (`auth`, `auth-postgres`), `cmd/api` запускает `app.Module` с реальным gRPC-клиентом, а dev-mock приведён в соответствие и остаётся опциональной альтернативой; поэтому приведённые выше утверждения о недоступности реального auth service, об актуальности `frontend/README.md` и о работе раздела только при dev-mock auth не описывают текущий стенд — см. `frontend/README.md`, раздел «Local authentication».

## Risks / Trade-offs

- **[Риск] Ошибка остаётся неклассифицированной при других SQLSTATE от ссылочных нарушений** → митигация: условие включает оба фактически возможных кода (`23001` и `23503`); прочие коды сознательно остаются 500.
- **[Риск] Выделение функции случайно меняет обёртку ошибок** → митигация: тесты проверяют префикс `execute delete query` и маппинг в 500 для нессылочных ошибок.
- **[Trade-off] Ветка `23503` проверяется только unit-тестами, не на реальной БД ≤ 17** → принято: кодовая ветка изолирована в чистой функции, синтетическая `pgconn.PgError` идентична по структуре реальной; реальный стек работает на PG 18.
- **[Информация] FK-нарушения разбираются в `product.Create` (`api/internal/product/pg_repository.go:77`: `23503` → `ErrSupplierNotFound`), а `product.Delete` не различает FK-ошибки вовсе** → вне scope; изменения этого change касаются только удаления поставщика.
- **[Trade-off] Ручная проверка не воспроизводится в CI** → принято: в проекте нет Go-интеграционных тестов; шаги фиксируются в `tasks.md` для повторяемости.

## Migration Plan

Не применимо: контракт API, БД и миграции не меняются. Развёртывание — обычная сборка образа `api`; rollback — откат коммита изменения. Данные не мигрируются.

## Open Questions

Нет. Отложено (вне scope): проверка аналогичного маппинга в других операциях с FK при появлении подтверждённого сценария.
