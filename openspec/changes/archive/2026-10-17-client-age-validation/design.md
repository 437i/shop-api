# Design

## Context

См. `proposal.md` — Why. Поведенческий контракт — `specs/backend/clients-management/spec.md`.

Текущее состояние (проверено по коду):
- `POST /api/v1/clients` → `Handler.Create` (`api/internal/client/handler.go:39-72`): binding проверяет формат `birthday` (`2006-01-02`), `DTOToModel` (`api/internal/client/mapper.go:9-20`) парсит дату через `time.Parse(time.DateOnly, ...)` → UTC-полночь, ошибки маппятся в 400 (`api/internal/client/errors.go:20-47`).
- `validateBirthday` (`api/internal/client/service.go:34-45`) вызывается из `Create` до транзакции и сравнивает полные инстансы: `bday.After(now)`, `bday.Before(now.AddDate(-100, 0, 0))`, `bday.After(now.AddDate(-16, 0, 0))`.
- Колонка `birthday DATE` — date-only сквозь БД.
- Обязательность поля обеспечивает `binding`; `Mapper` возвращает `ErrInvalidBirthday` для несуществующих дат (`2026-02-30`), это отдельный от возраста путь.
- Go-тестов в `api/` нет; сообщения и статусы ошибок — часть наблюдаемого контракта.
- Frontend-спецификация `frontend/clients-management` уже требует календарную проверку 16–100; единая UTC-политика закреплена в её design и задачах (группа 8). Этот change приводит backend к той же политике без параллельной delta для frontend.

Дефект (подтверждён скриптом, повторяющим текущую логику):
- today `2026-10-16`: born `1926-10-16` (ровно 100) и born `1925-10-17` (100 лет, 101-й день рождения завтра) → `ErrTooOld`. Отклоняются все клиенты с календарным возрастом ровно 100; фактический максимум — 99.
- today `2016-02-29`: born `1915-03-01` (возраст 100, 101-й день рождения `2016-03-01`) → `now.AddDate(-100, 0, 0)` = `1916-02-29`, и `1915-03-01 < 1916-02-29` → `ErrTooOld` ошибочно.
- Возрастные границы вычисляются через `AddDate` от текущего инстанса, поэтому смещаются от времени суток и пояса процесса. `bday.After(now)` даёт `ErrTimeTravel` для даты, равной локальной «сегодня» в часовых поясах впереди UTC; по принятой UTC-политике такая дата будущая, и это отклонение сохраняется осознанно.

## Goals / Non-Goals

**Goals:**
- Привести серверную проверку к правилу спеки: 16–100 включительно по календарной дате UTC; будущая дата — отказ.
- Детерминированный результат относительно времени суток и часового пояса процесса; date-only семантика.
- Сохранить контракт (маршрут, статусы, тексты ошибок) и остальное поведение создания.
- Покрыть логику детерминированными unit-тестами без новых зависимостей.

**Non-Goals:**
- Изменения DTO, маршрутов, статусов, формата ответов, БД, миграций, gRPC.
- Передача часового пояса пользователя и «локальная дата пользователя»: осознанно заменена UTC-политикой; frontend выравнивается в `clients-management`.
- Рефакторинг несвязанного кода и оптимизация выборки/БД.

## Decisions

### 1. Явная календарная арифметика вместо AddDate

**Решение:** возраст вычисляется по гражданским компонентам (год, месяц, день):
- future: календарная дата рождения позже текущей даты UTC;
- слишком старый: возраст > 100 (101-й день рождения наступил);
- слишком молодой: возраст < 16 (16-й день рождения не наступил).

**Альтернативы и почему отклонены:**
- Обрезать время, оставив `AddDate(-100)`: не исправляет главный дефект — при today `2026-10-16` рождённый `1925-10-17` (возраст 100, 101-й день рождения завтра) всё равно отклоняется, так как его дата раньше усечённого порога `1926-10-16`; усечение меняет только случай рождённых ровно сегодня.
- Обрезать время и перейти на `AddDate(-101)`: при строгом `Before` равенство порогу пропускается — при today `2026-10-16` рождённый `1925-10-16` (101-й день рождения сегодня) ошибочно принимается, так как его дата равна усечённому порогу `1925-10-16`; при включительном `!After` ломается 29.02 — `time.Date(2016, 2, 29).AddDate(-101, 0, 0)` нормализуется в `1915-03-01`, и рождённый `1915-03-01` (возраст 100) при today `2016-02-29` ошибочно отклоняется как `ErrTooOld`. Нормализация делает порог неоднозначным.
- Библиотека дат (date-fns-подобная для Go): новая зависимость ради двух сравнений, избыточна.

**Обоснование:** явные компонентные сравнения детерминированы, совпадают с алгоритмом frontend и легко покрываются табличными тестами.

### 2. Опорная дата — календарная дата UTC

`today` берётся из компонент `now.UTC()`. Контракт `POST /api/v1/clients` не передаёт часовой пояс, поэтому определить локальную дату пользователя на сервере нельзя без расширения контракта (вне scope). UTC-дата детерминирована и совпадает с политикой frontend.

**Trade-off:** у полуночи UTC-дата может отличаться от локального календаря пользователя на ±1 день; затрагиваются только границы 16/100 и близкие к будущему даты (см. Risks).

### 3. Инъекция `now` для детерминированных тестов

`validateBirthday(bday, now time.Time) error` (неэкспортируемая), `Create` передаёт `time.Now()`. Внешние интерфейсы (`Service` в `handler.go`, `Repository`) не меняются.

**Альтернатива:** package-level переменная-часы — скрытое глобальное состояние, отклонено.

### 4. Сохранение порядка и семантики ошибок

Порядок проверок сохраняется: `ErrTimeTravel` → `ErrTooOld` → `ErrTooYoung`; все — HTTP 400 через существующий `MapErrToHTTP` с прежними текстами. Обёртка `fmt.Errorf("validate bday: %w", err)` сохраняется, `errors.Is` продолжает работать.

### 5. Правило 29 февраля

В невисокосный год день рождения 29 февраля считается наступившим 1 марта; в високосный — 29 февраля. Это выбранное правило (фиксируется впервые), оно следует из покомпонентного сравнения месяц/день и совпадает с frontend.

**Альтернатива:** считать наступившим 28 февраля — меняет возраст на день раньше и расходится с frontend, отклонено.

### 6. Тестирование без новых зависимостей

- `api/internal/client/service_test.go` (внутренний пакет `client`, табличные тесты): контролируемый `now`.
  - Границы: today `2026-10-16` UTC — `2010-10-17` → `ErrTooYoung`; `2010-10-16` → ok (ровно 16); `2009-10-16` → ok; `1926-10-16` → ok (ровно 100); `1925-10-17` → ok (100); `1925-10-16` → `ErrTooOld` (101); плюс по одному дню по обе стороны от обеих границ.
  - Будущая дата: `2026-10-17` → `ErrTimeTravel`; дата, равная today, не future и даёт `ErrTooYoung`.
  - Детерминизм: `00:00:01` и `23:59:59` одних и тех же суток UTC — одинаковые вердикты; один момент в `time.FixedZone` разных зон — одинаковые вердикты.
  - 29.02: born `2000-02-29` при `2016-02-28` → `ErrTooYoung`, при `2016-02-29` и `2016-03-01` → ok; born `1924-02-29` при `2025-02-28` → ok (100), при `2025-03-01` → `ErrTooOld` (101); дискриминирующий кейс born `1915-03-01` при `2016-02-29` → ok (100).
- `api/internal/client/mapper_test.go`: `DTOToModel` парсит `2000-02-29` в UTC-полночь и возвращает `ErrInvalidBirthday` для `2026-02-30`.
- `api/internal/client/errors_test.go`: сохранение контракта ошибок — `MapErrToHTTP` (`api/internal/client/errors.go`) для `ErrTooYoung`/`ErrTooOld`/`ErrTimeTravel` возвращает HTTP 400 и точные тексты сообщений; handler-проверка `POST /clients` на тестовом gin-роутере (существующая зависимость) с фейковым `Service`, возвращающим ошибку в обёртке реального сервиса (`validate bday: %w`), подтверждает формат `ErrorResponse` с полем `message`, содержащим точный текст причины.
- `api/internal/client/handler_test.go`: успешный путь `POST /clients` через тестовый gin-роутер (существующая зависимость) с фейковым `Service`, возвращающим созданного клиента и адрес, — HTTP 201 и существующий формат `Response`; подтверждает сценарий «Успешное создание» спеки.
- Регрессия `Create`: тест с ручными фейками `Repository`, `address.Repository`, `database.Transactor` — валидный клиент доходит до репозитория (вызовы зафиксированы), невалидный возраст прерывает выполнение до транзакции, ошибка оборачивается с сохранением `errors.Is`.

## Risks / Trade-offs

### [Риск] UTC-дата отличается от локальной даты пользователя у полуночи
**Митигация:** единая политика frontend/backend (уже закреплена в `clients-management`); расхождение ограничено ±1 днём и затрагивает только пограничные возраста и даты; сервер остаётся источником истины.

### [Риск] Исправление расширяет фактически принимаемый диапазон с 16–99 до 16–100
**Митигация:** это устранение дефекта (валидные по спеке клиенты с возрастом 100 перестают отклоняться), а не ослабление правила: младше 16 и старше 100 по-прежнему отклоняются. Контракт и статусы не меняются.

### [Trade-off] 29.02 — выбранное правило, а не выведенное из прежней спецификации
**Обоснование:** зафиксировано явно в спеке и покрыто тестами; сохраняет единую семантику с frontend.

## Migration Plan

Не применимо: миграции данных нет, контракт и зависимости не меняются, деплой обычный. **Rollback:** revert `api/internal/client/service.go` и удаление новых тестовых файлов; данные не затрагиваются.
