# Proposal

## Why

В панели нет фотографий товара, хотя API реализует весь контур работы с изображениями (`POST /api/v1/products/{id}/image`, `GET /api/v1/products/{id}/image`, `PUT /api/v1/images/{id}`, `DELETE /api/v1/images/{id}`), а ответы списка товаров уже содержат `image_id`, который панель не читает. Оператор выбирает товар исключительно по названию, категории, цене и остатку — в каталоге бытовой техники фото является основным признаком товара, и без него панель не позволяет полноценно работать с каталогом.

## What Changes

- `frontend/src/shared/api/client.ts` — общий HTTP-клиент получает поддержку бинарных операций: отправка тела-файла без `Content-Type: application/json` и чтение ответа как `Blob`. Текущий клиент всегда сериализует тело в JSON и всегда разбирает ответ как JSON, поэтому ни одна из существующих операций с изображениями через него невыполнима. Поведение JSON-запросов, разбор сообщения ошибки, обработка 401 и трактовка 204 остаются прежними и общими.
- `frontend/src/features/product-images/` — новый слой фичи: API-модуль изображений, хуки запроса и мутаций, компонент диалога фотографии товара.
- Страница `/products` — в меню действий строки товара появляется действие управления фотографией, открывающее диалог.
- Диалог фотографии — показывает текущее фото товара либо состояние «фото отсутствует», позволяет выбрать файл и предлагает действия в зависимости от наличия фотографии: пока фотографии нет, доступно только действие загрузки (`Upload photo`); когда фотография есть, доступны замена (`Replace photo`) и удаление (`Delete photo`), а действие загрузки скрыто, чтобы нельзя было загрузить второе изображение поверх существующего. Выбор файла остаётся доступным в обоих состояниях — выбранный файл нужен для замены.
- Фотография отображается через объектный URL (`URL.createObjectURL`) из загруженного `Blob`: API требует заголовок `Authorization: Bearer`, поэтому прямая ссылка `<img src="/api/v1/products/{id}/image">` не передаёт токен и не может использоваться. Объектный URL освобождается при закрытии диалога и при замене изображения, а изображение получает доступное имя, описывающее товар.
- Клиентская валидация зеркалит правила сервера: файл выбран, файл не пустой, размер не превышает 10 МиБ (`maxImageSize` в `api/internal/image/handler.go:13`). Сообщения сервера при 400, 404, 500 и сетевой ошибке отображаются дословно.
- Ключи локализации EN/RU для действий, диалога и сообщений.
- **Без изменений Go API, Java-сервиса и схемы БД.** Контракт используется ровно в том виде, в каком он объявлен в `api/docs/swagger.yaml`.

Изменение **не является BREAKING**: существующие страницы и операции не меняют поведение, а общий HTTP-клиент сохраняет прежнюю семантику для JSON-запросов.

## Capabilities

### New Capabilities
- `frontend/product-images`: управление фотографией товара в панели — загрузка, просмотр, замена и удаление фотографии, отображение результата, обработка ошибок и локализация. Набор действий в диалоге зависит от наличия фотографии: пока её нет, доступно только действие загрузки; когда фотография есть — замена и удаление, а действие загрузки скрыто.

### Modified Capabilities
- `frontend/products-management`: в меню действий строки товара добавляется действие управления фотографией, открывающее диалог работы с фотографией товара. Требования создания, удаления и уменьшения остатка товара не меняются.

## Impact

**Используемые API-эндпоинты** (контракт не меняется, перечислены как затрагиваемая поверхность):
- `GET /api/v1/products/{id}/image` — 200, `application/octet-stream`, тело изображения; 404 `image not found`; 400 `invalid product id`.
- `POST /api/v1/products/{id}/image` — 201, тело `{"id": "<image id>"}`; 400 `empty image`, `invalid product id`, `cannot read request body`; 404 `product not found`.
- `PUT /api/v1/images/{id}` — 204; 400 `empty image`, `invalid image id`; 404 `image not found`.
- `DELETE /api/v1/images/{id}` — 204; 400 `invalid image id`; 404 `image not found`.
- `GET /api/v1/products` — используется существующий список товаров, где поле `image_id` после загрузки фотографии становится заполненным.

**Код фронтенда:**
- `frontend/src/shared/api/client.ts` — бинарные запросы и ответы.
- `frontend/src/features/product-images/` — новый слой фичи.
- `frontend/src/pages/products/ProductsListPage.tsx` — действие в меню строки.
- `frontend/src/shared/i18n/locales/en/common.json`, `frontend/src/shared/i18n/locales/ru/common.json` — ключи локализации.
- `frontend/src/test/`, `frontend/e2e/` — тесты клиента, фичи и браузерный сценарий.

**Зависимости:** новых нет — используются уже подключённые React, TanStack Query, react-hook-form, zod и компоненты shadcn/ui (`Dialog`, `Button`, `Alert`).

**Не затрагивается:** Go API, Java auth service, схема БД, страницы клиентов и поставщиков, существующая семантика JSON-запросов общего клиента, архив завершённых изменений.

**Незавершённые вопросы контракта и аутентификации:**
- API не проверяет тип содержимого изображения и принимает произвольные байты, поэтому файл, не являющийся изображением, будет сохранён и показан как неотображаемый. Панель ограничивает выбор файла изображениями средствами элемента выбора файла, но не заявляет проверку типа как правило: правила сервера — только непустое тело и размер не более 10 МиБ.
- Превью фотографии в колонке таблицы товаров не реализуется: API не предоставляет пакетной выдачи изображений, поэтому такая колонка означала бы отдельный бинарный запрос на каждую строку списка. Фотография показывается в собственном контексте товара; вывод её в карточке товара относится к отдельному изменению.
- Загрузка, замена и удаление требуют `image_id` для замены и удаления: панель берёт его из `image_id` товара в ответе `GET /api/v1/products`, который backend заполняет транзакционно вместе с созданием изображения.
