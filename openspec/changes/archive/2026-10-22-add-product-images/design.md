# Design

## Context

См. `proposal.md` — Why.

Факты, определяющие подход:

- `frontend/src/shared/api/client.ts:77-89` — `buildHeaders()` всегда добавляет `Content-Type: application/json` и заголовок `Authorization: Bearer <token>` из `localStorage`.
- `frontend/src/shared/api/client.ts:118-146` — `request()`: при 401 вызывается `handleUnauthorized`, при неуспешном ответе тело разбирается как JSON ради поля `message`, ответ 204 трактуется как `undefined`, остальное всегда читается через `response.json()`.
- `frontend/src/shared/api/client.ts:148-178` — `apiClient` предоставляет `post`, `get`, `patch`, `delete`. Метода `put` нет, отправка бинарного тела невозможна, чтение ответа как `Blob` невозможно.
- `api/internal/image/handler.go:45-73, 88-115, 128-142, 156-172, 186-202` — пять операций: создание (201, `{"id": "<uuid>"}`), замена (204), удаление (204), чтение по `image_id` и чтение по `id` товара (200, `application/octet-stream`).
- `api/internal/image/handler.go:13` — `maxImageSize = 10 << 20` (10 МиБ); тело читается как есть, без проверки типа содержимого; пустое тело даёт 400 `empty image`; некорректный uuid — 400 `invalid product id` / `invalid image id`.
- `api/internal/image/errors.go` — 404 `image not found` и 404 `product not found`.
- `api/internal/product/dto.go:54-75` — `CreateResponse`, `FullResponse` и `ListResponse` содержат необязательное поле `image_id`.
- `frontend/src/pages/products/ProductsListPage.tsx:145-160` — меню действий строки товара: сейчас два пункта (уменьшить остаток, удалить); состояние диалогов страница держит в `useState` (`:174-176`).
- `frontend/src/pages/products/useProductMutations.ts:51-102` — принятый в проекте образец мутации: `useMutation`, `notifySuccess` при успехе, `invalidateQueries({ queryKey: PRODUCTS_QUERY_KEY })`.
- `frontend/src/app/providers.tsx` — `QueryClient` со `staleTime` 5 минут и `gcTime` 10 минут; глобальный обработчик 401 очищает кеш и перенаправляет на `/auth/login`.
- `frontend/src/pages/products/ProductsListPage.tsx:174-178` — страница хранит товар для открытого диалога снимком строки в `useState`, тогда как сама таблица рендерится из свежего `productsQuery.data` (`:226-231`); поэтому актуальный `image_id` диалог берёт из кеша списка, а не из снимка.
- `frontend/e2e/helpers.ts:33-39` — в `MockProduct` нет поля `image_id`, а ответ списка товаров в моке статичен; для браузерной проверки загрузки, замены и удаления мок изображений должен хранить состояние: до загрузки `GET /api/v1/products/{id}/image` отдаёт 404, после загрузки — 200 с телом, ответ списка содержит заполненный `image_id`, а удаление сбрасывает состояние.
- `frontend/src/features/` — в рабочем дереве есть пустые каталоги-заготовки (`auth`, `client-address`, `client-create`, `product-create`, `product-image`, `product-stock`, `supplier-address`, `supplier-create`), но они не отслеживаются git и в репозитории не входят; весь фичевый код сейчас живёт в `src/pages/**`.
- Токен хранится в `localStorage` и передаётся заголовком, cookie-сессии нет — поэтому прямая ссылка `<img src="/api/v1/products/{id}/image">` вернёт 401 и использовать её нельзя.

## Goals / Non-Goals

**Goals:**
- Научить общий HTTP-клиент работать с бинарными телами и ответами, не меняя поведение существующих JSON-операций.
- Дать оператору загрузить, посмотреть, заменить и удалить фотографию товара из панели.
- Показывать фотографию товара в его собственном контексте и освобождать ресурсы отображения корректно.
- Сохранить существующие соглашения проекта: один общий клиент, TanStack Query, `notifySuccess`, инвалидация кеша, EN/RU, серверные сообщения дословно.

**Non-Goals:**
- Превью фотографии в колонке таблицы товаров: API не отдаёт изображения пакетно, такая колонка означала бы отдельный бинарный запрос на каждую строку.
- Показ фотографии в карточке товара: карточка товара — отдельное изменение.
- Проверка типа содержимого изображения: API её не выполняет, и панель не заявляет правил, которых нет в контракте.
- Изменения Go API, Java auth service, схемы БД и сгенерированных типов: контракт используется в готовом виде.

## Decisions

### 1. Бинарная поддержка добавляется в общий HTTP-клиент

**Решение.** В `frontend/src/shared/api/client.ts` добавляются три метода: отправка бинарного тела методом `POST`, отправка бинарного тела методом `PUT` и чтение ответа как `Blob`. Внутренняя функция запроса получает способ чтения ответа и способ формирования тела, поэтому обработка 401, разбор сообщения ошибки, `ApiError`, `NetworkError` и трактовка 204 остаются общими и не дублируются.

**Обоснование.** Единый клиент — единственное место, где живут Bearer-заголовок, глобальное завершение сессии по 401 и правила разбора `ErrorResponse`. Отдельный клиент для изображений размёк бы контракт ошибок на две реализации.

**Альтернативы.**
- *Отдельный `imageClient`* — отклонено: дублирование 401, `ApiError` и разбора сообщений.
- *Один универсальный метод с флагом формата* — отклонено: сделает сигнатуру существующих JSON-вызовов неоднозначной; новые методы сохраняют типизацию и не затрагивают текущих вызывающих.

### 2. Тело файла отправляется как есть, с `Content-Type: application/octet-stream`

**Решение.** Бинарные запросы отправляют содержимое файла без преобразования и объявляют `application/octet-stream` — так, как объявлено в контракте (`@Accept octet-stream`).

**Обоснование.** Обработчик читает тело как есть и проверяет только, что оно непустое. `multipart/form-data` сервер не разбирает, а `application/json` для байтов неверен.

**Альтернативы.**
- *`multipart/form-data`* — отклонено: контракт не предусматривает разбор формы.
- *Отправка base64 в JSON* — отклонено: контракт ждёт байты, а кодирование раздувает объём примерно на треть.

### 3. Фотография отображается через объектный URL из `Blob`

**Решение.** Ответ `GET /api/v1/products/{id}/image` читается как `Blob`, кешируется TanStack Query, а компонент создаёт `URL.createObjectURL` и освобождает его при закрытии диалога и при замене изображения. Показанное изображение получает доступное имя, описывающее товар, и локализуется вместе с остальными текстами диалога.

**Обоснование.** Эндпоинт требует заголовок `Authorization`, поэтому `<img src>` на URL API не авторизуется и вернёт 401. Объектный URL дешёв, отзываем и не раздувает память, в отличие от `data:`-ссылки. Доступное имя нужно потому, что изображение — единственный новый визуальный элемент изменения, а `frontend/AGENTS.md` требует доступных контролов и семантической разметки.

**Альтернативы.**
- *`<img src="/api/v1/products/{id}/image">`* — отклонено: нет cookie-сессии, запрос уйдёт без токена.
- *`data:`-ссылка* — отклонено: base64 занимает примерно на треть больше и не освобождается отдельно.
- *Cookie-сессия на бэкенде* — отклонено: изменение бэкенда вне области.

### 4. Фотография живёт в диалоге товара, а не в колонке таблицы

**Решение.** Действие управления фотографией открывает диалог, который показывает фотографию, позволяет загрузить, заменить или удалить её. Таблица товаров остаётся без колонки изображения.

**Обоснование.** `GET /api/v1/products` отдаёт только `image_id`; байты требуют отдельного запроса на каждое изображение. Колонка означала бы отдельный бинарный запрос на каждую строку при каждом обновлении списка. Фронтенд подстраивается под форму API: фото показывается там, где оно запрошено явно.

**Альтернативы.**
- *Колонка с ленивой загрузкой превью* — отложено: возможна позже как отдельное улучшение, если API получит пакетную выдачу.
- *Отдельная страница галереи изображений* — отклонено: API не перечисляет изображения, и оператору нужна привязка к товару.

### 5. Загрузка идёт по `id` товара, замена и удаление — по актуальному `image_id` товара

**Решение.** Загрузка отправляет файл на `POST /api/v1/products/{id}/image`. Замена и удаление используют `image_id` товара **из актуальной строки списка**: `PUT /api/v1/images/{image_id}` и `DELETE /api/v1/images/{image_id}`. Страница передаёт диалогу `id` товара и имя для показа, а текущее значение `image_id` диалог берёт из кеша списка `["products"]`, который мутации инвалидируют.

**Обоснование.** API предлагает ровно эти два способа адресации, и `image_id` приходит в строке списка, поэтому дополнительный запрос за идентификатором не нужен. Значение должно быть актуальным: снимок строки, снятый в момент клика по действию, устаревает сразу после первой загрузки — сервер заполняет `image_id` транзакционно вместе с созданием изображения, — и замена с удалением остались бы недоступны у товара, только что получившего первую фотографию. Набор действий диалога зависит от наличия фотографии: пока фотографии нет, доступно только действие загрузки; когда фотография есть — только замена и удаление, а действие загрузки не отображается, чтобы повторная загрузка не создавала вторую запись изображения поверх существующей.

**Альтернативы.**
- *Всегда сначала `GET /api/v1/images/{id}`* — отклонено: лишний запрос перед каждым действием при уже известном `image_id`.
- *Замена через `POST` с повторной загрузкой* — отклонено: бэкенд не заменяет изображение при повторном POST, а создаёт новое; `PUT` выражает замену прямо.
- *Передавать снимок строки и обновлять его после инвалидации списка* — отклонено: добавляет состояние синхронизации между снимком и кешем; чтение актуального значения из кеша списка обходится без него.

### 6. Фича живёт в `src/features/product-images/`, список товаров — в своём слое

**Решение.** API-модуль изображений, хук запроса фотографии и хуки мутаций размещаются в `frontend/src/features/product-images/`. Страница списка товаров получает действие в меню строки и самостоятельное состояние открытого диалога.

**Обоснование.** `AGENTS.md` требует держать страницы, фичи, общий API-код и UI-компоненты раздельно — размещение фичи в `src/features/product-images/` следует этому требованию. Модель данных страницы (`image_id` в строке списка) остаётся в `src/pages/products/`, логика изображения — в слое фичи. Пустые каталоги-заготовки в `src/features/` не отслеживаются git и в репозиторий не входят, поэтому имя каталога выбрано по правилу проекта, а не по наличию готовой папки.

**Альтернативы.**
- *Всё в `src/pages/products/`* — отклонено: нарушает соглашение проекта о разделении страниц и фич.
- *Фича в `src/entities/product/`* — отклонено: `entities` описывает данные, а здесь есть действие пользователя над подресурсом.

### 7. Клиентская валидация повторяет только правила сервера

**Решение.** До отправки проверяется, что файл выбран, что он непустой и что его размер не превышает 10 МиБ. Проверка типа содержимого не вводится; элемент выбора файла лишь ограничивает выбор изображениями (`accept="image/*"`) как удобство интерфейса.

**Обоснование.** Сервер проверяет только непустое тело и предельный размер; тип содержимого он не проверяет. Панель не должна заявлять правил, которых нет в контракте, — иначе она отвергала бы файлы, которые сервер принял бы.

**Альтернативы.**
- *Список допустимых MIME-типов в панели* — отклонено: изобретение правила, которого нет в API.

### 8. Ошибки: сообщение сервера дословно, 404 при чтении — это «фото отсутствует»

**Решение.** Для операций загрузки, замены и удаления сообщение из поля `message` отображается дословно, а при его отсутствии — локализованный текст по образцу `resolveProductMutationError`. Ответ 401 завершает сессию глобальным обработчиком и не сопровождается сообщением в форме. Ответ 404 при чтении фотографии трактуется как отсутствие фотографии, а не как ошибка: сервер отвечает так, когда у товара нет изображения.

**Обоснование.** Семантика 404 при чтении задана сервером: `image not found` означает «изображения нет». Показывать при этом ошибку было бы неверно.

**Альтернативы.**
- *Показывать 404 при чтении как ошибку* — отклонено: ломает обычное состояние «у товара нет фото».

### 9. Ошибки разных операций диалога не смешиваются

**Решение.** Перед запуском операции диалог сбрасывает состояние ошибок только тех операций, которые уже завершились и сейчас не выполняются: `reset()` вызывается у остальных мутаций, но не у той, чьё состояние ещё активно, — выполняющаяся операция и существующая защита от параллельных действий (`isBusy`) не нарушаются. Сообщение об ошибке показывается только для операции, завершившейся неудачей.

**Обоснование.** Мутации загрузки, замены и удаления — независимые хуки со своими состояниями ошибки, а TanStack Query сбрасывает ошибку только при следующем вызове той же мутации, поэтому ошибка одной операции оставалась бы на экране после успеха другой и вводила в заблуждение. Сброс состояний в момент старта новой операции убирает устаревшее сообщение там же, где операция начинается, и не требует отдельного состояния диалога.

**Альтернативы.**
- *Отдельное состояние «последняя операция» в диалоге* — отклонено: его пришлось бы синхронизировать с тремя мутациями, тогда как сброс состояний решает задачу в той же точке, где операция начинается.
- *Скрывать сообщения об ошибках по времени их появления* — отклонено: время не является надёжным признаком операции.

## Risks / Trade-offs

- **[Risk] Изменение общего клиента затрагивает все существующие запросы** → бинарные возможности добавляются новыми методами, а поведение JSON-веток остаётся прежним; его защищают существующие 16 проверок `frontend/src/test/api-client.test.ts` и полный юнит-прогон.
- **[Risk] Утечка объектных URL** → URL освобождается при закрытии диалога и при замене изображения; сами `Blob` остаются в кеше запросов и освобождаются по `gcTime` кеша.
- **[Risk] API хранит произвольные байты, поэтому не-изображение будет сохранено и показано как неотображаемое** → элемент выбора файла ограничивает выбор изображениями, а ограничение API зафиксировано в предложении и не маскируется клиентской проверкой типа.
- **[Risk] Фотография не видна без открытия диалога** → оператор по-прежнему опознаёт товар по названию, категории, цене и остатку; показ фото в карточке товара запланирован отдельным изменением.
- **[Trade-off] Замена и удаление недоступны, пока у товара нет `image_id`** → состояние соответствует данным сервера: сначала фотография загружается, затем ей можно управлять.
- **[Risk] API допускает повторную загрузку поверх существующей фотографии: `POST` создаёт вторую запись `images`, а прежнее изображение остаётся в базе** → действие загрузки не отображается, когда фотография есть, поэтому из панели этот путь недоступен; контракт API не меняется, и прямое обращение к API по-прежнему создаст запись — это ограничение API, а не панели.

## Migration Plan

Миграций данных, новых маршрутов и изменений контракта нет; развёртывание обычное (`npm run build`). **Откат:** revert изменений `frontend/src/shared/api/client.ts`, каталога `frontend/src/features/product-images/`, `frontend/src/pages/products/ProductsListPage.tsx`, ключей локализации и связанных тестов.

## Open Questions

Открытых вопросов, способных изменить спецификации, подход или разбиение на задачи, нет. Отложенные и не влияющие на текущий объём: показ фотографии в карточке товара (отдельное изменение) и колонка с превью в таблице (отклонена до появления пакетной выдачи в API).
