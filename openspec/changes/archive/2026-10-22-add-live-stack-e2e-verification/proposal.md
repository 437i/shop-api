# Proposal

## Why

Все 503 unit-теста фронтенда и 41 e2e-тест работают с мокнутой API-границей: `frontend/e2e/helpers.ts` перехватывает `/api/v1/*` через `page.route()`, а vitest-тесты подменяют `fetch`. Реальный поток аутентификации (Java-сервис по gRPC), реальный Go API и реальные базы данных не проверялись из браузера ни разу, поэтому расхождение фронтенда с живым контрактом остаётся незаметным — при проверке изменения `document-admin-access-model` его пришлось подтверждать вручную. Нужен воспроизводимый, но строго опциональный способ прогнать ключевые сценарии против настоящего локального стенда.

## What Changes

- Появляется отдельный opt-in запуск `npm run test:e2e:live`: своя директория `frontend/e2e-live/`, свой конфиг `frontend/playwright.live.config.ts` и свой набор спек. Команды `npm run test` и `npm run test:e2e` не меняют поведения, а дефолтный `playwright.config.ts` (`testDir: "./e2e"`) не подхватывает живые спеки, поэтому в общий прогон они не попадают.
- Перед сценариями выполняется проверка готовности стенда: убеждаемся, что запущен ожидаемый локальный Compose-проект (сервисы `api`, `auth`, `postgres`, `auth-postgres`), Go API отвечает, а связка Go API → gRPC → Java auth работает. Признак готовности — `GET /api/v1/products` без токена возвращает **401** (сервис жив, цепочка gRPC работает), тогда как 502/503 или отказ соединения означают «стенд не готов» (коды ответа auth-цепочки — `api/internal/auth/errors.go:23, 33`). Дополнительно проверяется локальность адреса Go API: hostname должен быть loopback, а порт — совпадать с опубликованным портом локального сервиса `api`, иначе preflight прерывается до любых запросов и до создания тестовых данных.
- Тестовые данные получают префикс прогона (`e2e-live-<YYYYMMDDTHHMMSSZ>-<6 символов из [a-z0-9]>`): email тестового пользователя, имена клиента, поставщика и товара помечаются этим префиксом. Данные, созданные через Go API, удаляются через API в порядке **товар → клиент → поставщик**; тестовый пользователь удаляется из локальной `auth-postgres` только по совпадению префикса прогона. Очистка выполняется и при падении теста.
- Живой прогон **не входит** в общий CI-прогон и запускается только отдельной явной командой.
- Сброс пароля проверяется в той части, которую стенд действительно поддерживает: почтовой инфраструктуры в стеке нет, поэтому `POST /api/v1/reset` возвращает 204, а новый пароль публикуется в логах сервиса `auth` — проверяется 204, извлечение нового пароля из логов и вход с ним.
- **Запрещённые операции:** `docker compose down -v`, `docker volume rm`, `prune` и любые другие команды удаления постоянных данных. Прогон не управляет томами и не останавливает сервисы, которые сам не запускал.

## Capabilities

### New Capabilities

- Нет. Изменение относится к внутренней тестовой инфраструктуре и не меняет продуктовое поведение, поэтому в `.openspec.yaml` объявлен `skip_specs: true` и delta-спеки не создаются. Capability `frontend/live-verification` не создаётся: для описания самого тестового скрипта нормативные требования не нужны.

### Modified Capabilities

- Нет. Требования существующих capabilities не меняются, `openspec/specs/` не затрагивается.

## Impact

- **Код продукта:** не изменяется. Затрагиваются только тестовая инфраструктура и скрипты.
- **Фронтенд:** новые `frontend/e2e-live/` (живые спеки), `frontend/playwright.live.config.ts` (конфиг живого прогона), `frontend/src/test-support/live/` (переиспользуемые модули проверки готовности `stack-readiness.ts` и очистки `run-data.ts`) и `frontend/scripts/live-preflight.ts` (CLI-обёртка проверки готовности); в `frontend/package.json` добавляется один скрипт `test:e2e:live`. Побочный эффект: в стандартном прогоне vitest появятся чистые unit-тесты этих двух модулей — они не требуют ни Docker, ни сети, поэтому `npm run test` остаётся герметичным и быстрым.
- **Команды:** `npm run test`, `npm run test:e2e` и `npm run check` сохраняют текущее поведение; общий CI не меняется.
- **API:** новых, изменяемых и удаляемых endpoints нет — используется существующий контракт Go API.
- **Системы:** локальный Compose-стенд (`api`, `auth`, `postgres`, `auth-postgres`) используется в режиме чтения и записи тестовых данных; постоянные тома не затрагиваются.
- **Зависимости:** новых npm-пакетов нет — используются уже установленные `@playwright/test` и `vitest`.

## Существующие API endpoints, на которые опирается изменение

| Endpoint | Назначение в живом прогоне |
|---|---|
| `POST /api/v1/register` | Регистрация тестового пользователя через настоящий Java-сервис |
| `POST /api/v1/auth` | Вход и проверка нового пароля после сброса |
| `POST /api/v1/reset` | Сброс пароля; 204 без почтовой доставки |
| `GET /api/v1/products` | Проверка готовности (401 без токена) и работа со списком товаров |
| `POST /api/v1/products`, `DELETE /api/v1/products/{id}` | Создание и удаление тестового товара |
| `GET /api/v1/clients`, `POST /api/v1/clients`, `DELETE /api/v1/clients/{id}` | Создание и удаление тестового клиента |
| `GET /api/v1/suppliers`, `POST /api/v1/suppliers`, `DELETE /api/v1/suppliers/{id}` | Создание и удаление тестового поставщика |
| `POST /api/v1/products/{id}/image` | Не используется в этом изменении: живая проверка загрузки фотографии отложена (design.md, Open Questions) |

## Нерешённые вопросы контракта и аутентификации

1. **Удаление пользователя недоступно через API.** В proto и в Go API нет операции удаления пользователя, поэтому тестовая учётная запись чистится прямой выборкой из локальной `auth-postgres` по префиксу email прогона. Это осознанный обход API, допустимый только в локальном стенде и только для записей, созданных текущим прогоном.
2. **Сброс пароля не имеет почтовой доставки.** Сервис `auth` публикует новый пароль в своих логах, поэтому живая проверка сброса зависит от доступа к `docker compose logs auth` и подтверждает только поддерживаемую стендом часть: 204, новый пароль в логах и вход с ним.
3. **Модель доступа на backend отсутствует и этим изменением не проверяется.** Ролей и проверок прав нет ни в Go API, ни в Java-сервисе, поэтому живой прогон подтверждает лишь то, что любой зарегистрированный пользователь получает административный доступ, — и не может подтвердить никаких гарантий разграничения прав. Изменение модели доступа вынесено в отдельную работу.
