# Design

## Context

Мотивация — в `proposal.md` (раздел Why). Здесь только текущее состояние и ограничения, определяющие подход.

**Как устроены существующие e2e-тесты и почему они не покрывают живой стенд:**

- `frontend/playwright.config.ts`: `testDir: "./e2e"`, `baseURL: "http://127.0.0.1:5173"`, `webServer: npm run dev`.
- `frontend/e2e/helpers.ts` (676 строк) перехватывает через `page.route()` все endpoints, которыми пользуются спеки: `/api/v1/auth`, `/api/v1/register`, `/api/v1/reset`, `/api/v1/change`, `/api/v1/clients`, `/api/v1/suppliers`, `/api/v1/products`, `/api/v1/images`. Токен — константа `MOCK_TOKEN = "mock-access-token"`.
- Vitest-тесты перехватывают `fetch`/`apiClient` на уровне модуля.

**Что доступно на живом стенде (проверено на текущем запущенном стенде):**

```
  vite dev :5173 ──proxy /api/v1──> Go API :8080 ──gRPC ValidateToken──> Java auth :50051
       │                                 │                                      │
       │ и /api/v1 → :8080               │                                      └──> auth-postgres
       └── служит SPA                    └──> postgres (products, clients, suppliers, images, categories)
```
- Проксирование задано в `frontend/vite.config.ts:23-27` (`"/api/v1" → http://127.0.0.1:8080`), поэтому отдельная конфигурация фронтенда для живого прогона не нужна.
- Compose: `api` (порт 8080, healthcheck `wget … /swagger/index.html`, `docker-compose.yml:106`), `auth` (gRPC 50051, healthcheck `bash -c '</dev/tcp/127.0.0.1/50051'`, `docker-compose.yml:245`), `postgres` (`pg_isready`, `:15`), `auth-postgres` (`pg_isready`, `:219`), `nginx` (:80/:443, отдаёт `frontend/dist`).
- Постоянные тома: `postgres_data`, `pgadmin_data`, `auth_postgres_data` (`docker-compose.yml:257-260`) — неприкосновенны.
- Контейнеры БД имеют фиксированные имена `be3-postgres` и `be3-auth-postgres`; учётные данные передаются в контейнер через переменные `POSTGRES_USER`/`POSTGRES_DB` (`docker-compose.yml:208-215`), поэтому `psql` можно вызвать изнутри контейнера, не читая `.env` и не печатая секреты: `docker compose exec -T auth-postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" …'` (проверено: команда отрабатывает).
- Таблица пользователей auth-сервиса — `users` (`service_auth/.../entity/UserEntity.java:9`), колонка `email`.

**Ограничения контракта, влияющие на тестовые данные:**

- Java-сервис валидирует регистрацию: email по шаблону `*@*.ru|*@*.com` и короче 50 символов, пароль длиннее 5 и не длиннее 72 байт, имя и фамилия — только буквы, телефон по шаблону `+7-XXX-XXX-XX-XX` (`service_auth/.../grpc_service/GrpcServiceAuthImpl.java:26-80`).
- Удаления пользователя нет ни в proto, ни в Go API.
- Почтовой инфраструктуры в стенде нет. Сброс пароля генерирует новый случайный пароль и публикует его в логах сервиса `auth`: `PASSWORD RESET SUCCESS for user: <email>` и `New password: <12 символов>` (`service_auth/.../security/PasswordResetService.java:36-40`). Проверено на живом стенде: `POST /api/v1/reset` → 204, пароль извлекается из `docker compose logs auth`, вход с ним → 200.
- `DELETE /suppliers/{id}` отклоняет удаление, пока на поставщика ссылается товар, — порядок очистки обязан быть «товар → клиент → поставщик».

## Goals / Non-Goals

**Goals:**
- Дать воспроизводимую проверку ключевых сценариев панели против настоящего стенда: браузер → Go API → Java auth → базы данных.
- Гарантировать, что обычные команды тестирования не меняют поведения и живые спеки не попадают в общий прогон.
- Сделать подготовку и очистку тестовых данных детерминированными и безопасными для постоянных данных.
- Дать actionable-диагностику, когда стенд не готов: прогон не должен падать на «неожиданном» 401 или таймауте.

**Non-Goals:**
- Не менять продуктовый код, Go API, Java-сервис, контракт и main specs.
- Не включать живой прогон в общий CI и не добавлять его в `npm run check`.
- Не проверять модель доступа на backend: ролей и проверок прав не существует, живой прогон подтверждает лишь отсутствие разграничения, но не какие-либо гарантии.
- Не реализовывать сценарии, поддержка которых в стенде отсутствует (доставка письма со ссылкой сброса, отзыв токена).
- Не управлять жизненным циклом стенда: скрипт не поднимает и не останавливает сервисы.

## Decisions

### 1. Отдельные каталог и конфиг Playwright вместо второго проекта в существующем конфиге

**Решение.** Живые спеки живут в `frontend/e2e-live/`, конфиг — `frontend/playwright.live.config.ts` с `testDir: "./e2e-live"`.

**Обоснование.** `playwright.config.ts` задаёт `testDir: "./e2e"`, поэтому спеки из `e2e-live/` в него физически не попадают: общий `npm run test:e2e` не может их собрать даже при ошибочном запуске. Конфиг живой проверки переиспользует тот же `webServer: npm run dev` (dev-сервер уже проксирует `/api/v1` на живой Go API) и тот же `baseURL: 127.0.0.1:5173`, но задаёт `workers: 1`: сценарии работают с общей базой и должны идти последовательно.

**Альтернативы.**
- *Второй проект в `playwright.config.ts` с `testMatch`-фильтром* — отклонено: фильтр пришлось бы поддерживать вручную, и при его ослаблении живые спеки попали бы в общий прогон.
- *Отдельная папка с собственным `package.json`* — отклонено: дублирование зависимостей и конфигурации без выигрыша.

### 2. Отдельный npm-скрипт, стандартные команды не меняются

**Решение.** В `frontend/package.json` добавляется один скрипт `test:e2e:live`. `test`, `test:e2e`, `check` остаются в текущем виде.

**Обоснование.** Требование владельца: существующие команды не должны менять поведение. Отдельный скрипт делает живой прогон явно opt-in и не требует ни флага, ни переменной окружения в привычных командах.

**Альтернативы.**
- *Флаг `--grep @live` в общем `playwright test`* — отклонено: меняет поведение `npm run test:e2e` (например, случайный прогон с `--grep` начал бы поднимать стенд).
- *Переменная окружения `E2E_LIVE=1` в общем скрипте* — отклонено по той же причине: поведение существующей команды стало бы зависеть от окружения.

### 3. Проверка готовности — общий модуль, вызываемый и из CLI, и из `globalSetup`

**Решение.** Логика проверки живёт в переиспользуемом модуле `frontend/src/test-support/live/stack-readiness.ts` с экспортируемой функцией проверки. Её вызывают: отдельный CLI-скрипт `frontend/scripts/live-preflight.ts` (ручная проверка готовности без прогона тестов) и `globalSetup` живого Playwright-конфига (гарантия, что проверка всегда выполняется до сценариев).

**Обоснование.** Проверка должна выполняться всегда — иначе сценарии падали бы с невнятными симптомами. При этом её полезно запускать отдельно: «готов ли мой стенд?» — частый вопрос, и он не должен требовать прогона тестов. Через `globalSetup` проверка не обходится: Playwright не запустит спеки, если `globalSetup` завершился с ошибкой.

**Расположение файлов.** Модуль лежит в `src/`, а не в `scripts/`, потому что `tsconfig.app.json` включает только `src` (`include: ["src"]`), а `vite.config.ts` собирает vitest-тесты только из `src/**` — модуль вне `src/` не был бы ни типизирован, ни покрыт unit-тестами. Существующие `e2e/` и `playwright.config.ts` не входят ни в один tsconfig-проект, поэтому живые спеки и конфиг следуют тому же режиму: eslint без `tsc`. Изменять `tsconfig.*` нельзя — это изменило бы поведение `npm run typecheck` и `npm run check`.

**Альтернативы.**
- *Только `globalSetup`* — отклонено: нельзя быстро проверить готовность без прогона.
- *Только отдельный CLI, вызываемый из npm-скрипта* — отклонено: обход через прямой запуск Playwright оставил бы сценарии без проверки.

**Состав проверки (порядок от дешёвых к дорогим; блокирующими являются пункты 1–4 и 6, пункт 5 — справочный):**
1. Локальность адреса Go API: hostname должен быть loopback (`127.0.0.1`, `localhost`, `::1`), а порт — совпадать с опубликованным портом локального Compose-сервиса `api` (в текущей конфигурации — 8080). Проверка выполняется **до** HTTP-проб: при нелокальном адресе или неверном порте preflight завершается с понятной ошибкой, не отправляя запросы по указанному адресу и не создавая тестовых данных.
2. Ожидаемый локальный Compose-проект: `docker compose ps` показывает запущенными `api`, `auth`, `postgres`, `auth-postgres`; проверяются имена контейнеров `be3-postgres` и `be3-auth-postgres`. Если сервисы не те или стенд не запущен — отказ с указанием команды запуска. Это защита от прогона против внешнего или production-окружения.
3. Доступность Go API: `GET http://127.0.0.1:8080/swagger/index.html` → 200 (та же проверка, что в healthcheck `docker-compose.yml:106`).
4. Живая цепочка авторизации: `GET http://127.0.0.1:8080/api/v1/products` без токена → **401**. 401 означает, что Go API жив и gRPC до Java auth работает. Иначе middleware отдаёт код из `api/internal/auth/errors.go`: **503** «auth service unavailable» при недоступном или зависшем auth-сервисе (`codes.Unavailable` и `codes.DeadlineExceeded`, `api/internal/auth/grpc_client.go:41-42`) и **502** «auth service error» при прочих ошибках gRPC (`grpc_client.go:29, 44`); ветка обработки — `api/internal/auth/middleware.go:36-42`. И 502/503, и отказ соединения означают, что auth-сервис недоступен, — это отдельная диагностика, а не «стенд не готов».
5. Отсутствие сбойных HTTP-ответов от сервиса `auth` в последних логах — необязательная подсказка при сбое, не блокирующая проверка.
6. Отчёт об оставшихся записях: выборка из локальной `auth-postgres` по общему префиксу `e2e-live-` (то есть записи любых прогонов) — остатки прерванных прогонов должны быть видны оператору до начала сценариев; сама очистка при этом использует точный префикс текущего прогона.

**Параметризация и тестируемость.** Модуль принимает адрес Go API параметром (по умолчанию `http://127.0.0.1:8080`): это позволяет проверять ветку отказа на **недоступном опубликованном** порту (сервис `api` не отвечает), не останавливая стенд; адрес с другим портом отклоняется проверкой локальности (пункт 1 перечня проверок) ещё до HTTP-проб. Параметр не отменяет ограничения локальности: адрес должен указывать на loopback, а порт — совпадать с опубликованным портом локального сервиса `api`, иначе прогон прерывается до любых запросов и до создания тестовых данных. Сбор сырых результатов (вывод `docker compose ps`, HTTP-ответы) отделён от чистой классификации исходов: unit-тест проверяет только классификацию на подставленных результатах и не требует ни Docker, ни сети, поэтому стандартный `npm run test` остаётся герметичным.

### 4. Префикс прогона и именование тестовых данных

**Решение.** Префикс прогона формируется как `e2e-live-<YYYYMMDDTHHMMSSZ>-<6 символов из [a-z0-9]>` — метка времени фиксирована в формате `YYYYMMDDTHHMMSSZ` (16 символов), поэтому длина префикса всегда 32 символа (например, `e2e-live-20261022T160000Z-a1b2c3`), а длина email — всегда 44 символа; префикс передаётся в спеки через переменную окружения `E2E_LIVE_RUNID`. Email тестового пользователя — `<префикс>@example.com` (например, `e2e-live-20261022T160000Z-a1b2c3@example.com`, 44 символа): длина укладывается в ограничения клиентской схемы (не больше 49 символов) и Java-сервиса (`< 50`), домен `.com` проходит оба regex. Имена клиента, поставщика и товара создаются через Go API с тем же префиксом — их DTO ограничивают только длиной в 255 символов, без ограничения алфавита. Имя и фамилия регистрируемого пользователя префикс **не** получают: и клиентская схема (`NAME_PATTERN = /^[А-Яа-яЁёA-Za-z]+$/`, до 29 символов), и Java-сервис (`NAME_REGEX`, до 30 символов) принимают только буквы, поэтому для них задаются отдельные буквенные значения без пробелов и цифр (например, имя `Live` и фамилия `Probe`). Телефон задаётся по шаблону `+7-XXX-XXX-XX-XX`; фиксированное значение допустимо, поскольку уникальность проверяется только по email.

**Обоснование.** Единый префикс даёт три свойства: тестовые данные однозначно отличимы от пользовательских; очистка может искать их по префиксу; два параллельных прогона не пересекаются. Формат email выбран так, чтобы проходить валидацию клиентской схемы и Java-сервиса без исключений, а длина в 44 символа укладывается в их ограничения. Случайная часть берётся из `[a-z0-9]`, чтобы в префиксе не оказалось символов, специальных для `LIKE` (`%` и `_`): иначе выборка по префиксу могла бы захватить чужой прогон.

**Альтернативы.**
- *Фиксированная учётная запись, переиспользуемая между прогонами* — отклонено: сброс пароля в одном прогоне ломает следующий, а накопление состояния делает прогоны невоспроизводимыми.
- *UUID-идентификаторы сущностей вместо префикса в именах* — отклонено: идентификаторы назначает сервер, а префикс в имени нужен и для читаемости, и для очистки по имени.

### 5. Очистка: два механизма, по владельцу данных, с гарантией выполнения при сбое

**Решение.**
- Сущности, созданные через Go API (товар, клиент, поставщик), удаляются **через Go API** в порядке **товар → клиент → поставщик** (иначе удаление поставщика отклоняется, пока на него ссылается товар).
- Тестовый пользователь удаляется из локальной `auth-postgres` прямой выборкой по точному префиксу текущего прогона: `DELETE FROM users WHERE email ILIKE '<префикс прогона>%'` (например, `e2e-live-20261022T160000Z-a1b2c3%`). Сравнение регистронезависимое, потому что Go API приводит email к нижнему регистру (`api/internal/auth/dto.go`, `normalizeEmail`), и учётная запись хранится в нижнем регистре. Команда выполняется через `docker compose exec -T auth-postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" …'`, поэтому учётные данные не появляются ни в репозитории, ни в командной строке, ни в выводе.
- Очистка регистрируется в `globalTeardown` живого конфига, поэтому выполняется и при падении сценария, и при прерывании прогона. Операции идемпотентны: удаление отсутствующей записи не является ошибкой.
- Очистка затрагивает только записи текущего прогона: чужие строки с другим префиксом и любые пользовательские данные не трогаются.

**Расположение файлов.** Логика прогона и очистки живёт в `frontend/src/test-support/live/run-data.ts` (префикс прогона, именование, порядок и команды очистки) и покрывается unit-тестами в том же каталоге: `npm run test` подхватывает `src/**/*.{test,spec}.*` (`vite.config.ts`). Очистка удаляет данные, поэтому её логика обязана быть проверена автотестом, а не только ручным прогоном. Побочный эффект: в стандартном прогоне vitest появляется несколько чистых unit-тестов — они не требуют ни Docker, ни сети, поэтому `npm run test` остаётся герметичным и быстрым.

**Обоснование.** Удаление пользователя через API невозможно, а обход API в других местах не нужен: всё, что создано через Go API, удаляется через него же. Выборка по префиксу ограничивает обход API минимальным, предсказуемым набором строк.

**Альтернативы.**
- *Удалять всех пользователей с префиксом `e2e-live-%` (не только текущего прогона)* — отклонено: это затрагивает данные других прогонов и нарушает требование «очищать только данные этого запуска».
- *Оставлять тестового пользователя и удалять его вручную* — отклонено: накопление мусора в постоянном томе `auth_postgres_data` противоречит требованию детерминированной очистки.

**Запрещённые операции (жёстко):** `docker compose down -v`, `docker volume rm`, `docker compose down`, `docker system prune` и любое другое удаление постоянных данных или томов. Прогон не останавливает сервисы, которые сам не запускал.

### 6. Набор живых сценариев

**Решение.** Живой прогон покрывает пять сквозных сценариев, опираясь на наблюдаемое поведение, зафиксированное в `frontend/admin-access-model`:

| # | Сценарий | Что доказывает |
|---|---|---|
| S1 | Регистрация и вход через UI формы против настоящего Java-сервиса; токен сохраняется, защищённая страница открывается | Формат регистрации и выпуск JWT совпадают с контрактом; панель принимает настоящий токен |
| S2 | Недействительный токен в `localStorage`: раздел открывается по факту наличия токена, затем 401 сервера завершает сессию и происходит переход на `/auth/login` | Панель не анализирует токен, валидность определяет сервер — ровно как зафиксировано в capability `frontend/admin-access-model` |
| S3 | Наблюдение сетевых запросов панели: нет обращений к профилю/правам, у защищённых запросов есть `Authorization: Bearer` | Панель не запрашивает сведения о пользователе |
| S4 | Созданные через API поставщик, товар и клиент появляются в соответствующих списках UI, в строке товара доступны действия | Контракт списков и DTO совпадают с тем, что панель ожидает |
| S5 | Сброс пароля: 204, новый пароль из логов `auth`, вход с ним | Стенд не имеет почты — проверяется поддерживаемая часть пути |

**Обоснование.** S1–S3 закрывают то, что мокнутые e2e-тесты принципиально не проверяют: соответствие настоящих ответов сервисов ожиданиям панели. S4 проверяет, что панель корректно читает реальные DTO. S5 фиксирует отличие стенда от production: пароль приходит не письмом, а в логах сервиса.

**Альтернативы.**
- *Только проверка готовности без сценариев (health-check)* — отклонено: не проверяет путь браузер → Go API → Java auth, ради которого затевался прогон.
- *Проверка только входа, без CRUD* — отклонено: расхождение в DTO списков — самая частая причина поломки панели после изменений бэкенда.

### 7. Сценарий сброса пароля читает логи сервиса `auth`

**Решение.** Сценарий S5 получает новый пароль из вывода `docker compose logs auth` по шаблону `New password: <значение>` и входит с ним. Берётся **последняя** запись `New password:`, появившаяся после запроса сброса: лог контейнера накапливается и сохраняет пароли прошлых прогонов, поэтому более ранняя запись дала бы устаревший пароль и недетерминированный сбой сценария. Запись ищется **только в той части лога, которая появилась после запроса сброса** (объём лога до запроса фиксируется заранее): ограничение по числу строк не используется, поэтому результат не зависит от количества старых записей в логе. Полный лог auth-сервиса и сами пароли в пользовательский вывод не печатаются.

**Обоснование.** Почтовой инфраструктуры в стенде нет, а именно это и делает путь сброса в стенде непохожим на production. Проверка «только поддерживаемой части» означает: 204, пароль в логах, успешный вход. Никакой имитации письма не вводится.

**Альтернативы.**
- *Пропустить сброс в живом прогоне* — отклонено: тогда путь сброса останется непроверенным нигде.
- *Считать ссылку из лога* — отклонено: сервис не генерирует ссылку, а меняет пароль и публикует новый (`PasswordResetService.java:31-40`), и это подтверждено на живом стенде.

## Risks / Trade-offs

- **[Risk] Живой прогон пишет в локальные базы данных, то есть в постоянные тома.** → Mitigation: все создаваемые данные помечены префиксом прогона и удаляются детерминированно — через API для сущностей и точечной выборкой по префиксу для пользователя; очистка зарегистрирована в `globalTeardown` и выполняется даже при сбое; постоянные тома не затрагиваются никакими командами.
- **[Risk] Прогон прерван до регистрации очистки (например, принудительное завершение процесса) — данные останутся.** → Mitigation: префиксное именование делает остатки заметными: проверка готовности сообщает о записях с общим префиксом `e2e-live-` (то есть записи любых прогонов), найденных в локальной `auth-postgres`, чтобы оператор увидел и удалил их вручную; сама очистка использует точный префикс текущего прогона. Массовое удаление по общему префиксу намеренно не выполняется, чтобы не затронуть чужие прогоны.
- **[Risk] Проверка готовности пройдена, но стенд находится не в том окружении (внешний или production-хост).** → Mitigation: проверка требует именно локальный Compose-проект с контейнерами `be3-postgres` и `be3-auth-postgres`, а адрес Go API — loopback-хост и порт, совпадающий с опубликованным портом локального сервиса `api` (в текущей конфигурации — 8080); несоответствие обнаруживается до HTTP-проб, поэтому запросы по указанному адресу не отправляются, а прогон прерывается до создания данных.
- **[Trade-off] Живой прогон не входит в CI, поэтому регрессии живой связки не ловятся автоматически.** → Это осознанное решение: стенд требует Docker и локальные тома. Включение в CI или ночной запуск — отдельное решение, не влияющее на подход; автоматизация потребует отдельного окружения.
- **[Trade-off] Очистка тестового пользователя обходит API и обращается к базе напрямую.** → Осознанный компромисс: удаления пользователя в API нет, а обход применяется только к локальной `auth-postgres` текущего Compose-проекта и только к строкам текущего прогона.
- **[Risk] Сценарии зависят от данных, оставшихся в локальной БД (например, товаров от других прогонов).** → Mitigation: сценарии не полагаются на пустоту списков: проверяется наличие созданных прогоном сущностей по уникальному префиксу, а не общее число строк.
- **[Risk] Сброс пароля меняет пароль тестового пользователя, и следующий прогон с тем же email не сможет войти.** → Mitigation: каждый прогон использует новый префикс прогона, а email включает его; повторное использование email не предусмотрено.

## Migration Plan

Изменение аддитивное и не разворачивается: новые файлы `frontend/e2e-live/`, `frontend/playwright.live.config.ts`, `frontend/src/test-support/live/`, `frontend/scripts/live-preflight.ts` и один новый ключ в `frontend/package.json`. Откат — удаление этих файлов и ключа скрипта; существующие команды и артефакты не меняются.
