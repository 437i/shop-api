# Proposal

## Why

Аудит архивированного изменения `user-auth-management` (2026-10-21) зафиксировал дефект OS-001: на странице `/auth/reset` ссылка «Вернуться ко входу» находится внутри формы, поэтому после успешного сброса пароля (`isReset === true`) она исчезает, и на странице не остаётся ни одной ссылки — только два текста о новом пароле (`frontend/src/pages/auth/ResetPasswordPage.tsx:59-66` против `:102-107`). Это прямое расхождение с действующим требованием основной спецификации «Переходы между экранами аутентификации → Сценарий: Возврат к входу» (`openspec/specs/frontend/user-authentication/spec.md:230-232`): находясь на `/auth/reset`, система обязана отображать ссылку обратно на `/auth/login`, а состояние успеха — это всё ещё состояние той же страницы. Дефект бьёт ровно в тот момент, когда ссылка нужнее всего: после сброса пользователь должен уйти на `/auth/login` и войти с новым паролем из лога сервиса авторизации.

## What Changes

- `frontend/src/pages/auth/ResetPasswordPage.tsx` — ссылка «Вернуться ко входу» (`auth.links.toLogin`) рендерится в обоих состояниях страницы: в состоянии формы (как сейчас) и в состоянии успешного сброса. Оба текущих сообщения (`auth.reset.success` и `auth.reset.successWarning`) сохраняются без изменений.
- `frontend/src/test/reset-password-page.test.tsx` — регрессионный тест: после успешного ответа 204 на странице присутствует ссылка «Back to sign in», и переход по ней открывает `/auth/login`. Существующая проверка, что после успеха кнопка отправки исчезает, сохраняется.
- `frontend/e2e/auth.spec.ts` — e2e-сценарий состояния успешного сброса: после ответа 204 видны оба сообщения о новом пароле и ссылка «Back to sign in», переход по ссылке открывает `/auth/login`; в том же сценарии проверяется, что неявная отправка формы по Enter в поле email не сломалась. Существующие e2e-сценарии, включая переход из состояния формы, не меняются.
- Навигация выполняется существующим способом проекта — компонентом `Link` из `react-router` с классами `buttonVariants` (как на странице входа и странице регистрации), поэтому ссылка остаётся настоящей ссылкой с ролью `link` и работает с клавиатуры.
- Локализация не меняется: используется уже существующий ключ `auth.links.toLogin` с переводами `Back to sign in` / `Вернуться ко входу`.

Изменение **не является BREAKING**: HTTP-контракт, Go API, Java auth service и поведение сброса пароля не затрагиваются.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

Нет. Требование, которому соответствует исправление, уже существует в основной спецификации: «Переходы между экранами аутентификации → Сценарий: Возврат к входу» (`openspec/specs/frontend/user-authentication/spec.md:230-232`) формулирует условие без ограничения по состоянию страницы и потому уже описывает ожидаемое поведение. Изменение не меняет и не уточняет продуктовое поведение — оно приводит реализацию в соответствие с действующим требованием и закрывает регрессию тестом. Поэтому в `.openspec.yaml` установлен `skip_specs: true`, а файл дельт не создаётся: формулировать новую требования только ради валидации нельзя.

## Impact

**Код фронтенда:**
- `frontend/src/pages/auth/ResetPasswordPage.tsx` — перенос ссылки «Вернуться ко входу» за пределы условного рендеринга формы.
- `frontend/src/test/reset-password-page.test.tsx` — регрессионный тест наличия ссылки и перехода по ней после успешного сброса.
- `frontend/e2e/auth.spec.ts` — новый сценарий состояния успешного сброса в браузере и проверка неявной отправки формы по Enter.

**Используемые API-эндпоинты** (контракт не меняется; перечислены как затрагиваемая поверхность):
- `POST /api/v1/reset` — сброс пароля, 204 без тела. Механика запроса и обработки ответа не меняется.

**Основные спецификации:** `openspec/specs/` не затрагиваются — изменение приводит код в соответствие с уже опубликованным требованием, новая capability не создаётся.

**Зависимости:** новых нет — `react-router` и компонент `buttonVariants` уже используются на соседних auth-страницах.

**Не затрагивается:** Go API, Java auth service, схема БД, страница регистрации и страница входа, ключи локализации, остальные e2e-файлы, архив `openspec/changes/archive/2026-10-21-user-auth-management/`.

**E2e-тесты:** изменяется только `frontend/e2e/auth.spec.ts` — в него добавляется сценарий состояния успешного сброса. Существующие e2e-сценарии, включая переход `/auth/reset` → `/auth/login` из состояния формы, не меняются и должны остаться зелёными.

**Незавершённые вопросы контракта и аутентификации:**
- Считать ли состояние успеха отдельным экраном, на котором ссылка на вход не обязательна? Нет: требование сформулировано для страницы `/auth/reset` без ограничения по состоянию, а состояние успеха — это состояние той же страницы. Альтернатива (уточнить требование отдельной строкой «в том числе после успешного сброса») отклонена: она пересказала бы уже действующее требование и породила лишнюю дельту; фиксирующая регрессионная проверка делает трактовку явной без изменения спецификации.
- Должна ли страница после успеха позволять отправить сброс повторно? Требования этого не требуют, продуктового решения по этому поводу в проекте нет; вопрос вынесен за рамки исправления и не меняет текущее поведение.
- Остальные замечания аудита (OS-002 — неточный пример email в `design.md`, OS-003 — расхождение формулировки 409 в `proposal.md`, OS-004 — ссылки на строки в задаче 1.3) относятся к документации архивного изменения и к продуктовому поведению не имеют; они не входят в это изменение и требуют отдельного решения.
