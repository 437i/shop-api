# Design

## Context

См. `proposal.md` — Why.

Факты, определяющие подход:

- `frontend/src/pages/auth/ResetPasswordPage.tsx:58-110` — `CardContent` содержит условный блок: при `isReset === true` рендерится `<div className="grid gap-3">` с двумя текстами (`:60-65`), иначе — `<form className="grid gap-4">` с полем email, блоком ошибки, кнопкой отправки и ссылкой «Вернуться ко входу» (`:67-108`). Ссылка находится **внутри** формы, поэтому в состоянии успеха исчезает вместе с формой.
- `frontend/src/pages/auth/ResetPasswordPage.tsx:102-107` — ссылка реализована как `<Link className={buttonVariants({ variant: "link", size: "xs" })} to="/auth/login">` из `react-router`. Этот же приём применён на странице входа (`LoginPage.tsx:162-173`) и странице регистрации (`RegisterPage.tsx:158-163`).
- `frontend/src/components/ui/button.tsx:40-53` — `Button` — обёртка над Base UI `Button`; `buttonVariants` экспортируется отдельно и применяется к обычным ссылкам. Компонент `Button` с `render={<Link…/>}` в проекте не используется: Base UI при `nativeButton` по умолчанию выдаёт предупреждение о потере нативной семантики, а при `nativeButton={false}` ставит на элемент `role="button"`, из-за чего ссылка перестаёт быть ссылкой для скринридера и для `getByRole("link")` в тестах. `render={<Link…/>}` встречается в проекте только в `SidebarMenuButton` (`frontend/src/app/AdminLayout.tsx:64,73,82`), который построен на `useRender` и `role="button"` не добавляет, — то есть этим путём ссылка не ломается.
- `frontend/src/pages/auth/ResetPasswordPage.tsx:24` — состояние `isReset` в локальном `useState`, переключается в `onSuccess` мутации `useResetPassword` (`:47-49`); форма при этом размонтируется.
- `openspec/specs/frontend/user-authentication/spec.md:230-232` — требование «Переходы между экранами аутентификации → Сценарий: Возврат к входу»: «WHEN пользователь находится на странице `/auth/register` или `/auth/reset` THEN система отображает ссылку обратно на `/auth/login`». Условие не привязано к состоянию страницы, поэтому ожидаемое поведение уже описано действующей спецификацией.
- `frontend/src/test/reset-password-page.test.tsx:31-47` — `renderResetPasswordPage()` поднимает `createMemoryRouter` с маршрутами `/auth/reset` и `/clients` и возвращает роутер; маршрута `/auth/login` в тестовом роутере нет.
- `frontend/src/test/reset-password-page.test.tsx:101-120` — существующая проверка после успеха убеждается, что оба текста показаны, а кнопка отправки исчезла; наличие ссылки не проверяется.
- `frontend/e2e/helpers.ts:239-245` — мок `POST /api/v1/reset` отвечает `204`, поэтому состояние успеха воспроизводится в e2e без бэкенда; `frontend/e2e/auth.spec.ts:140-152` уже проверяет переход `/auth/reset` → `/auth/login` из состояния формы.

## Goals / Non-Goals

**Goals:**
- Ссылка «Вернуться ко входу» присутствует на `/auth/reset` в обоих состояниях страницы: до отправки формы и после успешного сброса.
- Переход по ссылке открывает `/auth/login` в обоих состояниях.
- Внешний вид страницы не меняется: расстояния между элементами остаются прежними.
- Регрессия ловится автоматически: юнит-тест страницы и e2e-сценарий.

**Non-Goals:**
- Требования, спецификации и основные файлы `openspec/specs/` не меняются: исправление приводит реализацию в соответствие с уже действующим требованием.
- Поведение запроса `POST /api/v1/reset`, обработка 204, тексты `auth.reset.success` и `auth.reset.successWarning` не меняются.
- Go API, Java auth service, схема БД и ключи локализации не затрагиваются.
- Возможность отправить сброс повторно после успеха не добавляется — требования этого не требуют, продуктового решения по этому поводу в проекте нет.
- Другие замечания аудита (`user-auth-management`: OS-002, OS-003, OS-004) в это изменение не входят: они касаются текста архивных артефактов и не влияют на поведение.

## Decisions

### 1. Ссылка рендерится один раз, вне условного блока состояния

**Решение.** В `ResetPasswordPage.tsx` содержимое `CardContent` оборачивается в `<div className="grid gap-4">`, внутри которого стоит условный блок (сообщения об успехе либо форма) и, после него, единственный экземпляр ссылки `<Link className={buttonVariants({ variant: "link", size: "xs" })} to="/auth/login">{t("auth.links.toLogin")}</Link>`.

**Обоснование.** Источник истины для ссылки — один, поэтому она не может «потеряться» в новом состоянии: добавление состояния страницы не потребует править ссылку. Обёртка `grid gap-4` сохраняет текущие расстояния: внутри формы расстояния задаёт её собственная `grid gap-4`, а между формой (или блоком сообщений) и ссылкой добавляется такой же `gap-4`, каким он был между кнопкой отправки и ссылкой до исправления. `CardContent` при этом остаётся без дополнительных классов — все три auth-страницы используют его одинаково.

**Альтернативы.**
- *Дублировать ссылку в обеих ветках условного блока* — визуально совпадает с текущим экраном без лишней обёртки, но заводит две копии одного элемента: правка текста или цели должна будет менять обе. Отклонено.
- *Оставить ссылку внутри формы и показывать форму вместе с сообщениями после успеха* — форма исчезает намеренно (сброс выполнен, повторная отправка не нужна), и требование этого не требует; вариант меняет продуктовое поведение шире, чем нужно для исправления. Отклонено.
- *Отдельная страница «пароль сброшен»* — ради одного состояния заводить маршрут, состояние и переходы; дефект касается одной ссылки. Отклонено.

### 2. Ссылка остаётся настоящей ссылкой `react-router` с классами `buttonVariants`

**Решение.** Используется тот же приём, что на странице входа и странице регистрации: `Link` из `react-router` с классами `buttonVariants({ variant: "link", size: "xs" })`.

**Обоснование.** `Link` даёт настоящий `<a href="/auth/login">` с ролью `link`, доступный с клавиатуры и читаемый скринридером, и не порождает консольных предупреждений Base UI, которые возникают при `<Button render={<Link/>}>` (при `nativeButton={false}` элемент получает `role="button"`, и ссылка перестаёт быть ссылкой). Визуально результат совпадает с текущей ссылкой: те же классы `buttonVariants`, тот же ключ локализации `auth.links.toLogin`.

**Альтернативы.**
- *`<Button variant="link" render={<Link/>}>`* — Base UI либо предупреждает о потере нативной семантики, либо ставит `role="button"`; оба варианта хуже для доступности и для тестов. Отклонено.
- *Обычный `<a href>` без `react-router`* — полная перезагрузка страницы и расхождение со способом навигации проекта. Отклонено.

### 3. Регрессия закрывается юнит-тестом страницы и e2e-сценарием

**Решение.** В `frontend/src/test/reset-password-page.test.tsx` добавляется тест «после успешного сброса на странице есть ссылка «Back to sign in», и переход по ней открывает `/auth/login`»; для этого тестовый роутер дополняется маршрутом `/auth/login` с маркером навигации, а сценарий использует уже настроенный мок `postMock` с ответом 204. Дополнительно в `frontend/e2e/auth.spec.ts` добавляется сценарий: отправка формы сброса при моке 204 → видны оба сообщения и ссылка «Back to sign in» → переход открывает `/auth/login`; в том же сценарии проверяется, что неявная отправка формы по Enter в поле email сохраняется (см. Risk/Trade-off ниже).

**Обоснование.** Юнит-тест — основная защита: он детерминирован, выполняется в общем прогоне `npm run test` и проверяет именно то состояние, в котором возник дефект. E2e-сценарий подтверждает то же в реальном браузере тем же мок-контуром, который уже используется для auth-сценариев, и закрывает путь «пользователь после успеха уходит на страницу входа» целиком. Сценарий занятости email и прочие e2e-проверки не затрагиваются.

**Альтернативы.**
- *Только e2e* — проверка медленнее и не попадает в `npm run test`, который запускают чаще. Отклонено как единственная мера.
- *Только юнит-тест* — не подтверждает реальный переход в браузере, где раньше ловились расхождения семантики ссылок. Отклонено как единственная мера.
- *Снимок экрана (snapshot)* — визуальные снимки в проекте не используются, они чувствительны к шрифтам и окружению. Отклонено.

### 4. `skip_specs: true` — спецификация уже описывает нужное поведение

**Решение.** В `.openspec.yaml` установлен `skip_specs: true`; файл дельт не создаётся, основные спецификации `openspec/specs/` не меняются.

**Обоснование.** Требование «Переходы между экранами аутентификации → Сценарий: Возврат к входу» уже существует и формулирует условие без ограничения по состоянию страницы, то есть описывает и состояние формы, и состояние успеха. Продуктовое поведение не меняется — меняется только реализация, которая этому требованию не соответствовала. Дельта-спека с пересказом уже действующего требования была бы избыточной, а требования, «придуманного ради валидации», добавлять нельзя. Регрессионные тесты фиксируют трактовку требования явно, не меняя текст спецификации.

**Альтернативы.**
- *Дельта `## MODIFIED Requirements` с уточнением «в том числе после успешного сброса»* — требование существовало бы и до исправления, а уточнение лишь повторило бы его словами. Отклонено.
- *Новая capability для auth-навигации* — набор требований `frontend/user-authentication` уже описывает эту область; дробление capability ради уточнения одного сценария структурно хуже. Отклонено.

## Risks / Trade-offs

- **[Risk] Перенос ссылки за пределы `<form>` меняет DOM и может повлиять на существующие проверки** → элемент перестаёт быть потомком формы, но остаётся тем же `<a href="/auth/login">` с тем же текстом; `frontend/src/test/reset-password-page.test.tsx` и `frontend/e2e/auth.spec.ts` обращаются к ней по роли и имени, а не по структуре DOM. Митигация: после изменения прогоняются целевые тесты страницы, весь `npm run test` и полный e2e-прогон.
- **[Risk] Смещение вёрстки при переносе ссылки** → расстояние между формой и ссылкой задаётся `gap-4` обёртки и совпадает с прежним `gap-4` формы. Митигация: визуальная проверка страницы в обоих состояниях (форма и успех) в браузере.
- **[Trade-off] Ссылка перестаёт быть частью формы** — семантически это правильнее: переход на страницу входа не является действием формы, и ссылка не должна выглядеть отправкой сброса. Митигация: `<form>` и её кнопка отправки остаются внутри формы, поэтому неявная отправка по Enter в поле email сохраняется (в текущей реализации она работает: один `POST /api/v1/reset` и сообщение об успехе); отдельного e2e-сценария нажатия Enter в проекте раньше не было — в `frontend/e2e/` нет ни одного `press("Enter")`, поэтому проверка добавлена в задачу 2.1 этого изменения.
- **[Trade-off] Трактовка требования «без ограничения по состоянию» закрепляется тестом, а не текстом спецификации** → при следующем расширении auth-экранов требование может потребовать уточнения. Митигация: замечание аудита OS-001 и обоснование в `proposal.md` фиксируют, что спецификация уже покрывает поведение, а расхождение было в реализации.

## Migration Plan

Не применимо — миграций данных, новых маршрутов и зависимостей нет. Развёртывание обычное (`npm run build`). **Откат:** revert изменений `frontend/src/pages/auth/ResetPasswordPage.tsx`, `frontend/src/test/reset-password-page.test.tsx` и `frontend/e2e/auth.spec.ts`.

## Open Questions

Открытых вопросов, способных изменить спецификации, подход или разбиение на задачи, нет. Вопрос «нужна ли возможность повторного сброса после успеха» отложен: он не относится к дефекту, не влияет на требование о ссылке и может быть решён отдельным изменением, если продукт его запросит.
