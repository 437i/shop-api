# Spec Delta

## Purpose

Позволяет администратору управлять клиентами из административной панели: создавать клиента с валидацией, удалять его после подтверждения и изменять адрес существующего клиента из строки списка.

## ADDED Requirements

### Requirement: Форма создания клиента

Система MUST предоставлять форму создания клиента с полями имя, фамилия, дата рождения, пол и адрес (страна, город, улица) и MUST отправлять данные на `POST /api/v1/clients` с Bearer-авторизацией.

#### Scenario: Открытие формы создания

- **WHEN** пользователь находится на странице `/clients` и активирует действие создания клиента
- **THEN** система отображает форму с полями Name, Surname, Birthday, Gender, Country, City, Street
- **THEN** поле Gender предлагает только значения из контракта: `m`, `f`, `n/a`

#### Scenario: Успешное создание клиента

- **WHEN** пользователь отправляет форму с валидными значениями
- **THEN** система отправляет POST-запрос на `/api/v1/clients` с телом `{"name": "<name>", "surname": "<surname>", "birthday": "YYYY-MM-DD", "gender": "m|f|n/a", "address": {"country": "<country>", "city": "<city>", "street": "<street>"}}`
- **THEN** при ответе 201 система закрывает форму
- **THEN** система инвалидирует кеш списка клиентов
- **THEN** созданный клиент отображается в обновлённом списке

#### Scenario: Блокировка повторной отправки

- **WHEN** запрос создания выполняется
- **THEN** кнопка отправки становится disabled и отображает текст выполнения
- **THEN** повторная отправка формы невозможна до завершения запроса

### Requirement: Клиентская валидация формы создания

Система MUST проверять форму до отправки: обязательность полей и ограничение длины 255 символов для имени, фамилии и полей адреса, корректность календарной даты рождения, возраст от 16 до 100 лет включительно, дату не в будущем и значения пола из контракта.

#### Scenario: Пустые обязательные поля

- **WHEN** пользователь отправляет форму с пустым обязательным полем
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Превышение длины поля

- **WHEN** значение имени, фамилии или поля адреса превышает 255 символов
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Возраст ниже допустимого

- **WHEN** дата рождения соответствует возрасту младше 16 лет
- **THEN** система отображает сообщение валидации о минимальном возрасте
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Возраст выше допустимого

- **WHEN** дата рождения соответствует возрасту старше 100 лет
- **THEN** система отображает сообщение валидации о максимальном возрасте
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Граничные возрасты допустимы

- **WHEN** дата рождения соответствует ровно 16 годам или ровно 100 годам на текущую дату
- **THEN** система считает значение валидным и не блокирует отправку по возрасту

#### Scenario: Дата рождения в будущем

- **WHEN** пользователь вводит дату рождения позже текущей даты
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Некорректная календарная дата

- **WHEN** пользователь вводит несуществующую дату, например `2026-02-30`
- **THEN** система отображает сообщение валидации
- **THEN** запрос на `/api/v1/clients` не отправляется

#### Scenario: Границы возраста не зависят от часового пояса

- **WHEN** текущее локальное время находится близко к полуночи и дата рождения попадает ровно на границу 16 или 100 лет по календарной дате пользователя
- **THEN** система определяет возраст по календарным датам без смещения из-за преобразования в UTC

### Requirement: Ошибки мутаций отображаются и сохраняют ввод

Система MUST отображать понятное сообщение при неуспешном ответе мутации (400, 404, 500, 503 или сетевая ошибка) и MUST сохранять введённые данные в открытой форме.

#### Scenario: Ошибка 400 с сообщением

- **WHEN** мутация завершается ответом 400 с полем `message` в ErrorResponse
- **THEN** система отображает сообщение из поля `message`

#### Scenario: Ошибка 400 без сообщения

- **WHEN** мутация завершается ответом 400 без поля `message`
- **THEN** система отображает "Invalid request"

#### Scenario: Ошибка 404

- **WHEN** мутация завершается ответом 404 с полем `message`
- **THEN** система отображает сообщение из поля `message`
- **THEN** при отсутствии поля `message` система отображает локализованное сообщение о том, что клиент не найден

#### Scenario: Ошибки сервера и сеть

- **WHEN** мутация завершается ответом 500 или 503 без поля `message`
- **THEN** система отображает "Server error. Please try again later."
- **WHEN** запрос не возвращает ответ (timeout, network error)
- **THEN** система отображает "Network error. Please try again."

#### Scenario: Ввод сохраняется при ошибке отправки формы

- **WHEN** отправка формы завершается ошибкой
- **THEN** форма остаётся открытой
- **THEN** введённые пользователем значения сохранены

#### Scenario: 401 завершает сессию

- **WHEN** мутация завершается ответом 401
- **THEN** система удаляет токен, очищает кеш и перенаправляет на `/auth/login` в соответствии с существующим глобальным поведением

### Requirement: Удаление клиента с подтверждением

Система MUST предоставлять удаление клиента из строки списка только после явного подтверждения и MUST отправлять `DELETE /api/v1/clients/{id}` с Bearer-авторизацией лишь при подтверждении.

#### Scenario: Подтверждение показывает клиента

- **WHEN** пользователь активирует удаление в строке клиента
- **THEN** система отображает диалог подтверждения с именем и фамилией этого клиента

#### Scenario: Отмена удаления

- **WHEN** пользователь отменяет подтверждение
- **THEN** запрос на удаление не отправляется
- **THEN** список клиентов не изменяется

#### Scenario: Успешное удаление

- **WHEN** пользователь подтверждает удаление
- **THEN** система отправляет DELETE-запрос на `/api/v1/clients/{id}`
- **THEN** при ответе 204 система закрывает диалог подтверждения
- **THEN** система инвалидирует кеш списка клиентов
- **THEN** удалённый клиент отсутствует в обновлённом списке

#### Scenario: Блокировка повторного удаления

- **WHEN** запрос удаления выполняется
- **THEN** элементы управления подтверждения становятся disabled
- **THEN** повторная отправка невозможна до завершения запроса

#### Scenario: Ошибка удаления не меняет список

- **WHEN** запрос удаления завершается ошибкой 400, 404, 500, 503 или сетевой ошибкой
- **THEN** система отображает сообщение об ошибке
- **THEN** список клиентов не изменяется и не инвалидируется

### Requirement: Изменение адреса из строки списка

Система MUST позволять изменять адрес существующего клиента из строки списка, MUST предзаполнять форму текущими значениями адреса из загруженного `ClientResponse` и MUST отправлять на `PATCH /api/v1/clients/{id}/address` только адрес.

#### Scenario: Предзаполнение формы адреса

- **WHEN** пользователь активирует изменение адреса в строке клиента
- **THEN** система отображает форму с текущими значениями country, city, street этого клиента из загруженного списка
- **THEN** система не выполняет дополнительный запрос за данными клиента

#### Scenario: Тело запроса содержит только адрес

- **WHEN** пользователь отправляет форму адреса
- **THEN** система отправляет PATCH-запрос на `/api/v1/clients/{id}/address` с телом `{"address": {"country": "<country>", "city": "<city>", "street": "<street>"}}`
- **THEN** остальные поля клиента в запрос не включаются

#### Scenario: Успешное изменение адреса

- **WHEN** сервер отвечает 204 на PATCH-запрос
- **THEN** система закрывает форму
- **THEN** система инвалидирует кеш списка клиентов
- **THEN** повторное открытие формы адреса для этого клиента показывает обновлённые значения после обновления списка

#### Scenario: Ошибка изменения адреса

- **WHEN** PATCH-запрос завершается ошибкой 400 или 404 с полем `message`
- **THEN** система отображает сообщение из поля `message`
- **THEN** форма остаётся открытой с сохранёнными значениями
- **WHEN** PATCH-запрос завершается ответом 500, 503 или сетевой ошибкой
- **THEN** система отображает сообщение об ошибке в соответствии с общими правилами ошибок мутаций

#### Scenario: Отмена изменения адреса

- **WHEN** пользователь отменяет форму адреса
- **THEN** PATCH-запрос не отправляется
- **THEN** данные списка не изменяются

### Requirement: Инвалидация кеша списка клиентов

Система MUST инвалидировать кеш списка `["clients"]` только после успешного завершения мутации (201 для создания, 204 для удаления и изменения адреса) и MUST NOT инвалидировать его при неуспешных запросах.

#### Scenario: Успешная мутация обновляет кеш

- **WHEN** мутация создания, удаления или изменения адреса завершилась успешно
- **THEN** система помечает кеш списка клиентов устаревшим
- **THEN** список отображает актуальные данные с сервера

#### Scenario: Неуспешная мутация не обновляет кеш

- **WHEN** мутация завершилась ошибкой 400, 404, 500, 503 или сетевой ошибкой
- **THEN** система не инвалидирует кеш списка клиентов
- **THEN** отображаемые данные списка не изменяются

#### Scenario: 401 очищает кеш глобально

- **WHEN** мутация завершилась ответом 401
- **THEN** кеш очищается существующим глобальным обработчиком 401, а сессия завершается

### Requirement: Существующее поведение списка сохраняется

Система MUST сохранять текущее поведение страницы клиентов: состав колонок, skeleton при загрузке, empty state, отображение ошибок и кеширование списка.

#### Scenario: Состав списка не меняется

- **WHEN** список клиентов успешно загружен
- **THEN** таблица отображает колонки Name, Surname, Birthday, Gender, Registration Date без изменений
- **THEN** действия создания, удаления и изменения адреса доступны, но не изменяют состав колонок

#### Scenario: Состояния загрузки, пустого списка и ошибок

- **WHEN** список находится в процессе загрузки
- **THEN** система отображает skeleton загрузки, как раньше
- **WHEN** сервер возвращает пустой массив
- **THEN** система отображает "No clients found", как раньше
- **WHEN** запрос списка завершается ошибкой
- **THEN** система отображает Alert с сообщением, как раньше

### Requirement: Локализация новых сценариев

Система MUST отображать все тексты сценариев управления клиентами (подписи полей, кнопки, диалоги подтверждения, сообщения валидации и ошибок) на выбранном языке: английском или русском.

#### Scenario: Английский язык

- **WHEN** выбранный язык — английский
- **THEN** подписи формы создания, формы адреса, диалога удаления и сообщения валидации отображаются на английском

#### Scenario: Русский язык

- **WHEN** выбранный язык — русский
- **THEN** подписи формы создания, формы адреса, диалога удаления и сообщения валидации отображаются на русском
