# Design

## Context

См. proposal.md — Why для мотивации. Спецификация поведения — `specs/frontend/clients-management/spec.md`.

Текущее состояние: страница `/clients` (`frontend/src/pages/clients/ClientsListPage.tsx`) читает `GET /api/v1/clients` через TanStack Query с ключом `["clients"]` и обрабатывает состояния загрузки/пустого списка/ошибок. HTTP-клиент `frontend/src/shared/api/client.ts` умеет только `get`/`post` и уже возвращает `undefined` для 204. Формы строятся на react-hook-form + zod с i18n-ключами в сообщениях (`pages/auth/loginSchema.ts`). UI-компоненты `dialog`, `alert-dialog`, `select`, `dropdown-menu` уже установлены. Toaster в приложении не смонтирован.

Контракт (проверен по Go-коду):
- `POST /api/v1/clients` → 201 `internal_client.Response`; 400 (binding: `name`/`surname` обязательны и max 255, `birthday` формата `2006-01-02`, `gender` ∈ `m|f|n/a`, `address.country/city/street` обязательны и max 255; сервис: возраст 16–100 включительно, дата не в будущем), 500.
- `DELETE /api/v1/clients/{id}` → 204; 400 (невалидный uuid), 404, 500.
- `PATCH /api/v1/clients/{id}/address` → 204; body `{address: {country, city, street}}`; 400, 404, 500.
- `GET /api/v1/clients/{id}` отсутствует — источник данных для формы адреса только строка списка.
- Middleware: 401 → сброс сессии глобальным обработчиком (`app/providers.tsx`), 503 без поля `message` (`{"error": ...}`) → локализованный fallback.

## Goals / Non-Goals

**Goals:**
- Первые сценарии записи в админ-панели с едиными паттернами: форма в диалоге, подтверждение, инвалидация кеша, обработка ошибок.
- Точное соответствие клиентской валидации контракту Go API.
- Переиспользование существующих зависимостей и стиля (RHF + zod, TanStack Query, shadcn/ui, i18n).

**Non-Goals:**
- Отдельные маршруты для создания/редактирования клиента (нет `GET /clients/{id}` как источника; диалоги достаточны).
- Оптимистичные обновления кеша и toast-уведомления об успехе.
- Рефакторинг существующей страницы списка, клиентов списка и auth-слоя за пределами необходимого.
- Backend-изменения любого рода.

## Decisions

### 1. Размещение UI: диалоги на странице списка

**Решение:** все новые компоненты co-located в `frontend/src/pages/clients/`:
- `CreateClientDialog.tsx` — диалог создания (shadcn/ui `dialog`);
- `EditClientAddressDialog.tsx` — диалог изменения адреса (shadcn/ui `dialog`);
- `DeleteClientDialog.tsx` — подтверждение удаления (shadcn/ui `alert-dialog`);
- `clientFormSchema.ts` — zod-схемы и функции валидации возраста;
- `useClientMutations.ts` — мутации создания/удаления/изменения адреса и общий резолвер ошибок.

`ClientsListPage.tsx` получает кнопку «Add client» и меню действий в строке (`dropdown-menu`: «Edit address», «Delete»); состояние «какой клиент выбран/диалог открыт» — локальный `useState` страницы.

**Альтернативы:**
- Отдельные маршруты `/clients/new`, `/clients/:id/address` — отвергнуто: нет `GET /clients/{id}`, форма адреса всё равно живёт на данных списка, лишняя навигация.
- `src/features/clients/` — папка `features/` зарезервирована под переиспользуемые между страницами фичи; текущие компоненты специфичны для страницы клиентов. Вернуться к выносу, когда появится переиспользование (например, адресные поля для поставщиков).

**Обоснование:** минимальная структура без преждевременных абстракций, согласованная с существующим размещением `pages/*`.

### 2. Расширение API-клиента: `patch` и `delete`

**Решение:** добавить в `shared/api/client.ts` методы `apiClient.patch<TRequest, TResponse>(path, body)` и `apiClient.delete<TResponse>(path)`, реализованные через существующий `request`: Bearer-заголовок из localStorage, парсинг ErrorResponse, `undefined` для 204, глобальная обработка 401 без изменений.

**Альтернативы:**
- Новая HTTP-библиотека — отвергнуто (лишняя зависимость).
- Отдельные функции под каждый endpoint — дублирование логики клиента.

**Обоснование:** 204 уже обрабатывается общим `request`; расширение минимально и переиспользуется всеми разделами.

### 3. Форма: react-hook-form + zod с i18n-ключами

**Решение:** схема `clientFormSchema` по образцу `loginSchema`: обязательность и `max(255)` для `name`, `surname`, `country`, `city`, `street`; `gender` — enum `m|f|n/a`; `birthday` — строка `YYYY-MM-DD`. Сообщения — i18n-ключи (резолвятся через `useTranslation`). Поле пола — shadcn/ui `select`: отображаются локализованные подписи (Male/Female/N/A, М/Ж/Н/Д), в API уходят только сырые значения `m|f|n/a`. Дата рождения — `<input type="date">`.

**Альтернативы:**
- Валидация «руками» без zod — расходится с существующим паттерном.
- Транслитерация/произвольные значения пола — запрещено контрактом.

**Обоснование:** полностью повторяет существующий подход проекта и обеспечивает локализацию сообщений.

### 4. Валидация возраста: календарная дата, устойчивая к часовым поясам

**Решение:** отдельная функция в `clientFormSchema.ts`:
1. строку `YYYY-MM-DD` разобрать регуляркой в компоненты `(y, m, d)`;
2. проверить существование календарной даты round-trip: `new Date(y, m-1, d)` имеет те же компоненты; иначе — ошибка;
3. `today` брать из локальных компонент текущей даты (`getFullYear/getMonth/getDate`), не через `Date`-парсинг строк;
4. вычислить возраст сравнением компонент `(y, m, d)` с `today`; валидный диапазон — от 16 до 100 включительно; дата позже `today` — ошибка.

Такой подход не использует `new Date("YYYY-MM-DD")` (UTC-парсинг) и не смешивает UTC и локальное время. Функция принимает `today` параметром с значением по умолчанию `new Date()`, что делает границы детерминированно тестируемыми (плюс `vi.setSystemTime`).

**Соответствие backend:** Go `validateBirthday` (`api/internal/client/service.go:34-45`) сравнивает инстанты: `bday.After(now)`, `bday.Before(now-100y)`, `bday.After(now-16y)`; для date-only значений это эквивалентно календарному сравнению с границами включительно. При редком расхождении на границе серверный 400 с сообщением показывается пользователю как есть.

**Альтернативы:**
- date-fns/dayjs — новые зависимости, избыточны для одной функции.
- Проверка через `toISOString()` — источник сдвигов даты.

**Обоснование:** детерминированность, тестируемость и отсутствие зависимостей.

### 5. Мутации и владение состоянием

**Решение:** `useClientMutations.ts` экспортирует три хука на базе `useMutation`:
- `useCreateClient` — `POST /clients`, body ровно `{name, surname, birthday, gender, address}`;
- `useDeleteClient` — `DELETE /clients/{id}`;
- `useUpdateClientAddress` — `PATCH /clients/{id}/address`, body ровно `{address: {country, city, street}}`.

Каждый хук в `onSuccess` вызывает `queryClient.invalidateQueries({ queryKey: ["clients"] })` — существующий ключ страницы; при ошибках инвалидация не выполняется. Server state остаётся в TanStack Query, состояние форм — в react-hook-form, состояние диалогов — локальное. Общий `resolveClientMutationError(error, t)` маппит ошибки: `NetworkError` → `errors.network`; 400 → `message` ?? `errors.invalidRequest`; 404 → `message` ?? `errors.notFound`; 401 → `null` (глобальный сброс сессии); прочие → `message` ?? `errors.server`.

**Альтернативы:**
- Оптимистичные обновления `setQueryData` — преждевременно; инвалидация и refetch достаточны и безопаснее.
- Инвалидация всего кеша — избыточна.
- Глобальный стор — не нужен (существующее решение проекта).

**Обоснование:** согласовано с существующим паттерном (`LoginPage` — `useMutation`; `ClientsListPage` — `useQuery`), единая точка правды для кеша.

### 6. Обратная связь и обработка ошибок

**Решение:** успех = закрытие диалога + сброс формы + обновлённый список; toast-уведомления не добавляются (Toaster не смонтирован; добавление — вне scope). Ошибки отображаются inline в диалоге (текст под кнопкой/формой). Формы при ошибке API остаются открытыми, значения сохраняются (RHF не сбрасывается). Во время запроса кнопки отправки/подтверждения disabled. 401 не обрабатывается локально — существующий глобальный обработчик удаляет токен, очищает кеш и перенаправляет на `/auth/login` (полная перезагрузка навигации сбрасывает UI).

**Альтернативы:**
- Toast-уведомления — новая точка монтирования и поведение вне запрошенного scope.
- Оптимистичное закрытие диалога до ответа — противоречит требованию «обновлять список только после успеха».

**Обоснование:** минимальная обратная связь, целиком из уже существующих паттернов.

### 7. Удаление: подтверждение через alert-dialog

**Решение:** действие «Delete» в строке открывает `DeleteClientDialog` (alert-dialog), который показывает имя и фамилию клиента, кнопки подтверждения/отмены; запрос выполняется только по подтверждению; в процессе запроса обе кнопки disabled.

**Альтернативы:**
- Удаление без подтверждения — запрещено требованиями.
- Нативный `window.confirm` — не соответствует UI-kit и плохо тестируется.

**Обоснование:** `alert-dialog` уже установлен и семантически предназначен для деструктивных операций.

### 8. Локализация

**Решение:** новые ключи в существующий namespace `common` (файлы `en/common.json` и `ru/common.json` синхронно): секции `clients.actions`, `clients.create`, `clients.editAddress`, `clients.delete`, `clients.validation`, `gender.*`, дополнение `errors.notFound`. Значения enum (`m`, `f`, `n/a`) не переводятся — локализуются только подписи.

**Обоснование:** один namespace — принятое решение foundation; разделение преждевременно.

### 9. Тестирование

**Решение:**
- Unit (Vitest + Testing Library, размещение в `src/test/` как существующие тесты):
  - `clients-management-schema.test.ts` — границы возраста (15/16/17, 99/100/101), будущая дата, некорректная дата (`2026-02-30`), длины, enum; `today` передаётся параметром;
  - `clients-management.test.tsx` — рендер `ClientsListPage` с диалогами: создание (успех, 400/500/сеть, сохранение ввода, pending), удаление (отмена, успех 204, 404 без инвалидации, pending), адрес (предзаполнение, тело только с address, успех, ошибки), инвалидация `["clients"]` после успеха. Мок fetch — `vi.stubGlobal("fetch")` с маршрутизацией по методу/URL, как в существующих тестах.
- E2E (Playwright): `e2e/helpers.ts` расширяется method-aware перехватами `POST /api/v1/clients`, `DELETE /api/v1/clients/{id}`, `PATCH /api/v1/clients/{id}/address` (существующие сценарии не затрагиваются); новый `e2e/clients-management.spec.ts` проверяет видимый результат: появление созданного клиента в таблице, сообщение об ошибке 400 при создании, подтверждение и исчезновение клиента после удаления, изменение адреса с проверкой обновлённых значений при повторном открытии формы.

**Обоснование:** полное соответствие существующим тестовым соглашениям; e2e проверяет пользовательский результат, а не только вызовы endpoints.

## Risks / Trade-offs

### [Риск] Расхождение клиентской и серверной проверки возраста на границе суток
**Митигация:** фронтенд допускает границы 16 и 100 включительно, как backend; типовая валидация отсекает ошибки до запроса; при редком расхождении серверный 400 с `message` показывается пользователю без искажения.

### [Риск] Устаревшие данные адреса в форме (кеш до 5 минут)
**Митигация:** форма адреса всегда открывается из данных строки списка, которые обновляются инвалидацией после каждой успешной мутации; дополнительный запрос за клиентом контрактом не предусмотрен.

### [Риск] Англоязычные сообщения backend о возрасте
**Митигация:** сообщения показываются как есть — существующий паттерн проекта; локализуются только клиентские сообщения валидации и fallback-тексты.

### [Trade-off] Нет toast-уведомлений об успехе
**Обоснование:** Toaster не смонтирован; обратная связь — закрытие диалога и обновлённый список. Добавление тостов — отдельное решение вне scope.

### [Trade-off] Нет оптимистичных обновлений
**Обоснование:** инвалидация + refetch проще и исключает рассинхронизацию; при текущих объёмах данных задержка незаметна.

### [Ограничение] Ручная проверка — только с dev-mock auth
**Обоснование:** реальная аутентификация недоступна до подключения Java auth service; ограничение уже задокументировано в `frontend/README.md`.

## Migration Plan

Не применимо — миграции данных нет, новых маршрутов и зависимостей нет. Deployment обычный (`npm run build`). **Rollback:** revert изменений `frontend/` (диалоги, расширение API-клиента, ключи i18n, тесты); состояние данных не затрагивается.
